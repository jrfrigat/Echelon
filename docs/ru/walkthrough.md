# Echelon - Первая настройка по шагам

> [English version ->](../en/walkthrough.md) - [← К оглавлению](../README.md)

Сервис развёрнут, вы открыли админку и не знаете, что заполнять первым. Этот документ - ровно об
этом: что и куда добавить, какими значениями, и **что должно произойти после каждого шага**, чтобы
не идти дальше вслепую.

Установка и переменные окружения - в [Начале работы](getting-started.md). Зачем нужна каждая часть -
в [Руководстве пользователя](user-guide.md). Здесь - только порядок действий.

---

## Как это устроено, в двух абзацах

**Руками заводятся только настройки. Данные приходят сами.** Задачи оркестратор читает из трекера,
merge request'ы и ветки - из VCS. Ни задачу, ни merge request создать в интерфейсе нельзя, и это не
недоделка: они уже существуют в системах, которые ими владеют.

Поэтому настройка - это три ответа: **куда ходить** (подключения), **что там читать** (репозитории)
и **куда катить** (окружения и цели выкатки). Дальше задачи появляются сами, на каждую строится
план, и план запускается в окружение.

**Первый прогон делайте на подключениях в режиме опроса (`-poll`)**, даже если в бою будут вебхуки.
Опрос не требует, чтобы GitLab и трекер достучались до вашего ingress, и даёт кнопку «Опросить
сейчас» - не надо ждать события, чтобы понять, работает ли связка. Вебхуки включаются потом,
[шагом 13](#шаг-13-вебхуки-вместо-опроса).

# Часть A. Минимальный путь до первой выкатки

Тринадцать шагов; первые одиннадцать - обязательные. Все экраны - в левом меню.

## Шаг 1. Убедиться, что у вас есть права

Откройте **Администрирование → Права доступа**. Если страница открылась и показывает список прав -
всё в порядке, идите к шагу 2. Если API отвечает 403 или кнопки сохранения не работают, у вашей
учётной записи нет права `config.edit`.

Права всего четыре, и они хранятся в БД под этими именами:

| Право | Что разрешает |
| :-- | :-- |
| `release.plan.view` | Читать задачи, планы, merge request'ы и выкатки. Базовое право |
| `config.edit` | Всё администрирование: подключения, репозитории, окружения, сами права |
| `release.execute` | Запускать, отменять, повторять и пропускать выкатки |
| `release.plan.approve` | Решения о готовности: пины на merge request'ах, ручной статус |

Первому администратору права выдаются переменной окружения - см.
[Начало работы, §1](getting-started.md). После входа под ней раздайте права остальным на этом же
экране и переменную уберите.

## Шаг 2. Подключение к VCS

**Администрирование → Подключения к VCS → «Новое подключение»**

| Поле | Пример значения | Замечания |
| :-- | :-- | :-- |
| Название | `gitlab-main` | **Только латиница, цифры, `-` и `_`** (до 100 символов). Имя подставляется в URL вебхука, и имя вида `GitLab (прод)` сделает вебхук неработающим. Переименовать подключение потом можно, но URL вебхука сменится вместе с ним |
| Тип | `gitlab-poll` | Для первого прогона. `gitlab-webhook` - когда GitLab сам шлёт события. **Тип задаётся при создании и потом не меняется**: чтобы перейти с опроса на вебхуки, создайте второе подключение |
| Адрес API | `https://gitlab.company.ru` | Корень инстанса, без `/api/v4` |
| Poll interval (seconds) | `60` | Только у `gitlab-poll`. Допустимо 30 - 86400, по умолчанию 300 |
| Task-key source | `branch` | Откуда брать ключ задачи: ветка, заголовок MR или метка |
| Task-key pattern | оставьте как есть | Regex по умолчанию берёт ключ в верхнем регистре: `PROJ-42`, `ПР-5639`. Кириллица поддерживается |
| Токен доступа | `glpat-…` | Скоупы `api` и `read_repository`. Хранится зашифрованным; при редактировании пустое поле означает «оставить прежний» |

Подписи `Poll interval (seconds)`, `Task-key source` и прочие настройки провайдера - **на
английском независимо от языка интерфейса**: их объявляет сам провайдер, а не приложение.

**Проверьте правило связи, не сохраняя форму.** Под полями есть живой предпросмотр: введите пример
ветки - `feature/PROJ-42-add-login` - и он покажет извлечённый ключ (`PROJ-42`). Если ключ не
извлекается, merge request'ы приедут, но ни к одной задаче не привяжутся, и никакого сообщения об
этом не будет.

**После шага:** подключение в списке, в колонке «Тип» - чип `gitlab-poll`, справа появилась иконка
обновления (это и есть «Опросить сейчас»).

## Шаг 3. Подключение к трекеру

**Администрирование → Подключения к трекеру → «Новое подключение»**

| Поле | Пример значения | Замечания |
| :-- | :-- | :-- |
| Название | `tracker-main` | Те же ограничения на символы, что и у VCS-подключения |
| Тип | `yandextracker-poll` | Для первого прогона. `yandextracker-webhook` - когда трекер шлёт события сам |
| Адрес API | `https://api.tracker.yandex.net` | |
| Poll interval (seconds) | `60` | Только у `-poll` |
| **Queues to sweep** | `PROJ, INFRA` | **Ключевое поле.** Ключи очередей через запятую. Из них строится запрос `Queue: PROJ, INFRA AND Resolution: empty()` - это и есть единственный способ, которым система вообще узнаёт о существовании задач |
| Search query (optional) | пусто | Целый запрос на языке трекера - вместо очередей, если «открытая» у вас определяется не отсутствием резолюции |
| Organization ID | `1234567` | Уходит заголовком `X-Org-Id`. Обязательное поле: без него подключение не создастся |
| Closed statuses | пусто | Пусто = значения по умолчанию (`closed, cancelled, rejected, resolved`). Это статусы, при которых задача считается завершённой |
| Токен доступа | ваш OAuth-токен | Уходит как `Authorization: OAuth <токен>` |

**Если оставить Queues to sweep пустым, опрос не найдёт ни одной задачи** и скажет об этом прямо -
но только когда вы нажмёте «Опросить сейчас». Молча пустой список - самая частая причина «я всё
настроил, а задач нет».

**После шага:** подключение в списке с чипом `yandextracker-poll` и иконкой обновления.

## Шаг 4. Репозитории

**Администрирование → Репозитории → «Новый репозиторий»**

Заведите каждый репозиторий, которым будет управлять оркестратор.

| Поле | Пример значения | Замечания |
| :-- | :-- | :-- |
| Название | `Backend` | Как его называете вы; видно в планах и выкатках |
| Внешний ID | `my-group/backend` | **Полный путь в GitLab**, а не имя проекта. `backend` даст 404, и репозиторий будет молча пропускаться при каждом опросе |
| Подключение к VCS | `gitlab-main (gitlab-poll)` | |

Это не формальность: **merge request из незарегистрированного репозитория отбрасывается.** Событие
дойдёт до сервиса и будет посчитано на экране «Приём», но в списке «Что выкатывать» ничего не
появится - в логе останется предупреждение `Repository not found`. Опрос точно так же обходит
**только** зарегистрированные репозитории.

**После шага:** репозиторий в списке; колонка «Подключение к VCS» заполнена.

## Шаг 5. Окружение

**Администрирование → Окружения** - форма прямо над таблицей.

| Поле | Пример значения | Замечания |
| :-- | :-- | :-- |
| Ключ | `dev` | Короткий машинный ключ; по нему адресуются цели выкатки и области действий |
| Название | `Разработка` | |
| Порядок | `10` | Позиция в прогрессии контуров: `dev` 10, `staging` 20, `prod` 30 |
| Проверка | **Без проверки** | Для первого прогона - именно так. Правило готовности добавите в [части B](#b1-правила-готовности) |

Кнопка - «Добавить окружение».

**После шага:** строка в таблице, «Проверка» пустая, «Включено» - да. Выключенное окружение в
выборе при запуске не появляется.

## Шаг 6. Цель выкатки

**Администрирование → Цели выкатки**

Одна строка на пару **(репозиторий, окружение)**: чем именно катить этот репозиторий в этот контур.
**Без цели выкатки запуск откажет** сообщением вида «Repository 'Backend' has no deploy strategy for
environment 'dev'».

| Поле | Пример значения | Замечания |
| :-- | :-- | :-- |
| Репозиторий | `Backend` | |
| Контур | `dev` | |
| Стратегия | `gitlab-merge` | Чем именно катить - см. три варианта ниже |
| Повтор | `Один раз` | `Всегда` разрешает повторную выкатку того же MR в этот контур |
| Готовность | «по умолчанию» | Переопределение правила окружения для этого репозитория |

Стратегий три, и выбор между ними - это выбор того, **что вообще считается выкаткой**:

| Стратегия | Что делает | Свои поля |
| :-- | :-- | :-- |
| `gitlab-merge` | Вливает merge request | нет |
| `gitlab-pipeline` | Запускает **новый** пайплайн по ветке или тегу и ждёт его | `Pipeline ref` - ветка или тег, по умолчанию `main` |
| `gitlab-job` | Запускает **одну job'у в последнем пайплайне самого merge request'а** и ждёт её | `Job name`, `Re-run` |

**`gitlab-job` - это про ручной гейт в существующем пайплайне.** Пайплайн MR уже прошёл, артефакт собран, и выкатить - значит нажать на нём одну кнопку (`deploy:staging`). `gitlab-pipeline` для этого не годится: он запускает **второй** пайплайн, то есть пересобирает всё заново и по голове ветки, а не по тому коммиту, который тестировался.

| Поле | Пример значения | Замечания |
| :-- | :-- | :-- |
| Job name | `deploy:staging` | Имя job'ы **точно как в `.gitlab-ci.yml`**, с учётом регистра. Если ошибётесь - выкатка откажет и перечислит, какие job'ы в пайплайне есть на самом деле |
| Re-run | `if-not-successful` | Что делать, если эта job'а уже выполнена успешно. По умолчанию - считать выкатку уже сделанной. `always` - запустить ещё раз (это и имеет в виду «Повтор: Всегда» на цели выкатки, если job идемпотентна) |

Что происходит по состоянию job'ы: ждущая ручного запуска (`manual`) - **запускается** (`play`); уже отработавшая (`failed`, `canceled`, `skipped`) - **перезапускается** (`retry`, это новая job'а с новым id); уже идущая - подхватывается, а не запускается второй раз; успешная - `Уже выполнено`, если `Re-run` не `always`.

Повторите для каждого репозитория из шага 4.

**После шага:** строки в таблице целей.

## Шаг 7. Первый опрос трекера

**Администрирование → Подключения к трекеру** → иконка обновления в строке подключения.

Кнопка сообщит, сколько задач поставлено на синхронизацию и сколько из них новых. Если трекер
прочитать не удалось, вы увидите причину - обычно незаданные очереди или отвергнутый токен, - а не
«ничего не найдено».

**После шага:** сообщение вида «поставлено на синхронизацию: 12, из них новых: 12».

## Шаг 8. Первый опрос VCS

**Администрирование → Подключения к VCS** → иконка обновления.

Опрос обходит все репозитории подключения, отправляет по событию на каждый открытый merge request и
отдельно - список веток. Репозиторий, который прочитать не удалось, называется по имени, а остальные
всё равно обрабатываются.

**После шага:** сообщение о числе отправленных событий и список нечитаемых репозиториев, если такие
были.

## Шаг 9. Проверить экран «Приём»

**Администрирование → Приём**

Это ответ на вопрос «дошло ли хоть что-нибудь». Три таблицы:

- **Раннеры** - «Опрос VCS», «Опрос трекера», «Сверка задач». Состояние: *работает*, *ждёт*,
  *другая реплика* (сейчас этим занят другой экземпляр сервиса) или *выключен*. Плюс период,
  последний проход, длительность и проблема, если проход упал;
- **Что пришло** - счётчики по видам с момента старта процесса: «Создано задач», «Увидено merge
  request'ов», «Увидено веток», «Пересчётов плана». Считается одинаково для вебхука и опроса;
- **Последний опрос по соединениям** - по строке на каждое poll-подключение, с именами
  репозиториев, которые прочитать не удалось.

Экран обновляется сам раз в 5 секунд. Счётчики - **по реплике и с момента её запуска**: перезапуск
сервиса обнуляет их, это не потеря данных.

**Что должно быть видно:** «Создано задач» больше нуля и «Увидено merge request'ов» больше нуля.
Если сигнал посчитан, а данных в списках нет - смотрите [часть C](#часть-c-если-что-то-пошло-не-так).

## Шаг 10. Задачи и merge request'ы

**Задачи** - список импортированных задач: ключ, заголовок, статус, число MR, есть ли план.

**Что выкатывать** - единицы работы: задача, репозиторий, носитель (merge request или просто ветка),
состояние и готовность. Здесь же ставится ручной статус merge request'а, если провайдер чего-то не
сообщил.

**Что должно быть видно:** ваша задача (`PROJ-42`) в списке задач, и её merge request'ы - в «Что
выкатывать», с непустой колонкой «Задача». Если MR есть, а задача в его строке не указана - правило
связи из шага 2 не сработало.

## Шаг 11. Построить план

**Задачи → откройте задачу → «Построить план»** (у уже построенного - «Пересчитать план»).

План - это волны: внутри волны всё катится параллельно, волна 2 ждёт волну 1. Пока правил порядка
нет, все репозитории задачи попадают в первую волну - это нормально.

Кнопка «Показать YAML» отдаёт план текстом: его можно сохранить, отредактировать и загрузить
обратно.

**После шага:** карточки волн с merge request'ами. Если сверху предупреждение о конфликтах -
кнопка запуска будет заблокирована, пока конфликты не разрешены.

## Шаг 12. Запустить выкатку

На той же странице: выберите **Окружение** (`dev`) и нажмите **«Запустить выкатку»**. Переключатель
«Повторно» оставьте выключенным.

Откроется страница выкатки: шаги по волнам, их состояния, события. Все выкатки - в разделе
**Выкатки**.

**Если запуск отказал** - причина будет в сообщении, и она всегда одна из трёх: нет цели выкатки для
репозитория, merge request не прошёл проверку готовности, или план устарел и его надо пересчитать.

## Шаг 13. Вебхуки вместо опроса

Когда цепочка проехала на опросе целиком, можно переводить на вебхуки - события приходят за секунды,
а не по таймеру.

**Тип подключения при создании фиксируется**, так что переход - это новое подключение с типом
`gitlab-webhook` / `yandextracker-webhook`; репозитории придётся перепривязать (создать заново на
новом подключении), поэтому лучше решить это до того, как накопится история.

Куда слать:

| Провайдер | URL (на **ingress**-сервисе) | Заголовок с секретом |
| :-- | :-- | :-- |
| GitLab | `POST https://ingress.company.ru/webhooks/gitlab/gitlab-main` | `X-Gitlab-Token` |
| Яндекс.Трекер | `POST https://ingress.company.ru/webhooks/tracker/tracker-main` | `X-Tracker-Token` |

Последний сегмент URL - **название подключения**, поэтому оно и ограничено латиницей.

Секрет задаётся конфигурацией ingress-сервиса, а не в интерфейсе:

```bash
Webhooks__GitLab__gitlab-main__Token=<секрет, который вы вписали в GitLab>
Webhooks__Tracker__tracker-main__Token=<секрет трекера>
```

Неверный или отсутствующий секрет - `401` без тела. Неизвестное имя подключения - тоже `401`, чтобы
по разнице ответов нельзя было перебрать список подключений.

# Часть B. Что настроить после первого успеха

## B1. Правила готовности

**Администрирование → Правила готовности**

Что merge request должен показать, прежде чем его вообще можно катить. Правило - набор
**сигналов**, объединённых по «Все из» или «Любая из».

Сигнал - это токен `вид:значение`:

| Вид | Пример | Откуда берётся |
| :-- | :-- | :-- |
| `label:` | `label:ready-prod` | Метки merge request'а |
| `mr-status:` | `mr-status:merged` | Нормализованный статус MR |
| `pipeline:` | `pipeline:success` | Результат последнего пайплайна (у опроса есть, у вебхука - нет) |

Под полем ввода - **словарь кликом**: чипы со всеми статусами и со всеми метками, которые реально
встретились в ваших merge request'ах. Правило, требующее сигнал, которого ни у кого нет, - это
шлагбаум, который никто не пройдёт, и узнаете вы об этом при запуске.

Пример: Название `prod-gate`, Совпадение `Все из`, Требуемые сигналы
`label:ready-prod pipeline:success`.

Дальше правило назначается **окружению** (поле «Проверка» на экране «Окружения») и при необходимости
переопределяется на конкретной **цели выкатки**.

Проверка блокирует **весь запуск**, а не отфильтровывает неготовые MR: у merge request'ов одной
задачи есть зависимости по порядку, и выкатить часть, тихо выбросив остальные, - это неполная
выкатка, которая выглядит завершённой.

Точечное исключение - **пин** на конкретном merge request'е: на странице задачи, иконка булавки в
строке MR, отдельно по каждому окружению. Требует права `release.plan.approve`.

## B2. Порядок выкатки

**Администрирование → План по умолчанию**

Порядок задаётся один раз и применяется к каждой задаче. Два режима, **один документ**: визуальный
редактор строит YAML, который тут же читается тем же читателем, что и у планировщика.

```yaml
version: 1

groups:
  db:
    repositories: ["my-group/migrations"]
  backend:
    repositories: ["my-group/backend"]
  frontend:
    repositories: ["my-group/web"]

order:
  - group: backend
    needs: [db]
    type: hard        # hard - настоящее ограничение; soft - предпочтение, уступает при цикле
  - group: frontend
    needs: [backend]
    type: soft
```

Селекторы поддерживают glob: `repositories: ["my-group/svc-*"]`, оси `connectors`, `branches`,
`tasks.keys`, `tasks.labels` и вложенный `exclude`. Полное описание языка - в
[012 - Язык правил порядка](../issues/012-ordering-rules.md).

Здесь же живёт политика ожидания задач:

```yaml
tasks:
  wait_for_subtasks: true
  wait_for_linked: true
  group_order: together      # together | subtasks_first | linked_first
```

Страница сразу показывает получившиеся волны и отдельно - конфликты (правила, которые
противоречат друг другу).

## B3. Обработчики действий

**Администрирование → Обработчики действий**

Привязка «событие → действие».

События, которые сервис действительно отправляет: `RolloutSucceeded`, `RolloutFailed` (выкатка
встала на упавшем шаге), `RolloutCancelled`, `RolloutChanged`.

Действия:

| Тип действия | Настройки |
| :-- | :-- |
| `telegram` | `botToken` (секрет), `chatId`, `template` |
| `tracker-status` | `status` - целевой статус в терминах вашего трекера |
| `tracker-comment` | `template` |

В шаблоне доступны `{task}`, `{environment}`, `{status}`, `{event}`.

**Область (необязательно)** сужает привязку: `env:prod` - только выкатки на prod, `task:PROJ-42` -
только эта задача. Пустая область - все события этого типа.

Пример: Тип события `RolloutSucceeded`, Тип действия `tracker-comment`, Область `env:prod`,
template `Выкачено на {environment}`.

Отказ действия изолирован: он пишется в лог и не роняет ни шаг выкатки, ни соседние привязки.

## B4. Права доступа

**Администрирование → Права доступа → «Добавить сопоставление»**

Сопоставление «SID группы AD → право». SID вставляется целиком (`S-1-5-21-…`), право выбирается из
списка шага 1. Обладатель `config.edit` может выдать любое право кому угодно, включая себя, поэтому
каждое изменение здесь попадает в **Журнал запросов**.

# Часть C. Если что-то пошло не так

Идите по симптому. Почти всё диагностируется экраном **Приём** плюс двумя кнопками «Опросить
сейчас».

### Задач нет вообще

- Тип подключения к трекеру - `yandextracker-webhook`? Тогда задачи приходят только вебхуком, сам
  он ничего не ищет. Для поиска нужен тип `-poll`.
- У `-poll`-подключения **пустое Queues to sweep** - искать негде. Нажмите «Опросить сейчас»:
  причина будет названа.
- Раннер «Опрос трекера» на экране «Приём» - *выключен*? Значит, опрос отключён конфигурацией
  (`TrackerPolling__Enabled`). По умолчанию он включён с периодом 60 с.
- Токен или Organization ID не приняты - «Опросить сейчас» покажет ответ трекера.

### Задачи есть, merge request'ов нет

- **Репозиторий не зарегистрирован** (шаг 4) - самая частая причина. Признак характерный: на экране
  «Приём» счётчик «Увидено merge request'ов» растёт, а список «Что выкатывать» пуст. В логе -
  `Repository not found for connection=…, path=…`.
- **Внешний ID - не полный путь.** GitLab хочет `group/project`; `backend` даёт 404. Такой
  репозиторий будет назван в колонке «Проблема» последнего опроса.
- Merge request закрыт или уже влит - опрос забирает только открытые.

### Merge request'ы есть, но не привязаны к задаче

- Правило связи (шаг 2). Откройте подключение и вбейте в предпросмотр **реальное** имя ветки:
  сразу видно, извлекается ключ или нет.
- Источник ключа выбран не тот: ключ в заголовке MR, а в настройках стоит `branch`.
- Ключ задачи в нижнем регистре (`proj-42`) - шаблон по умолчанию требует верхний.
- Задача с таким ключом есть **в двух трекерах** - тогда связь не ставится намеренно, чтобы не
  ошибиться. Лечится привязкой репозитория к конкретному трекеру (см. приложение).

### План пустой или не строится

- У задачи нет ни одного merge request'а - смотрите предыдущий пункт.
- План старше, чем текущее устройство волн: сообщение «Recalculate the plan before launching».
  Нажмите «Пересчитать план».
- Предупреждение о конфликтах - в правилах порядка есть цикл или противоречие; запуск заблокирован
  осознанно.

### Запуск выкатки отказывает

- **«has no deploy strategy for environment …»** - нет цели выкатки для этого репозитория и контура
  (шаг 6).
- **Не пройдена проверка готовности** - у merge request'а нет требуемых сигналов. Посмотрите
  колонку «Готовность» в «Что выкатывать», добавьте метку в GitLab и опросите подключение заново
  либо поставьте пин (B1).
- **В выборе нет окружений** - все окружения выключены; включите нужное на экране «Окружения».

### Повторная выкатка не происходит

Нужны **оба** условия: переключатель «Повторно» при запуске **и** политика `Всегда` у цели выкатки.
Одного из них недостаточно - это защита от случайного повторного деплоя на прод.

### Счётчики на «Приёме» обнулились

Так и задумано: они живут в памяти реплики и считаются с её старта. Это факты о живом процессе, а не
история. История задачи - на её таймлайне, история запросов - в «Журнале запросов».

## Приложение. Что пока задаётся только через API

**Привязка репозитория к трекеру** (`TrackerConnectionId`). Форма репозитория её не предлагает,
хотя API принимает. Пока трекер один, она не нужна: ключ задачи ищется глобально. Она становится
нужна, когда трекеров два и один и тот же ключ (`PROJ-42`) существует в обоих - без привязки связь
не ставится вовсе, чтобы не поставить неверную.

```
PUT /api/repositories/{id}
{ "name": "Backend", "externalId": "my-group/backend",
  "connectionId": "…", "trackerConnectionId": "…" }
```

Интерактивная документация ко всему API - на `/swagger`; там же можно выполнить запрос из браузера
под своей учётной записью.
