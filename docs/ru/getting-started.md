## Требования

- **.NET SDK 10** (для сборки)
- **SQL Server 2019+** или **PostgreSQL 14+** (рабочая и архивная БД - поддерживаются оба провайдера)
- **RabbitMQ 3.8+** (шина сообщений)
- **Redis 6.0+** (кэш вычисленных прав)
- **Docker и Docker Compose** (рекомендуется для локальной разработки)
- Провайдер аутентификации: OpenID Connect (например, Azure AD, Keycloak) или встроенный провайдер `Local` для разработки

## 1. Локальный запуск через Docker Compose

Проще всего запустить локально через Docker Compose - все нужные сервисы уже включены.

### 1.1 Подготовьте файл `.env`

В корне проекта создайте `.env` на основе `.env.example`:

```bash
# SQL Server
MSSQL_SA_PASSWORD=YourComplexPassword123!
SA_PASSWORD=YourComplexPassword123!

# RabbitMQ
RABBITMQ_DEFAULT_USER=guest
RABBITMQ_DEFAULT_PASS=guest

# Redis (пусто - без авторизации в dev)
REDIS_PASSWORD=

# OpenID Connect (настройте своего провайдера или используйте Auth:Provider=Local в dev)
OIDC_AUTHORITY=https://your-oidc-provider/.well-known/openid-configuration
OIDC_CLIENT_ID=your-client-id
OIDC_CLIENT_SECRET=your-client-secret
OIDC_REDIRECT_URI=https://localhost:5173/authentication/login-callback

# Echelon
ASPNETCORE_ENVIRONMENT=Development
CONNECTION_STRING_DEFAULT=Server=sqlserver;Database=Echelon;User Id=sa;Password=YourComplexPassword123!;TrustServerCertificate=true;
CONNECTION_STRING_ARCHIVE=Server=sqlserver;Database=EchelonArchive;User Id=sa;Password=YourComplexPassword123!;TrustServerCertificate=true;
REDIS_CONNECTION_STRING=redis:6379
QUEUE_USERNAME=guest
QUEUE_PASSWORD=guest
QUEUE_HOST=rabbitmq
QUEUE_PORT=5672
```

**⚠️ ВАЖНО для production:**
- Используйте надёжные пароли (не `guest`)
- Включите авторизацию Redis (`--requirepass`)
- Используйте HTTPS с корректными сертификатами
- Установите `ASPNETCORE_ENVIRONMENT=Production`
- Настройте реальные учётные данные OIDC

### 1.2 Запустите сервисы

```bash
docker-compose up -d
```

Дождитесь готовности БД (30-60 секунд):

```bash
docker-compose logs -f sqlserver | grep "Recovery is complete"
```

### 1.3 Примените миграции БД

По умолчанию приложение накатывает незавершённые миграции при запуске (`Database:MigrateOnStartup`),
так что для одиночного или локального запуска этот шаг можно пропустить. Применяйте вручную, если это
отключили - например, при развёртывании на нескольких репликах, где одновременная авто-миграция гонялась
бы, и миграции запускают из init-контейнера или CI:

Миграции лежат в отдельном проекте под провайдера (`...Migrations.MsSql` для SQL Server,
`...Migrations.Postgres` для PostgreSQL). Возьмите тот, что соответствует вашей БД, и накатите **оба**
контекста:

```bash
# Из корня проекта - рабочая БД
dotnet ef database update --project src/Echelon.Migrations.MsSql \
  --startup-project src/Echelon.Web \
  --context AppDbContext

# Архивная БД
dotnet ef database update --project src/Echelon.Migrations.MsSql \
  --startup-project src/Echelon.Web \
  --context ArchiveDbContext
```

### 1.4 Создайте администратора (bootstrap)

При первом запуске ни у кого нет прав. Режим bootstrap-администратора выдаёт права первому:

```bash
# Временно, только на этот запуск
$env:AUTHORIZATION__BOOTSTRAPADMINOBJECTIDS="your-oid-value"

# Затем запустите приложение
dotnet run --project src/Echelon.Web
```

**Как найти свой OID:**
1. Войдите через своего провайдера
2. Приложение создаст запись пользователя
3. Найдите в логах свой claim `oid`
4. Укажите это значение в `AUTHORIZATION__BOOTSTRAPADMINOBJECTIDS` и перезапустите

После входа как bootstrap-администратор вы получаете полные права и можете выдать их другим через
**Admin -> Permissions**. В production переменную `AUTHORIZATION__BOOTSTRAPADMINOBJECTIDS` уберите
(предохранитель: пока она задана, админом становится любой, кто под неё подходит).

## 2. Настройка оркестратора

Всё настраивается из меню **Administration**, примерно в порядке ниже - каждый шаг зависит от
предыдущих. Это и есть вся настройка; YAML руками писать не нужно.

Ниже - что лежит на каждом экране. Тот же путь пронумерованными шагами, с примерами значений в
каждом поле и проверкой после каждого шага, - в [Первой настройке](walkthrough.md).

### 2.1 VCS-подключения (`Admin -> VCS Connections`)

Подключение к каждому инстансу GitLab, откуда оркестратор читает merge request'ы и который выкатывает.

- **Name** - имя подключения.
- **Type** - `gitlab-webhook` (GitLab шлёт события в ingress оркестратора) или `gitlab-poll`
  (оркестратор опрашивает сам, с интервалом, который вы задаёте). Push или poll - это *тип*, а не
  переключатель на подключении.
- **API URL** - например `https://gitlab.company.com`.
- **Access Token** - токен со скоупами `api`, `read_repository` (шифруется при хранении).
- **Правило связи** - как входящий merge request сопоставляется с задачей трекера: **источник ключа**
  (ветка, заголовок или метка) и **шаблон (regex)**. По умолчанию извлекается ключ в верхнем регистре
  вроде `PROJ-12`. Форма показывает **живой предпросмотр** - введите пример ветки/заголовка/метки, и
  она покажет, какой ключ извлечёт правило, так что настроить его можно до сохранения.
- **Только `gitlab-poll`** - среди настроек добавляется **интервал опроса** (в секундах).

Поля "ready-for-deploy label" нет - готовность к выкатке настраивается отдельно (§2.5).

### 2.2 Подключения трекеров (`Admin -> Tracker Connections`)

Задачи, их статусы, зависимости и иерархия приходят из трекера.

- **Name**, **API URL** (`https://api.tracker.yandex.net`), **Access Token**.
- **Type** - `yandextracker-webhook` (принимает вебхуки задач) или `yandextracker-poll` (без вебхука; трекер опрашивается с **интервалом опроса**, который вы задаёте, поэтому poll-типу нужны ещё и **Queues to sweep** - без них искать негде и ни одна задача не будет найдена).
- **Organization ID** - отправляется в заголовке `X-Org-Id` (Yandex Tracker).
- **Closed statuses** - список статусов через запятую, означающих, что задача *завершена*; пусто -
  значения по умолчанию (`closed, cancelled, rejected, resolved`).

### 2.3 Репозитории (`Admin -> Repositories`)

Зарегистрируйте каждый репозиторий, которым управляет оркестратор.

- **Name**, **External ID** (путь в VCS, например `my-group/my-project`) и его **VCS-подключение**.
- Репозиторию также нужна **стратегия выкатки** (как его катить - влить MR или запустить пайплайн).
  Она задаётся как **deploy target** на окружение (§2.6); без неё шаг выкатки не выполнится.

### 2.4 План выкатки по умолчанию (`Admin -> Default Plan`)

Порядок, который применяется к **каждой** задаче - настраивается один раз, а не на каждый релиз.
Единого глобального плана и "стеков" нет: вы задаёте правила порядка между репозиториями по одной паре
(*репозиторий A катится после репозитория B*), а страница показывает **волны**, в которые они
складываются. Каждое правило **жёсткое** (настоящее ограничение, не отбрасывается) или **мягкое**
(предпочтение, уступает первым при конфликте). Репозитории без правил катятся вместе в первой волне.

### 2.5 Правила готовности (`Admin -> Readiness Rules`)

Что merge request должен показать, прежде чем его можно выкатить. Правило - набор нормализованных
**сигналов**: метка (`label:ready-prod`), статус merge request'а (`mr-status:merged`) или результат
пайплайна (`pipeline:success`), объединённых по **AllOf** (все из) или **AnyOf** (любой из). Создайте
нужные проектам правила здесь; назначаются они в §2.6.

### 2.6 Окружения и deploy targets

- **Окружения** (`Admin -> Environments`) - у каждого целевого окружения есть ключ (`prod`), имя,
  порядок и опциональное **правило готовности** (§2.5). Окружение без правила ничего не ограничивает.
- **Deploy targets** (`Admin -> Deploy Targets`) - для каждой пары `(репозиторий, окружение)`:
  **стратегия выкатки** и её настройки, **политика повторной выкатки** и опциональное
  **переопределение правила готовности** (при пустом значении берётся правило окружения).

### 2.7 Обработчики действий и права

- **Обработчики действий** (`Admin -> Action Handlers`) - привязывают событие выкатки (например, шаг
  успешно завершён) к действию (уведомить канал, перевести задачу в трекере). Каждый обработчик
  объявляет свои настройки.
- **Права** (`Admin -> Permissions`) - сопоставляют группы аутентификации с правами.

## 3. От задачи к выкатке

Оркестратор планирует и катит **по задачам**, а не одним глобальным релизом:

1. **Задача импортируется** из трекера, а её merge request'ы связываются с ней по правилу связи
   подключения (§2.1). Страница **Tasks** показывает задачи и есть ли у каждой построенный план.
2. **План на задачу** строится из порядка по умолчанию (§2.4): волны, в которых катятся репозитории
   этой задачи.
3. **Вы запускаете выкатку** задачи в окружение. Каждый шаг катит один репозиторий через его deploy
   target (§2.6), в порядке волн, и удерживается на **гейте готовности**, пока не выполнено правило
   готовности окружения.
4. **Страница Rollouts** показывает все выкатки, их статус и прогресс; откройте выкатку, чтобы следить
   за шагами или вмешаться. **Таймлайн** задачи фиксирует, что и когда произошло.

Повторный запуск той же задачи в то же окружение не приводит к двойной выкатке: идентичный план
распознаётся как та же самая выкатка.

## 5. Подключение CI/CD

- **Webhooks** - основная интеграция для подключений `gitlab-webhook`: направьте GitLab на ingress-эндпоинт
  оркестратора для этого провайдера. Poll-подключениям webhook не нужен.
- **REST API** на `/api` (интерактивная документация на `/swagger`) покрывает те же операции, что и
  админ-интерфейс.

## 6. Диагностика

### "Database connection failed"
- Убедитесь, что БД запущена: `docker-compose logs sqlserver`
- Проверьте `CONNECTION_STRING_DEFAULT` в `.env` и что пароль совпадает

### "RabbitMQ connection failed"
- Проверьте `docker-compose logs rabbitmq`; убедитесь, что учётные данные совпадают с `.env`

### "У меня нет прав"
- Задайте `AUTHORIZATION__BOOTSTRAPADMINOBJECTIDS` со своим OID, проверьте в логах строку про
  bootstrap-администратора и перезапустите

### "Задачи не связываются с merge request'ами"
- Убедитесь, что merge request попадает под **правило связи** подключения (§2.1) - источник (ветка,
  заголовок или метка) и шаблон. Быстрее всего проверить предпросмотром в форме подключения.
- Убедитесь, что задача есть в трекере и не закрыта
- Дайте немного времени sync-консьюмеру

### "Merge request не выкатывается"
- Возможно, не выполнено **правило готовности** целевого окружения (§2.5), либо не настроены
  окружение / deploy target (§2.6). Закрытые merge request'ы исключаются намеренно.
