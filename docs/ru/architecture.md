# Release Orchestrator — Архитектура

> [English version ->](../en/architecture.md) - [← Вернуться к документации](../README.md)

---

## Обзор

Release Orchestrator превращает набор merge request'ов в упорядоченный план выкатки, разбитый на стадии. План строится из двух независимых источников:

- **Зависимости задач** из трекера (если TASK-2 зависит от TASK-1, то MR по TASK-1 катится раньше)
- **Зависимости стеков** между репозиториями (например, БД → Бэкенд → Фронтенд)

Система объединяет эти зависимости в **ориентированный граф**, разрешает конфликты отбросом рёбер и использует **топологическую сортировку Кана** для получения стадий деплоя. На каждой стадии находятся MR'ы, которые можно катить параллельно.

**Суть продукта:** это «вход + рёбра + топосортировка». Всё остальное — ручное редактирование, импорт/экспорт YAML, права доступа, архивация — обслуживает эти три компонента.

---

## Слои архитектуры

Система следует паттерну модульного монолита: один сервис со строгим разделением слоёв, позволяющим при необходимости выделить Release Planning в отдельный микросервис.

```
┌─────────────────────────────────────────┐
│  PWA (Blazor WebAssembly)               │  Фронтенд
├─────────────────────────────────────────┤
│  Web / Ingress.Webhooks                 │  HTTP-граница
├─────────────────────────────────────────┤
│  Application Layer                      │  Бизнес-логика
│  - VCS Service                          │
│  - Tracker Service                      │
│  - Release Planner                      │
│  - Authorization                        │
├─────────────────────────────────────────┤
│  Providers Layer                        │  Границы абстракции
│  - IVcsProviderAdapter                  │
│  - ITrackerProviderAdapter              │
├─────────────────────────────────────────┤
│  Infrastructure Layer                   │  Внешняя интеграция
│  - EF Core DbContext                    │
│  - Реализации провайдеров (GitLab,      │
│    Yandex Tracker)                      │
│  - RabbitMQ Consumers                   │
│  - Archive Service                      │
│  - Redis Cache                          │
├─────────────────────────────────────────┤
│  Core Domain Layer                      │  Entities (без I/O)
│  - TaskItem, MergeRequest, ReleasePlan  │
│  - ReleasePlanGraph (чистый алгоритм)   │
└─────────────────────────────────────────┘
```

### Ключевой принцип: направление зависимостей

Зависимости указывают **только внутрь**. Слой Core не имеет внешних зависимостей кроме C# standard library. Каждый внешний слой зависит только от слоёв внутри него:

- **Web** зависит от Application, Infrastructure, Core
- **Infrastructure** зависит от Application, Core
- **Application** зависит от Core
- **Core** не зависит ни от чего

Это позволяет выделить Release Planning в отдельный микросервис (через очередь сообщений) без переписывания архитектуры.

## Архитектура компонентов

### 1. Webhook Ingress (`Ingress.Webhooks`)

**Роль:** Приём событий от внешних систем и публикация нормализованных сообщений.

**Технология:** ASP.NET Core Minimal API, .NET 10

**Обязанности:**
- Приём вебхуков от GitLab, Yandex Tracker и других систем VCS/трекера
- Валидация сигнатуры каждого вебхука (токен-based)
- Нормализация специфичных для провайдера payload'ов в универсальные сообщения:
  ```csharp
  public record MrOpened(Guid MrId, string ExternalMrId, Guid RepositoryId, 
                         string SourceBranch, string TaskExternalId);
  public record TaskCreated(Guid TaskId, string ExternalId, string Title);
  public record TaskStatusChanged(string ExternalId, string NewStatus);
  ```
- Публикация сообщений в RabbitMQ
- Возврат `200 OK` сразу же (блокирование на бизнес-обработку исключено)

**Масштабирование:** Stateless, горизонтально масштабируется за reverse proxy.

**Важно:** Буферизация событий **не реализована**. Если RabbitMQ недоступен, вебхук возвращает 503 Service Unavailable с заголовком Retry-After. Это сигнализирует отправителям, что сбой временный и вебхук должен быть переотправлен, предотвращая постоянную потерю событий. Рекомендации см. в [Конфигурация](configuration.md).

### 2. Core Service

**Единый сервис** с модульной внутренней структурой: нет отдельных микросервисов для каждого провайдера или функции. Причины:

- **Транзакционная целостность:** Построение плана требует одновременного доступа к зависимостям задач, состояниям MR и конфигурации стеков. Распределённые запросы усложнили бы транзакционность.
- **Намеренная связанность:** Алгоритм графа чистый (без I/O), но чтение данных и сохранение плана — плотный цикл.
- **Гибкость на будущее:** Модуль Release Planning можно выделить в отдельный сервис, потребляющий сообщения из RabbitMQ, без изменения архитектуры.

#### 2.1 Application Layer

**VCS Service** (`Application/Vcs`): Оркестрирует управление репозиториями, MR'ами и подключениями VCS. Не привязана к конкретному провайдеру.

**Tracker Service** (`Application/Tracker`): Загружает определения и зависимости задач из трекера(ов). Запускает синхронизацию задач через очередь.

**Release Planner** (`Application/ReleasePlanning`):
- Читает текущие MR'ы, задачи и определения стеков
- Строит граф, используя `ReleasePlanGraph` (чистый алгоритм, без EF)
- Разрешает циклы отбросом рёбер (приоритет: Soft → Задачные → Hard)
- Запускает топологическую сортировку Кана для получения стадий
- Сохраняет план и лог конфликтов

**Authorization**: Права доступа на основе claims (не используются роли). Claims хранятся в таблице `PermissionClaims`, маппятся на группы AD/LDAP или отдельные переопределения для пользователя.

#### 2.2 Infrastructure Layer

**Persistence** (`Infrastructure/Persistence`):
- `AppDbContext`: Оперативные данные (текущие MR'ы, задачи, планы, подключения)
- `ArchiveDbContext`: Исторические данные (закрытые задачи/MR'ы, планы старше 90 дней)
- EF Core с Microsoft SQL Server, повторные попытки при транзиентных ошибках включены
- Миграции в отдельной сборке `ReleaseOrchestrator.Migrations.MsSql`

**Providers** (`Infrastructure/Providers`):
- `VcsProviderFactory`: Разрешает тип подключения в экземпляр адаптера (keyed DI)
- `TrackerProviderFactory`: Аналогичный паттерн для трекеров
- Провайдеры регистрируются на этапе компиляции (нет plug-in discovery)

**Queue** (`Infrastructure/Queue`):
- MassTransit как абстракция очереди
- Consumers для: MR opened/status changed, task created/status changed, task sync, plan recalculation
- Коалесинг: дублирующиеся запросы на пересчёт дедублируются перед `SaveChangesAsync`

**Archive Service** (`Infrastructure/Archive`):
- Запускается как hosted service (фоновый рабочий в каждом поде)
- Архивирует задачи/MR'ы, закрытые >90 дней назад, в архивную БД
- Гейтится распределённой арендой на Redis (не консенсус, не leader election)
- Порядок фаз: старые планы → старые MR'ы → старые задачи (FK-безопасность)

### 3. Алгоритм графа Release Plan

**Файл:** `Application/ReleasePlanning/ReleasePlanGraph.cs`

**Принцип:** Чистый алгоритм, без EF Core, без I/O. 100% тестируемо.

**Входные данные:**
- Merge request'ы со статусом (Opened, ReadyForDeploy и т.д.)
- Задачи со статусом закрытости
- Зависимости задач (DependentTaskId → DependsOnTaskId)
- Зависимости стеков (FromStackId → ToStackId, тип Hard или Soft)

**Алгоритм:**

1. **Построение рёбер:**
   - Для каждого MR со статусом ReadyForDeploy:
     - Если MR связан с задачей:
       - Добавить исходящие рёбра ко всем MR'ам задач-предшественников (зависимости задач)
   - Для каждого MR:
     - Добавить исходящие рёбра к MR'ам в зависимых стеках (зависимости стеков)

2. **Обнаружение и разрешение циклов:**
   - Вычислить компоненты сильной связности (SCC)
   - Для каждого SCC с >1 узлом:
     - Отбросить рёбра по приоритету: сначала Soft, потом задачные, потом hard stack-рёбра
     - Повторять до ацикличности
     - Логировать отброшенные рёбра в `ReleasePlan.ConflictsJson`

3. **Топологическая сортировка (алгоритм Кана):**
   - Для ацикличного графа вычислить in-degree каждого MR
   - Повторно извлекать узлы с in-degree 0 → стадия N
   - Уменьшить in-degree потомков
   - Продолжить до тех пор, пока все узлы не будут распределены

4. **Вывод:**
   - `ReleaseStage[]` упорядочены по sequence
   - Каждая стадия содержит `StageItem[]` (MR'ы, которые можно катить параллельно)

**Ключевые исправления (из аудита):**
- Маппинг зависимостей задач был инвертирован (исправлено через навигацию EF)
- Несколько MR'ов на задачу обрабатывались неправильно (теперь все упорядочены)
- Soft-зависимости игнорировались (теперь применяются с низким приоритетом конфликта)
- Циклы и все достижимые из них узлы молча группировались (теперь логируются в конфликты)

## Модель данных

### Оперативная БД (AppDbContext)

**VCS-подключения:**
- `VcsConnection`: id, name (уникальное, используется в YAML), type (GitLab, ...), URL, зашифрованный токен, ReadyForDeployLabel

**Трекер-подключения:**
- `TrackerConnection`: id, name, type (YandexTracker, ...), URL, зашифрованный токен, org ID

**Репозитории и задачи:**
- `Repository`: id, name, external ID (путь в VCS), connection ID
- `TaskItem`: id, external ID (например, "TASK-123"), title, status, closed at, tracker connection
- `TaskDependency`: зависимая задача → задача-предшественник

**Merge Request'ы:**
- `MergeRequest`: id, external ID (iid в VCS), source/target branches, repo, status (Opened, ReadyForDeploy, Merged, Closed), timestamps создания/слияния/закрытия
- Статус может быть установлен вручную через API (помечено `IsStatusManual`) — вебхуки не перезатирают ручной статус
- Связана с задачей через external key, распарсенный из имени ветки

**Release Plans:**
- `ReleasePlan`: id, name, version, is active, auto-generated flag, YAML hash, conflicts JSON
- Фильтрованный уникальный индекс на `(IsActive=true)` гарантирует только один активный план
- Атомарный swap через транзакцию: пересчёт деактивирует старые автоплны, новый становится активным

**Стеки и зависимости:**
- `Stack`: id, name (уникальное)
- `RepositoryStack`: многие-ко-многим (репозиторий в каких стеках)
- `StackDependency`: из стека → в стек, тип Hard (должна катиться раньше) или Soft (предпочтительный порядок)

**Стадии и элементы:**
- `ReleaseStage`: id, plan, sequence (порядок в плане), name (nullable), is manual override
- `StageItem`: id, stage, merge request, manual inclusion flag

**Архивная таблица:**
- `ArchivedReleasePlan`: Снимок плана после построения стадий (для audit trail)

### Архивная БД (ArchiveDbContext)

Аналогична оперативной БД, но:
- Содержит только данные, закрытые >90 дней назад
- Пишется отдельно (нет общей транзакции)
- Вставка идемпотентна (проверка, уже ли существует)

## Поток событий: вебхук до плана деплоя

```
1. VCS/Трекер отправляет вебхук
   ↓
2. Ingress.Webhooks получает, валидирует токен
   ↓
3. Публикует нормализованное сообщение в RabbitMQ
   ↓
4. Consumer получает сообщение
   ↓
5. Обновляет БД (статус MR, задача, зависимости задач)
   ↓
6. Публикует "ReleasePlanRecalculationRequested" если нужно
   ↓
7. ReleasePlanRecalculationConsumer:
   - Читает текущие MR'ы, задачи, стеки
   - Вызывает ReleasePlanGraph.BuildAsync()
   - Сохраняет новый план, деактивирует старый автоплан
   - Логирует конфликты при отбросе рёбер
   ↓
8. PWA загружает новый план через BFF API
   ↓
9. UI отображает стадии
```

**Коалесинг:** Если несколько запросов на пересчёт приходят подряд, consumer дедублирует их—запускается только один пересчёт, экономя дорогие запросы.

## Архитектура провайдеров

Провайдеры регистрируются на **этапе компиляции**, не runtime. Каждый провайдер реализует два интерфейса:

### IVcsProviderAdapter

```csharp
public interface IVcsProviderAdapter
{
    Task<IVcsProvider> ConnectAsync(VcsProviderContext context, CancellationToken ct);
}
```

Возвращает `IVcsProvider` после:
- Валидации endpoint'а + credentials
- Обнаружения версии сервера (если self-hosted)
- Инициализации необходимого состояния для последующих вызовов

Это разделение предотвращает состояние "не инициализирован" в самом провайдере.

### ITrackerProviderAdapter

```csharp
public interface ITrackerProviderAdapter
{
    Task<ITrackerProvider> ConnectAsync(TrackerProviderContext context, CancellationToken ct);
}
```

Аналогичный паттерн для трекеров задач.

**Регистрация провайдера:**
1. Создать проект: `ReleaseOrchestrator.Providers.NewVcs` или `ReleaseOrchestrator.Providers.NewTracker`
2. Реализовать интерфейс адаптера
3. Добавить в `InfrastructureExtensions.cs`: `services.AddNewVcsProvider();` (одна строка на провайдер)

Детальное пошаговое руководство см. в [Провайдеры](providers.md).

## Наблюдаемость

### Health-эндпоинты

- **`GET /health`:** Liveness (процесс работает). Всегда 200, если доступен.
- **`GET /health/ready`:** Readiness (зависимости инициализированы). 503, если БД, RabbitMQ или Redis недоступны.

### Логирование

- Структурированное логирование в консоль (JSON-формат в production)
- Опциональная интеграция с Seq (не включена по умолчанию)

### Метрики и трассировка

**OpenTelemetry-поддержка:** Framework-слой в месте; Prometheus-экспортёра нет. Требует установки `OTEL_EXPORTER_OTLP_ENDPOINT` и коллектора для приёма трассировок.

**Известное ограничение:** Асинхронный путь (Ingress → RabbitMQ → Core) имеет плохую видимость без OTLP. Рекомендация: используйте polling `/health/ready` + RabbitMQ admin UI + audit БД.

## Архитектура безопасности

Все credentials **зашифрованы в покое** (at rest) используя **ASP.NET Core Data Protection**. Ключи хранятся в БД с приложение-специфичной изоляцией.

**Важно:** Без сертификата для шифрования самих ключей (`DataProtection__CertificatePath`), это обеспечивает **отсутствие реальной безопасности**. Дамп БД, backup или restore содержит как зашифрованные токены, *так и* незашифрованные ключи—злоумышленники могут тривиально расшифровать токены. Это проверяется при запуске в non-Development окружении: приложение отказывается запускаться без сертификата или явного отказа. Development освобождается ради удобства; production deployments должны конфигурировать сертификат.

### Аутентификация

- OpenID Connect через внешний провайдер (AD, OIDC-совместимая система)
- User ID (`oid` claim) — уникальный идентификатор
- Email и другие claims — опциональны

### Авторизация

- На основе claims, не ролей
- Claims вроде `release.plan.approve`, `release.plan.view`, `config.edit` хранятся в `PermissionClaims`
- Маппятся на группы AD через `GroupPermissionMapping` или отдельные переопределения через `UserPermissionOverride`

**Bootstrap:** Свежая установка требует минимум одного админа. См. [Начало работы](getting-started.md).

### HTTPS

- Предполагается терминация на reverse proxy (Nginx, Traefik и т.д.)
- Используйте `ForwardedHeaders` middleware; конфигурируйте через `ASPNETCORE_FORWARDEDHEADERS_ENABLED`

## Топология деплоя

**Один под / процесс:**
```
PWA браузер → BFF API (Web) ←→ Core Logic (Application) ←→ AppDbContext ←→ SQL Server
                                                              ↓
                                                          ArchiveDbContext ↔ SQL Server (Архив)
          
          Ingress (отдельный под) → RabbitMQ ↔ Core (MassTransit consumer)
```

**Несколько реплик (Kubernetes, Docker Swarm и т.д.):**
```
             PWA браузер
                  ↓
         ┌─────┬─────┬─────┐
         ↓     ↓     ↓     ↓
      Web1  Web2  Web3  Web4  (за load balancer'ом)
         └─────┬─────┬─────┘
               ↓
         AppDbContext (shared)
               ↓
         SQL Server (BFF с информацией о лидере, все Web'ы)
               
   Ingress1 ───┐
   Ingress2 ───┼─→ RabbitMQ ←── Core1, Core2, Core3 (все Core'ы потребляют одну очередь)
   Ingress3 ───┘   (Competing consumers, MassTransit управляет)
               
         Archive service в каждом Core поде (гейтится Redis-арендой)
```

**Распределённая аренда (не консенсус):** Archive service работает в каждом поде, но гейтится распределённой арендой на Redis. Аренда использует `SET key owner NX PX ttl` с валидацией владельца и обновлением. В каждом цикле только один под может держать аренду и запускать архивацию. Это **не алгоритм консенсуса**: один Redis — единственная точка отказа, и при разделении сети две реплики могут ненадолго считать, что обе держат аренду. Однако это приемлемо для архивации, которая идемпотентна — двойной прогон один раз стоит столько же, сколько обычный случай (который раньше работал на каждой реплике). Для операций, где двойной прогон — ошибка корректности, нужны fencing-токены. Если Redis недоступен, аренда не берётся, прогон пропускается (fail-closed), предотвращая thundering herd на следующем цикле.
