> [English version ->](../en/architecture.md) - [← Вернуться к документации](../README.md)

## Обзор

Release Orchestrator планирует и выполняет выкатки **по задачам**. Единого глобального плана релиза и
"стеков" нет: для каждой задачи, импортированной из трекера, он строит порядок, в котором катятся
merge request'ы этой задачи, затем выполняет этот порядок как **выкатку (rollout)** в окружение.
**Гейт готовности** проверяется один раз, на запуске, и отклоняет запуск целиком, если хотя бы один
выкатываемый merge request не готов.

Порядок задают два входа:

- **Порядок репозиториев** - глобальные правила между репозиториями (`A` катится после `B`), каждое
  **жёсткое** (настоящее ограничение) или **мягкое** (предпочтение, уступающее первым при конфликте).
- **Иерархия задач** - связи родитель/предшественник из трекера.

Из них строится ориентированный ацикличный граф; циклы разрешаются отбрасыванием рёбер наименьшего
приоритета (сначала мягкие) и логируются, а топологическая сортировка даёт **волны** - merge
request'ы, которые можно катить параллельно.

### Порядок везде один, различается только способ

Осознанный инвариант, который стоит записать, потому что его легко нарушить по невнимательности:

| | Зависит от окружения |
|---|---|
| **В каком порядке катится** | **Нет.** Один порядок для всех. |
| **Как именно катится** - слияние, вызов шага пайплайна, что предлагает конкретная VCS | Да |
| **Можно ли катить вообще** - правило готовности | Да |

Поэтому в плане нет окружения: дерево и последовательность одинаковы для теста и для прода, а
окружение выбирается на запуске выкатки. По окружениям меняется цель выкатки для пары
`(репозиторий, окружение)` - её стратегия и настройки этой стратегии; именно там выражается "на
проде другой шаг пайплайна".

Практическое следствие: ключ `environment:` в правилах порядка - это ошибка проектирования, а не
недостающая возможность. Запрос, который выглядит как просьба о нём, обычно про способ, а не про
порядок.

## Слои архитектуры

Onion / ports-and-adapters. Зависимости направлены **только внутрь**.

```
Core                enum'ы, чистый разбор (извлечение ключа задачи, сигналы готовности); ноль зависимостей
  ← Application     порты, контракты сообщений, алгоритм планирования - без EF
      ← Infrastructure          EF-модели, DbContext, адаптеры (Rebus, Redis, DataProtection)
      ← Providers.Abstractions  порты провайдеров + нормализованные модели
          ← Providers.GitLab / Providers.YandexTracker
              ← Web (корень композиции, API) / Ingress.Webhooks
```

- **Ядро не знает ни об одном конкретном провайдере.** Имена вендоров, словари статусов и форматы
  ключей живут в адаптерах; домен видит только нормализованные значения.
- **EF-сущности не выходят из Infrastructure.** Планировщик принимает `PlanMergeRequest`, фабрики -
  `*ConnectionDescriptor`. Application и Providers.Abstractions EF-моделей не видят.
- **Алгоритм планирования (`Application/ReleasePlanning`) не зависит от EF** - он чистый и тестируется
  без БД.
- **Провайдеры регистрируются на этапе компиляции** (keyed DI + маркер-записи), без динамической
  загрузки сборок.
- **Миграции есть для обоих провайдеров** - `ReleaseOrchestrator.Migrations.MsSql` и
  `...Migrations.Postgres`, каждая с двумя контекстами (рабочий + архивный).
- **PWA - отдельный клиент.** Он общается с API по HTTP и ссылается только на внутренние
  zero-dependency сборки (Core, Providers.Abstractions), так что предпросмотр связи merge request↔задача
  использует тот же `TaskKeyExtractor`, что и приём.

## Приём: push и poll

События попадают в систему двумя путями, и оба испускают **одни и те же** нормализованные события,
чтобы push и poll не могли разойтись в трактовке "смержено" / "решено":

- **Push** - GitLab соединения `gitlab-webhook` шлёт доставки в `Ingress.Webhooks`. Хост владеет
  маршрутом, разрешает секрет соединения и кладёт события на шину; каждый провайдер владеет формой
  payload и аутентификацией за `IWebhookParser`.
- **Poll** - `VcsPollingCoordinator` обходит каждое соединение, чей тип провайдера зарегистрирован
  `IngestionMode.Poll`, с интервалом, заданным этим соединением (`VcsPollSettings`), и испускает те же
  события.

**Дедупликация** - доставка может прийти дважды (ретрай вебхука, перекрытие опроса). `EventDedupStep`
на inbox'е `ProcessedEvent` отбрасывает повторы; опрошенные события несут детерминированный id, так что
одно и то же состояние merge request'а сворачивается в одно событие.

Нормализованные контракты сообщений живут в `Application.Contracts.Messages` (`MrOpened` несёт ветку,
заголовок, метки и результат пайплайна; `TaskCreated`, `TaskStatusChanged`, `BranchesObserved`, ...);
в `Providers.Abstractions.Ingestion` лежит парсерная сторона шва (`IWebhookParser`, `WebhookRequest`,
помощники по подписям). **Правило связи**
соединения - привязку merge request'а к задаче - применяет консьюмер, а не парсер, потому что парсер
работает в ingress без БД.

## Планирование: по задачам

Для каждой задачи планировщик строит **план выкатки** (`RolloutPlan` с `PlanTaskNode` / `PlanItem`):

1. Собрать merge request'ы самой задачи и всех задач, от которых она транзитивно зависит (её замыкание).
2. Применить правила порядка репозиториев (`RepositoryDependency`, Hard/Soft) и иерархию задач.
3. Разрешить циклы, отбросив рёбра наименьшего приоритета, и записать, что отброшено.
4. Топологически отсортировать в **волны**.

План хранит **хэш содержимого по своему порядку**, так что эквивалентный пересчёт распознаётся как тот
же план, а не порождает новый. `PlanOverride` фиксирует осознанные ручные правки.

## Выполнение: выкатки

Запуск задачи в окружение создаёт `Rollout` с `RolloutStep` на каждый merge request, в порядке волн
(`RolloutStep`, `RolloutStepAttempt` для повторов, `RolloutEvent` для аудита):

- Каждый шаг катит один merge request через deploy target его репозитория - `RepositoryDeployTarget`
  на пару `(репозиторий, окружение)` со стратегией выкатки (`gitlab-merge`, `gitlab-pipeline`, ...),
  политикой повторной выкатки и замороженными на момент запуска настройками (секреты расшифровываются
  лишь при диспатче).
- **Гейт готовности** отрабатывает один раз, на запуске, и отклоняет запуск целиком, если хотя бы один
  выкатываемый merge request не готов - а не отфильтровывает неготовые: это была бы частичная выкатка,
  выглядящая как полная. Повторной проверки при диспатче нет: чтобы придержать уже идущую выкатку, её
  отменяют. Готовность - это набор нормализованных **сигналов** (`label:...`, `mr-status:...`,
  `pipeline:...`), проверяемых по именованному `ReadinessRule` (`AllOf` / `AnyOf`). Правило разрешается
  так: пин на merge request (`MergeRequestReadinessPin`) -> переопределение deploy target'а -> правило
  по умолчанию окружения (`DeploymentEnvironment.ReadinessRuleId`) -> без гейта.
- **Незавершённая работа блокирует запуск.** Ветка, называющая задачу из плана, которую не несёт ни
  один merge request, - это начатая и не приземлённая работа, поэтому запуск отклоняется, пока её не
  оформят в MR, не вольют или не удалят (`RepositoryBranch`).
- Состояние выкаченности отслеживается по окружениям (`MrDeploymentState`, `MrDeployClaim`): один и тот
  же merge request может быть выкачен на staging и не выкачен на prod. Повторный запуск идентичного
  плана распознаётся как та же выкатка, поэтому двойной выкатки не происходит.

## Сообщения

Rebus поверх RabbitMQ, маршрутизация по типу. Консьюмеры обрабатывают открытие/смену статуса MR,
создание/смену статуса задачи, синхронизацию задач и прогресс выкатки. Ядра - конкурирующие консьюмеры
одной очереди; inbox `ProcessedEvent` делает повторную доставку безопасной.

## Модель данных (рабочая БД, `AppDbContext`)

- **Соединения** - `VcsConnection`, `TrackerConnection`: имя, тип, URL, зашифрованный токен и
  непрозрачный мешок `ProviderSettingsJson` (правило связи / интервал опроса / org id / closed
  statuses). Колонки "ready-for-deploy label" нет.
- **Ветки** - `RepositoryBranch` (имя, `TaskExternalId`, признаки merged/default) - свидетельство того,
  что работа по задаче начата, даже если её не несёт ни один merge request.
- **Репозитории и порядок** - `Repository` (имя, внешний путь, соединение); `RepositoryDependency`
  (from -> after, Hard/Soft); `RepositoryDeployTarget` на пару `(репозиторий, окружение)` со стратегией,
  `DeploySettingsJson`, политикой повторной выкатки, опциональным `ReadinessRuleId`.
- **Задачи** - `TaskItem` (внешний id, заголовок, статус, closed-at); `TaskDependency`
  (родитель/предшественник).
- **Merge request'ы** - `MergeRequest` (внешний id, ветки, репозиторий, `Status`, `Labels`,
  `PipelineResult`, `IsStatusManual`); журналы `MergeRequestStatusChange`, `MergeRequestLabelChange`;
  `MergeRequestReadinessPin` для ручного переопределения гейта на конкретный MR.
- **Готовность и окружения** - `ReadinessRule` (уникальное имя, режим, требуемые сигналы);
  `DeploymentEnvironment` (ключ, порядок, включённость, `ReadinessRuleId`).
- **Планы** - `RolloutPlan`, `PlanTaskNode`, `PlanItem`, `PlanOverride`.
- **Выкатки** - `Rollout`, `RolloutStep`, `RolloutStepAttempt`, `RolloutEvent`; состояние выкаченности
  `MrDeploymentState`, `MrDeployClaim`.
- **Действия и права** - `ActionBinding`; `PermissionClaim`, `GroupPermissionMapping`,
  `UserPermissionOverride`.
- **Приём** - `ProcessedEvent` (inbox дедупликации).

**Архивная БД** (`ArchiveDbContext`) хранит давно закрытые задачи/выкатки; запись идемпотентная, без
общей транзакции, фоновым архиватором под Redis-лизом.

Расхождения SQL Server и PostgreSQL изолированы в `ProviderSpecificMapping` (токен конкурентности,
диалект фильтрованного индекса); даты хранятся только с `Kind=Utc`.

## Поток событий

```
1. GitLab шлёт webhook  ─или─  поллер обходит poll-соединение
2. Порождается нормализованное событие (парсер в ingress или координатор)
3. EventDedupStep отбрасывает повторы (inbox ProcessedEvent)
4. Консьюмер обновляет БД (статус/метки/пайплайн MR, задача, зависимости),
   применяя правило связи соединения для привязки MR к задаче
5. План выкатки задачи (пере)страивается, если изменились его входы (сравнение по хэшу)
6. Оператор запускает выкатку задачи в окружение
7. Каждый шаг катит свой репозиторий в порядке волн, удерживаясь на гейте готовности
8. PWA читает задачи, планы и выкатки через API
```

## Безопасность

Учётные данные **шифруются при хранении** через ASP.NET Core Data Protection. Без сертификата для
защиты key ring (`DataProtection__CertificatePath`) дамп БД содержит и зашифрованные токены, и ключи -
поэтому вне Development приложение отказывается стартовать без сертификата (или явного отказа от него).

- **Аутентификация** - OpenID Connect через внешнего провайдера (идентичность - claim `oid`) или
  встроенный провайдер `Local` в разработке.
- **Авторизация** - на правах (claims), не на ролях (`release.plan.approve`, `config.edit`, ...),
  сопоставляемых с группами через `GroupPermissionMapping` или на пользователя через
  `UserPermissionOverride`; вычисленные права кэшируются в Redis.
- **HTTPS** предполагается терминированным на реверс-прокси; используйте `ForwardedHeaders`.
- **Аудит запросов** фиксирует каждый запрос к API (recorder-middleware) для экрана аудита в админке.

## Наблюдаемость

- **Health** - `GET /health` (liveness) и `GET /health/ready`, который проверяет рабочую БД, архивную
  БД (Degraded, а не Unhealthy - архивация фоновая) и координационный кэш. Брокер намеренно не
  проверяется: при его недоступности ingress отвечает 503, который отправители ретраят, поэтому
  простой брокера - не повод выводить API из ротации.
- **Логирование** - структурное (Serilog), с correlation id, протянутым через запросы и консьюмеры.
  Логи не локализуются - они для операторов.
- **Метрики и трассировка** - эндпоинт метрик Prometheus и OpenTelemetry подключены; асинхронный путь
  (ingress -> RabbitMQ -> ядро) трассируется при настроенном OTLP-коллекторе.

## Топология развёртывания

Модульный монолит: API-хост (`Web`, отдаёт PWA и API) и ingress-хост (`Ingress.Webhooks`) могут
работать как отдельные процессы над общей БД и RabbitMQ. Несколько реплик - конкурирующие консьюмеры
одной очереди. Фоновый архиватор работает в каждом core-поде, но под Redis-лизом (`SET NX PX` с
проверкой владельца) - это не консенсус, но приемлемо, потому что архивация идемпотентна; при
недоступности Redis проход пропускается (fail-closed).
