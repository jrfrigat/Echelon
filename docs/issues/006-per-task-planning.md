# 006 — Планирование под задачу

Статус: **реализовано**, 2026-08-07. Документ остаётся справочником по инварианту и по схеме
документа плана — не планом работ.

## 1. Инвариант: одна деривация на все входы

**Импорт, ручная правка, пересчёт и запуск обязаны выводить порядок одним и тем же кодом.**

Держится не соглашением, а устройством: единственное место, где считается порядок, — это
`RolloutPlanner.ComputeAsync` → `ReleasePlanGraph.Build`. Всё остальное читает **сохранённый
результат**.

| Вход | Как приходит к порядку |
|---|---|
| Пересчёт | `ComputeAsync` → пишет волны в `PlanItem.Wave` |
| Ручная правка | дельты `PlanOverride` → тот же `ComputeAsync` на следующей сборке |
| Импорт YAML | волны → те же дельты → тот же `ComputeAsync` |
| Запуск | читает `PlanItem.Wave` сохранённого плана |
| Экран, экспорт | читают тот же сохранённый план |

Проверяется тестом `PlanImportTests.ImportSurvivesRecalculation`: импорт разворачивает выведенный
порядок, пересчёт (то, что делает каждое событие приёма) обязан его сохранить.

Три места, где это было нарушено, и все три чинились по одной причине:

- **запуск строил порядок сам** — `ReleasePlanGraph.Build` по навигациям EF, без политики ожидания,
  без правок оператора и без документа правил. То есть выкатывался порядок, которого оператор не
  видел;
- **экран и экспорт пересчитывали при чтении** — метаданные версии X с содержимым, которого в
  версии X не было (это было 011 §3.2);
- **`ViolatedBy` не вызывался ниоткуда** — снятие обязательного ребра давало молчаливый план: цикла
  нет, разрывать нечего, список конфликтов пуст. Теперь вызывается внутри `Build`, поэтому проверка
  распространяется на любого будущего вызывающего.

## 2. Схема документа плана

Экспорт и импорт — одна схема (`GET/POST /api/tasks/{id}/plan/export|validate|import`).

```yaml
version: 1
target_task: PROJ-1
plan_version: 7            # только вывод, при импорте игнорируется
nodes:
  - task: PROJ-1
    depends_on: [PROJ-2]   # только вывод: граф ожидания принадлежит атласу
    merge_requests:
      - mr: gitlab:group/api!42
        wave: 2
conflicts: [...]           # только вывод
```

**Документ заявляет ровно одно: в какой волне что выкатывается.** Всё остальное сверяется на
совпадение и никогда не применяется. Состав плана — из атласа, поэтому документ, который его меняет,
отвергается: план это проекция, и импорт, умеющий добавить в него работу, сделал бы его чем-то
другим.

Ключ MR — `подключение:путь/репозитория!id`. Словарь GitLab, но это ключ, а не диалект в домене:
именно он позволяет прочитать экспорт глазами и найти по нему настоящие merge request'ы.

Правила, за нарушение которых документ отвергается: неизвестный ключ, волна меньше 1, разрыв в
нумерации волн (пустая волна — это план, который не совпадает с запрошенным), MR или задача,
названные дважды, состав, не совпадающий с планом в обе стороны.

`force` пропускает **отказ**, но не **запись**: план всё равно сообщает каждое нарушенное
обязательное ограничение через `ConflictsJson`. План может выкатываться против объявленного порядка;
выглядеть при этом чистым — не может.

## 3. Как импорт превращается в дельты

`PlanWavePinning.Compute` — чистый, тестируется без БД:

1. **снять** каждое выведенное ребро, концы которого идут не по возрастанию волн;
2. **добавить** одно ребро из предыдущей волны к тому, у кого не осталось предшественника ровно там.

Волны — послойная разметка по длиннейшему пути, поэтому первое не даёт уехать позже, а второе —
раньше. Результат послойный, значит ациклический: импорт не порождает конфликтов сам, только те,
которые автор выбрал нарушить.

Минимально намеренно: закрепить, добавив все пары между соседними волнами, тоже верно и оставляет
задаче квадратичную кучу дельт, которую никто не прочитает — а они хранятся, значит их читают.

## 4. Что решено не делать

- **`PlanItem.IntraTaskOrder` и `PlanOverrideKind.SetIntraTaskOrder` удалены** (номер 5 не
  переиспользуется). Это был не забытый код, а вытесненный замысел: строки `PlanItem` пересоздаются
  на каждом пересчёте, а пересчёт идёт на каждом событии приёма, — авторский порядок терялся бы при
  первом вебхуке. Порядок внутри задачи — обычное ребро, живёт в `PlanOverride` на задаче.

  На то же место встала `PlanItem.Wave` — и это ровно противоположный случай: **вычисленное**
  значение, которое переписывается вместе со строками, которые описывает.

- **`PlanOverrideKind.IncludeMr` / `ExcludeMr` и `PlanItem.ManualInclusion` оставлены и не
  реализованы.** Спроектированная, но не построенная возможность: заставить план включить или
  исключить конкретный MR. Ничто их не читает и не пишет. Оставлены сознательно — в отличие от
  `IntraTaskOrder` замысел не вытеснен, он просто не сделан; но пока он не сделан, выставление
  `ManualInclusion` в БД руками не даст ничего.
