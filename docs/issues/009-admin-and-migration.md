# 009. Админка и план миграции

> Черновик от 2026-07-18. Проектный документ, не отчет о сделанном.

## 1. Зачем этот документ

Два вопроса, которые нельзя развести. Первый -- "я не понимаю, для чего приложение": сегодня домашняя страница PWA это один глобальный план выкатки всех готовых MR (маршрут "/"), а в админке нет ни списка задач, ни плана под задачу, ни экрана выкатки. Продукт визуально утверждает, что он про глобальный список стадий, тогда как целевая модель ([004](004-target-architecture.md)) -- про выкатку отдельной задачи. Второй вопрос -- как дойти из текущего кода до целевого, ни разу не сломав `main`. Здесь предлагается переякорить IA на Tasks/Rollouts и провести аддитивную миграцию P0-P5, где каждая фаза собирается, зелена и проверена на живой БД.

Ни одна строчка ниже не описывает сделанное. Это цель. Две посылки цели опираются на непроверенные внешние факты и помечены как таковые в разделе 4 (P0): `TaskDependency` должен быть реально заполнен на боевых конфигурациях, а НАПРАВЛЕНИЕ ребра зависимости в Яндекс.Трекере в коде помечено UNVERIFIED -- неверное направление инвертирует каждое дерево.

## 2. IA переякорена на Tasks и Rollouts

Диагноз из [002](002-provider-independence.md) s.2.4 (хардкод в выпадающих списках) и известный пробел PWA сходятся к одному: интерфейс построен вокруг не того объекта. Глобальный план демотируется из центрального объекта продукта во внутреннюю read-модель -- "атлас" всех рёбер зависимостей ([004](004-target-architecture.md)), из которого нарезается каждый план под задачу. Наружу выходят Tasks и Rollouts.

Все новые страницы переиспользуют `PageBase`/`CrudPageBase` (воронка ошибок `RunAsync`, `ApiException` с локализованным сообщением сервера, `ConfirmAsync`), зеркалируют DTO приложения в `Pwa/Models/ApiModels.cs` (граница onion сохраняется) и НЕ хардкодят ни одного значения провайдера.

Навигация:

| Раздел | Маршрут | Назначение |
|---|---|---|
| Tasks | `/` (новый лендинг) | список задач, заменяет глобальный план как дом |
| Task detail | `/tasks/{key}` | дерево плана, готовность, запуск, YAML |
| Rollouts | `/rollouts` | история всех выкаток |
| Rollout progress | `/rollouts/{id}` | живой прогресс отдельной выкатки |
| Administration | `/admin/*` | соединения, репозитории, порядок репозиториев, окружения, стратегии выкатки, обработчики действий, прием, права |

### 2.1. Список задач (лендинг)

`/`, замена глобального плана как дома. Постранично, фильтр по трекеру / статусу / готовности. Колонки: ключ, заголовок, трекер, статус (собственный ключ трекера), бейдж ГОТОВНОСТИ, число открытых MR, статус последней выкатки. Источник -- `GET /api/tasks`. Это первое, что видит оператор: не абстрактный граф всех стадий, а список того, что он может выкатить.

### 2.2. Деталь задачи

`/tasks/{key}`, вкладки:

- **План (дерево).** Дерево зависимостей с корнем в целевой задаче: задачи-предпосылки как раскрываемые дети через `TaskDependency`, MR как листья с `MergeRequestStatus` + `DeploymentState` + чипом волны. Дерево -- это ГРУППИРОВКА для показа, а не порядок исполнения: волны живут на уровне MR (`RolloutStep.Wave`), потому что MR одной задачи законно попадают в разные волны ([006](006-per-task-planning.md), [004](004-target-architecture.md)). Правки (включить/исключить MR, переопределить стратегию выкатки на MR, добавить/убрать ручное ребро, задать внутризадачный порядок MR, Recalculate) пишутся дельтами `PlanOverride` и переживают пересчет. Баннер конфликтов постоянен: `ViolatedBy` пересчитывает нарушения и показывает их -- план может нарушить связь, но никогда молча (docs/001 s.2.6). Переиспользуется существующая drag-drop механика, перепривязанная к дереву.
- **Готовность.** Отчет с блокирующими задачами, каждая ссылается на свою деталь. Готовность считается ПО ОКРУЖЕНИЮ: селектор окружения на детали задачи (и в списке) выбирает, для какого окружения показывать бейдж. Две истины: `MergeRequestStatus` -- истина ПРИЕМА, `DeploymentState` -- истина ОРКЕСТРАТОРА, и последняя теперь ведётся по паре (MR, окружение) через `MrDeploymentState` ([007](007-execution-engine.md)). Задача Deployed в окружении E (производно, без дублирующего флага), когда все её выкатываемые MR в Deployed/Skipped для E; цель (T, E) готова, когда каждая задача замыкания T (кроме самой цели) Deployed в E, ПЛЮС опциональный вентиль прогрессии окружений: выкатка (T, E) может требовать, чтобы T уже была Deployed в окружения, стоящие в порядке перед E (по умолчанию включён -- prod требует staging). Вентиль -- конфиг, редактируемый.
- **Запуск.** Пикер целевого окружения (из настроенного упорядоченного списка) плюс кнопка, неактивная, пока задача не Ready в выбранном окружении И у вызывающего нет права `release.execute` (новое в этом дизайне). Модалка подтверждения показывает выбранное окружение, упорядоченные волны и какие шаги будут Skipped. Выкатка нацелена ровно на одну пару (задача, окружение) ([007](007-execution-engine.md)).
- **YAML.** Экспорт/импорт/валидация под конкретную задачу ([006](006-per-task-planning.md)).

### 2.3. Прогресс выкатки (живой)

`/rollouts/{id}`: целевое окружение выкатки в шапке, волна-за-волной таймлайн шагов, чипы состояния, ссылки `ExternalRef` на pipeline/merge, per-step retry/skip, отмена выкатки. Живо -- через SignalR с polling fallback (см. 3.2). Оркестратор не держит состояния в памяти ([007](007-execution-engine.md)), поэтому UI читает ровно то, что в строках БД -- при потере соединения polling даёт ту же картину, что и push.

### 2.4. История

Вкладка на детали задачи плюс `/rollouts`: прошлые прогоны, кто запустил, в какое окружение, исход, длительность. Живёт на `Rollout`/`RolloutStep` + append-only логах ([007](007-execution-engine.md)).

### 2.5. Админ-разделы

| Раздел | Что добавляется |

| Repositories | пикер `DeployStrategyKey` (список с сервера + настройки по схеме) и привязка трекера |

Это КОНФИГ-данные -- правила построения плана, а не пятая ось расширения ([005](005-extension-model.md)) |

## 3. Новые DTO, бейджи, живой прогресс, обнаружение

### 3.1. DTO в ApiModels

Каждый новый серверный DTO зеркалируется в `Pwa/Models/ApiModels.cs` -- граница onion не размывается, PWA не видит EF-сущностей. Иллюстративная форма (предлагаемая, не скопированный код):

```csharp
// предлагаемые записи ApiModels, зеркало серверных DTO
public sealed record TaskListItem(
    string Key, string Title, string Tracker,
    string Status, ReadinessBadge Readiness,
    int OpenMergeRequests, string? LastRolloutStatus);

public enum ReadinessBadge { Ready, Blocked, Deploying, Deployed, Failed }

public sealed record RolloutStepView(
    Guid StepId, string MergeRequest, string Task,
    int Wave, string State, string? ExternalRef, string? LastError);
```

Бейдж `Readiness` в `TaskListItem` запрашивается ДЛЯ ВЫБРАННОГО ОКРУЖЕНИЯ (параметр запроса), а `RolloutStepView` наследует окружение своей выкатки. Окружение -- ортогональное измерение: оно не усложняет чистый граф, а лишь скоупит и гейтит его сверху ([006](006-per-task-planning.md), [007](007-execution-engine.md)).

### 3.2. Бейджи готовности и живой прогресс

Бейдж готовности считается ДЛЯ ВЫБРАННОГО ОКРУЖЕНИЯ и выводится из двух истин, а не из отдельного хранимого флага: сервер отдаёт `Blocked-by-N`, `Ready`, `Deploying`, `Deployed`, `Failed`, вычисляя их из `MrDeploymentState` (истина по паре (MR, окружение)) по замыканию, плюс опциональный вентиль прогрессии окружений. Для скорости списка есть проекция read-модели `TaskDeploymentStatus { TaskId, EnvironmentId, ... }`, но она явно пересобираема из `MrDeploymentState` -- она не может стать расходящимся источником истины ([004](004-target-architecture.md)).

Живой прогресс -- SignalR-хаб, транслирующий `StepSettled`/`TaskReadinessChanged` ([008](008-ingestion-and-messaging.md)), с ОБЯЗАТЕЛЬНЫМ polling fallback: если WebSocket недоступен (прокси, корпоративная сеть), страница опрашивает `GET /api/rollouts/{id}` с интервалом. Обе ветки читают одни и те же строки, потому что оркестратор бесстатусный ([007](007-execution-engine.md)) -- push и poll не могут разойтись в том, что показать.

### 3.3. Выпадающие списки от эндпоинтов обнаружения

Конец хардкоду `["GitLab"]` / `["YandexTracker"]` / `["Hard","Soft"]` (диагноз -- [002](002-provider-independence.md) s.2.4). Каждая ось расширения ([005](005-extension-model.md)) отдаёт свой список валидных ключей эндпоинтом обнаружения, из фабричного `Available`-списка, а форма настроек строится по `ProviderSettingSchema`:

```csharp
GET /api/discovery/vcs-providers        -> [{ key, displayName, settingSchema[] }]
GET /api/discovery/tracker-providers    -> [...]
GET /api/discovery/deploy-strategies    -> [...]
GET /api/discovery/action-types         -> [...]
GET /api/discovery/dependency-kinds     -> [{ key: "Hard" }, { key: "Soft" }]
```

Добавили провайдера/стратегию/обработчик -> новый ключ появляется в списке сам, без правки PWA. Неизвестный ключ на записи отвергается на этапе API (семантика `UnknownProviderException` с перечислением валидных), а не в рантайме выкатки.

## 4. Локализация

Все новые строки -- в `Resources/UiStrings.resx` (нейтральная культура = en) и `UiStrings.ru.resx`, ключ-в-ключ. Инфраструктура уже есть: `LanguageService`, `LocalizedComponent`, `LanguageSwitcher`, `AcceptLanguageHandler` (серверные ошибки возвращаются локализованными через `ApiException`). Добавляемое сверх этого -- две вещи:

1. **Тест паритета ключей.** Проверяет, что множества ключей en и ru совпадают. Забытый перевод -- это не пустая строка в рантайме, а красный тест. Без него локализация деградирует молча -- ровно тот класс отказа, который проект не терпит.
2. **Починка LocalLogin.** `LocalLogin.razor` -- единственная страница с захардкоженными английскими строками. Её строки уезжают в `UiStrings`, дыра закрывается.

Операторские ЛОГИ не локализуются: они для одного читателя-оператора и должны быть на одном языке (правило CLAUDE.md, повторено в [004](004-target-architecture.md)).

## 5. Фазы P0-P5

Каждая фаза аддитивна, самодостаточна и оставляет `main` собираемым и зелёным. Новые таблицы встают РЯДОМ со старыми, а не мутируют их: инвариант единственного активного плана не переворачивается, пока обе ветки живы. Миграции -- всегда обе, MsSql и Postgres.

### P0. Чистый алгоритм и проверка -- сначала

**Цель.** Доказать ядро планирования под задачу на EF-свободном движке ДО любой правки персистентности, свернуть в него порядок репозиториев вместо стеков и подтвердить, что атлас реален.

**Работы.**
- Расширить `ReleasePlanGraph.Build` аддитивно оверлеем ручных рёбер: новые опциональные параметры (`addEdges`, `removeEdges`) с пустым значением по умолчанию -- 17 существующих тестов проходят без изменений.
- Убрать стеки из ЧИСТОЙ модели графа: `PlanMergeRequest` больше не несёт `Stacks`, а несёт свой `RepositoryId`; `BuildEdges` выводит ребро порядка репозиториев `FromMr -> ToMr`, когда репозитории двух MR связаны настроенной `RepositoryDependency` (с учётом Hard/Soft). В `PlanEdgeKind` `StackHard`/`StackSoft` становятся `RepoHard`/`RepoSoft` с тем же приоритетом сброса (`RepoHard` критичнее всего, затем `TaskDependency`, `RepoSoft` сбрасывается первым) ([006](006-per-task-planning.md)).
- Добавить `PlanClosureBuilder` (чистый), вырезающий транзитивное замыкание `TaskDependency` целевой задачи.
- Добавить `BuildForTask(targetTaskId, closureMrs, overrides)`, переиспользуя `BuildEdges`/`BreakCycles`/`TopoSort`/`MandatoryEdges`/`ViolatedBy`; порядок репозиториев применяется И внутри задачи (её MR по разным репо теперь упорядочиваются политикой репо -- правило "MR одной задачи не упорядочивают друг друга" ослаблено до "не упорядочивают, КРОМЕ как политикой репозиториев"; task-зависимостью они по-прежнему не связаны), И между задачами замыкания. Юнит-тесты извлечения подграфа, порядка репозиториев и применения оверрайдов -- ноль БД.
- End-to-end проверить, что `TaskDependency` реально заполнен (аудит это флагнул, роадмап говорит "исправлено"), и ПОДТВЕРДИТЬ направление ребра зависимости Яндекс.Трекера против живого API.

**Риск.** Если направление ребра трекера неверно или `TaskDependency` пуст на боевых конфигурациях -- всё дерево под задачу бессмысленно. Это должно быть закрыто ДО P2. Оба факта сейчас непроверены: их проверка -- смысл P0, а не побочный эффект.

### P1. Шов приема и дедуп (без смены поведения)

**Цель.** Сделать push и pull симметричными за одним конвейером нормализованных событий с границей дедупа.

**Работы.**
- Добавить `IHasEventIdentity` пяти записям приема (`MrOpened`, `MrStatusChanged`, `TaskCreated`, `TaskStatusChanged`, `TaskSyncRequested`); добавить inbox `ProcessedEvent` + шаг дедупа во входящем pipeline Rebus.
- Ввести `IWebhookTranslator`, вынести диалект GitLab/Yandex из Ingress (эндпоинты роутятся по `connection.ProviderType`; хост всё ещё ProjectReferences провайдеры -- честная оговорка про отсутствие ALC, [005](005-extension-model.md)), сохранить constant-time секрет и семантику 503 + Retry-After.
- Обобщить `TaskReconciliationService` в хост `Workers.Polling` + `IPollingSource`; добавить VCS-источник опроса MR (сворачивает осиротевший `VcsService.SyncMergeRequestAsync`); добавить per-connection `IngestionMode` + курсор.
- Свести дублированный построитель AMQP-строки в `Application/Contracts`.

**Риск.** Поллер обязан синтезировать детерминированные id, иначе дедуп молча ломается и повторный опрос переобрабатывает всё на каждом цикле; рост inbox требует политики хранения (TTL/архив).

### P2. План под задачу РЯДОМ с глобальным (аддитивно, без смены индекса)

**Цель.** Выпустить IA задач и планы под задачу, не сломав старый глобальный путь; заземлить порядок репозиториев и измерение окружения в схеме.

**Работы.**
- Добавить НОВЫЕ таблицы `RolloutPlan(TargetTaskId, собственный фильтрованный уникальный индекс)` + `PlanTaskNode` + `PlanItem` + `PlanOverride`; старый `ReleasePlan` и его индекс НЕ трогать.
- Заменить стеки конфигурируемым порядком репозиториев: УДАЛИТЬ сущности `Stack`/`StackDependency`/`RepositoryStack` и стек-ordering, добавить таблицу `RepositoryDependency(FromRepositoryId, ToRepositoryId, Type Hard|Soft; уникальный (From, To); Restrict на обе FK; запрет самопетли)`. Поскольку боевых данных нет ([001](001-current-state.md)) -- приложение НИ РАЗУ не работало на проде, миграции на боевую БД не накатывались -- это чистое удаление, а не coexistence-танец ради сохранности строк: деструктивная миграция в dev допустима и делается здесь, а не откладывается в фазу демонтажа. Админ-страница Repository Ordering + правила в YAML/config.
- Ввести измерение окружения (СХЕМА): таблицы `Environment(Key uniq, Name, Order, IsEnabled)` и `MrDeploymentState(MergeRequestId, EnvironmentId, State, UpdatedAt Utc, RowVersion; PK (MergeRequestId, EnvironmentId))`; per-MR одноколоночное состояние на `MergeRequest` заменяется этим per-env ребёнком. Каждая новая RowVersion-сущность (`MrDeploymentState`) -- собственная запись `ProviderSpecificMapping` (rowversion/xmin). Админ-страница Environments (упорядоченный список, вкл/выкл, тумблер вентиля прогрессии). Заполняется состояние в P3.
- Добавить `TasksController` + методы `IReleasePlannerService`, scoped на задачу, + проекцию готовности (per-окружение) + per-task YAML import/export/validate. YAML плана остаётся env-agnostic; окружение выбирается на запуске, не хранится в плане ([006](006-per-task-planning.md)).
- PWA: лендинг Tasks + дерево плана под задачу (сначала read-only, затем правка) + бейджи готовности с селектором окружения; переключить сообщения пересчета на per-task (`RolloutPlanRecalculationRequested(taskId)`, env-free).
- Перевести выпадающие списки соединений/провайдеров на сервер.

**Риск.** Два представления рёбер (сохранённые рёбра плана против вычисляемых рёбер уровня MR) могут разойтись; правило единственной деривации (import/edit/recalc зовут один и тот же граф) должно держаться тестами. Ключевое решение фазы -- НЕ переключать фильтрованный уникальный индекс: новый индекс на `(TargetTaskId)` живёт на новой таблице, старый остаётся на старой ([004](004-target-architecture.md)). Так фаза действительно отгружаема -- ни один инвариант не переворачивается, пока обе ветки живы. Удаление стеков -- деструктивная миграция, но безопасная именно потому, что боевых строк нет ([001](001-current-state.md)); зеркальные миграции на MsSql и Postgres обязательны обе.

### P3. Движок выполнения (недостающая подсистема)

**Цель.** Запускать и вести безопасные, возобновляемые, упорядоченные выкатки, скоупленные на одно окружение.

**Работы.**
- Подключить `DeploymentState` (Core, значение неизменно) через `MrDeploymentState` из P2 -- истина по паре (MR, окружение); добавить `Rollout` (+`EnvironmentId`, ровно одна пара (TargetTask, Environment)) + `RolloutStep` (деплоит (MR, окружение), env наследуется от выкатки) + `MrDeployClaim` (ключ per (MergeRequestId, EnvironmentId): один MR может катиться в два РАЗНЫХ окружения параллельно, claim не даёт двойной выкатки в ОДНО) + append-only логи попыток/событий; зеркальные миграции с per-entity rowversion/xmin в `ProviderSpecificMapping`.
- Добавить семейство `IDeployStrategy` + `gitlab-merge`/`gitlab-pipeline` + `Workers.Executor` (лизованный оркестратор + консьюмер шагов + асинхронный `StepWatcher`) с атомарной per-(MR, окружение) claim, замороженным `PlanSnapshot`, возобновлением через `ReconcileAsync` и воротами запуска на обязательные рёбра ([007](007-execution-engine.md)). `DeployContext` несёт целевое окружение (ключ); env-специфичные параметры (pipeline, branch, variables) живут в schema-настройках стратегии, адресуемых по окружению ([005](005-extension-model.md)). Топосорт волн остаётся env-agnostic -- прогон идёт на одну пару rollout/окружение.
- Эндпоинты launch (с выбором окружения)/progress/cancel/retry/skip + готовность per-окружение с вентилем прогрессии + сид права `release.execute`; PWA пикер окружения при запуске + живой прогресс (с окружением) + история.

**Риск.** Завершение асинхронных pipeline (гонка poll-vs-webhook, зависший InProgress) и неидемпотентные сторонние стратегии -- там, где концентрируются баги; watchdog-таймаут + conformance-тест смягчают, но остаточный best-effort остаётся. Вентиль прогрессии окружений -- новая логика готовности, которую надо покрыть тестом прямо: молча пропущенный prod до staging -- ровно тот отказ, который проект не терпит. Каждая новая RowVersion-сущность (`Rollout`, `RolloutStep`, `RolloutPlan`, `MrDeployClaim`, `MrDeploymentState`) нуждается в СОБСТВЕННОЙ записи `ProviderSpecificMapping`, иначе Npgsql молча мапит `[Timestamp]` в незаписываемый `bytea` и оптимистичная конкуренция на Postgres не срабатывает вообще -- а на ней частично держится защита от двойной выкатки; per-(MR, окружение) ключевание claim и состояния удваивает число таких сущностей, которые надо изолировать для Postgres.

### P4. Подключаемые обработчики действий

**Цель.** Управляемые конфигом эффекты в трекере/уведомлениях на события выполнения и приема.

**Работы.**
- Добавить семейство `IActionHandler` + `ActionBinding` + опциональный `ITrackerMutator` на Yandex (проба через `is`, тот же шаблон, что `ITrackerDependencySource`) + `Providers.Telegram` + `ActionDispatcher`/`ActionConsumer`.

**Риск.** Отказ действия должен быть изолирован от пути выкатки (`ActionConsumer` отдельный, провал telegram/tracker НИКОГДА не валит шаг деплоя); двойной выстрел при падении после side-effect ограничен per-binding дедупом, но не исключён.

### P5. Демонтаж старой формы

**Цель.** Убрать допущение глобального плана отовсюду и добить UX.

## 6. Дисциплина "каждая фаза собирается и зелена"

`TreatWarningsAsErrors=true`, поэтому "0 предупреждений" -- условие сборки, а не пожелание. После каждой фазы:

```bash
dotnet build ReleaseOrchestrator.slnx -v q --nologo   # 0 ошибок, 0 предупреждений
dotnet test ReleaseOrchestrator.slnx
bash scripts/clean-empty-files.sh                       # перед каждым коммитом
```

Аддитивность -- не стиль, а условие зелени: новые таблицы рядом со старыми, опциональные параметры с дефолтами, новые типы сообщений на той же единственной входной очереди (`MessageRouting.InputQueue`). Ни одна фаза не переключает инвариант, пока обе ветки кода живы.

### 6.1. Проверка на живой БД -- часть определения "готово"

SQLite ДЛЯ БД-тестов остаётся ([006](006-per-task-planning.md), PlannerTestBase), но три поведения он НЕ воспроизводит, и ровно они -- в этом дизайне:

| Поведение | Почему SQLite не годится | Где проверять |
|---|---|---|
| Фильтрованный уникальный индекс на `(TargetTaskId)` | SQLite не воспроизводит write-семантику фильтрованного индекса; sqlcmd к тому же ставит `QUOTED_IDENTIFIER OFF` (нужен `-I`) | живой SQL Server + Postgres |
| rowversion vs xmin (токен конкуренции) | Npgsql молча принимает `[Timestamp]` как `bytea` -- баг невидим на SQLite и на одной БД | обе БД, отдельная запись `ProviderSpecificMapping` на сущность |
| Семантика claim (single-writer, порядок каскадов FK) | SQLite не показывает порядок каскадов и гонку одиночного писателя `MrDeployClaim` | живой SQL Server |

Локальный SQL Server и Postgres доступны (проверено, CLAUDE.md); "негде проверить интеграцию" больше не аргумент. Инвариант, который SQLite показать не может, пишется в тесте прямо -- что не проверено, называется непроверенным. Именно недостижимость чистого кода для теста однажды скрыла инверсию рёбер графа до аудита; повторять этот отказ нельзя.

## 7. Новая структура хостов и docker-compose

Два новых деплоя-хоста, оба разделяют `Infrastructure`, оба выбирают плагины по строке-ключу из строки БД (НЕ через env):

| Хост | Роль | Появляется в фазе |
|---|---|---|
| `Workers.Polling` | лизованный цикл на соединение с `IngestionMode=Poll`; читает курсор, зовёт `IPollingSource.PollAsync`, эмитит нормализованные события, двигает курсор | P1 |
| `Workers.Executor` | лизованный `RolloutOrchestrator` (без состояния в памяти) + консьюмер шагов + асинхронный `StepWatcher` | P3 |

Компиляция всех стратегий/обработчиков/источников -- в композиционном корне (`InfrastructureExtensions.AddInfrastructure`): существующие `AddGitLabProvider()`/`AddYandexTrackerProvider()` плюс `AddGitLabDeployStrategies()`, `AddTrackerActionHandlers()`, `AddTelegramAction()`, `AddGitLabIngestion()`/`AddYandexTrackerIngestion()`. Добавить плагин = новый проект `Providers.*` + одна строка `AddX()` + строка в БД + пересборка образа. Никакого Core-изменения, никакой миграции, никакой динамической загрузки ([005](005-extension-model.md)).

Влияние на `docker-compose` (иллюстративная форма, предлагаемая):

```yaml
services:
  web:               # корень композиции, API, PWA, SignalR-хаб
    image: releaseorchestrator/web
  ingress:           # send-only фронт вебхуков; ProjectReferences провайдеры
    image: releaseorchestrator/ingress
  workers-polling:   # НОВЫЙ, P1
    image: releaseorchestrator/workers-polling
  workers-executor:  # НОВЫЙ, P3
    image: releaseorchestrator/workers-executor
  # rabbitmq, db (mssql|postgres), seq -- как раньше
```

Env выбирает только host-синглтоны: `Auth:Provider` (AzureAd|Oidc|Local), провайдер БД (MsSql|Postgres, обе сборки миграций всегда зеркальны), RabbitMQ, Seq/OTEL, key ring DataProtection, секреты уведомлений (инжектятся env, читаются через схему). Версии пакетов -- только в `Directory.Packages.props` (CPM). Реестр Docker в среде фильтруется (CLAUDE.md), поэтому теги новых образов проверяются на имеющемся, а не тянутся заново.

## 8. Что осознанно отложено

- **Per-task/per-team авторизация запуска.** Пока только глобальная claim `release.execute`; кто может запускать выкатку какой задачи -- отложено ([004](004-target-architecture.md) risk register).
- **Рост inbox и append-only логов.** `ProcessedEvent` и логи попыток растут неограниченно под опросом и ретраями -- нужна политика TTL/партиционирования/архива, иначе горячая точка.

Всё перечисленное -- явные открытые пункты, а не полуреализованные допущения: проект не путает "спроектировано" с "работает" ([001](001-current-state.md)).
