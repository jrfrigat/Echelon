# 008. Прием событий и обмен сообщениями

> Черновик от 2026-07-18. Проектный документ, не отчет о сделанном.

## 1. Зачем этот документ

Пивот на per-task выкатку (см. [004](004-target-architecture.md)) ничего не меняет в том, откуда берутся данные: атлас (`TaskItem`, `TaskDependency`, `MergeRequest`, соединения) по-прежнему наполняется из вебхуков GitLab и из опроса трекера. Но он меняет требования к слою приема:

1. Появляется второй канал наблюдения. Сегодня MR приходят только push-ом (вебхук), а задачи -- только pull-ом (`TaskReconciliationService`). Целевая модель делает оба канала взаимозаменяемыми для любого соединения: одно и то же изменение "MR смержен" может прийти И вебхуком, И опросом. Как только это возможно, дедупликация из удобства превращается в обязательное условие корректности.
2. Появляется исполнение ([007](007-execution-engine.md)). Оно порождает собственный поток сообщений (команды шага, опрос пайплайна, оседание шага) и требует, чтобы событийная модель была типизированной и трассируемой, а не мешком нетипизированных конвертов.
3. Расчет плана перестает быть глобальным. Единое `ReleasePlanRecalculationRequested` уступает место per-task сообщениям.

Этот документ фиксирует шесть решений: минимальную идентичность события вместо полного конверта CloudEvents, обязательный inbox дедупликации, симметрию push/pull за одним нормализованным потоком, детерминированные id у поллера, per-connection режим приема с курсором и новый словарь сообщений. Работа разбита по фазам P1 (прием) и далее в [009](009-admin-and-migration.md).

## 2. Идентичность события: минимальная, а не конверт

Исследование [002](002-provider-independence.md) s.3.7 предлагало взять из CloudEvents "форму конверта, а не SDK": `source` + `id` для дедупа, `type` для роутинга, `dataschema` для версионирования. Целевое решение берет из этого ровно одну часть -- пару `(source, id)` -- и сознательно отказывается от остального.

Каждое нормализованное событие приема реализует один интерфейс:

```csharp
// Providers.Abstractions/Ingestion/IHasEventIdentity.cs (предлагаемая форма)
public interface IHasEventIdentity
{
    /// <summary>Источник события: "{providerType}/{connectionName}".</summary>
    string Source { get; }

    /// <summary>Идентификатор события, уникальный в пределах Source.</summary>
    string EventId { get; }
}
```

`Source` = `"{providerType}/{connectionName}"` -- нормализованный тип провайдера плюс имя соединения (соединения уникальны по имени). `EventId` -- собственный id провайдера там, где он есть (у GitLab это заголовок `X-Gitlab-Event-UUID`), иначе детерминированный хеш (см. s.5). Больше в идентичности нет ничего.

### Почему не единый JsonElement-конверт, маршрутизируемый по строке Type

Соблазн был: свернуть все в один `CloudEvent { Source, Id, Type, JsonElement Data }` и роутить консьюмеры по строке `Type`. Это отвергнуто.

| Что дает конверт | Что он стоит |
|---|---|
| Единая форма на проводе | `Data` становится нетипизированным `JsonElement` -- теряется вся проверка на этапе компиляции, которую дает Rebus `TypeBased` |
| Обобщенный роутинг по строке | Строковый `Type` -- это рукописный реестр, расходящийся с типами молча |
| Совместимость с чужими системами | У нас Ingress и консьюмеры -- один солюшн; совместимость с чужими системами не нужна |

Ключевое наблюдение: единственное, что нужно дедупу, -- это `(Source, EventId)`. Полный конверт платит цену типобезопасности и оставляет наполовину мигрированную модель сообщений ради выгоды, которую полностью закрывают два строковых поля. Поэтому пять существующих записей приема (`MrOpened`, `MrStatusChanged`, `TaskCreated`, `TaskStatusChanged`, `TaskSyncRequested`) просто получают интерфейс `IHasEventIdentity`, а не переезжают в конверт. Шестая запись контрактов, `ReleasePlanRecalculationRequested`, -- это не событие приема, а внутренний триггер пересчета, и она в этом дизайне заменяется на per-task `RolloutPlanRecalculationRequested` (разд. 8), поэтому идентичность события ей не нужна. Новые виды событий -- это новые типизированные записи, как и раньше.

## 3. Inbox дедупликации: `ProcessedEvent`

Дедуп реализуется таблицей-inbox и шагом входящего конвейера Rebus, а не логикой в каждом хендлере.

```csharp
// Infrastructure/Persistence/Models/ProcessedEvent.cs (предлагаемая форма)
public sealed class ProcessedEvent
{
    public string Source { get; set; } = default!;    // часть составного PK
    public string EventId { get; set; } = default!;   // часть составного PK
    public DateTime ProcessedAt { get; set; }         // Kind=Utc
}
// Составной первичный ключ (Source, EventId).
```

Порядок обработки во входящем шаге Rebus, до диспетчеризации в хендлер:

1. Сообщение реализует `IHasEventIdentity` -> пробуем вставить строку `(Source, EventId)`.
2. Вставка прошла -> событие новое, пропускаем дальше в хендлер.
3. Нарушение уникальности (составной PK) -> событие уже обработано -> ack-and-drop, хендлер не вызывается.

### Почему дедуп теперь обязателен

Раньше идемпотентности на уровне хендлера (upsert по натуральному ключу MR/задачи) хватало: каждое изменение приходило ровно из одного канала, повтор давал тот же upsert. Как только push И poll видят одно и то же изменение, этого недостаточно: два канала могут доставить одно событие в разной форме и в разное время, а поллер на каждом цикле будет пере-наблюдать неизменившееся состояние. Без inbox опрос порождал бы поток повторной обработки на каждом тике. Поэтому дедуп -- не оптимизация, а условие того, что два симметричных канала (s.4) никогда не разойдутся в том, что "смержено"/"решено".

Дедуп не отменяет уже существующий паттерн "retry-to-resolve" для доставки не по порядку (`*NotYetKnownException`, 5 попыток, затем error queue): inbox гасит повторы одного и того же события, а не упорядочивает разные. Оба механизма ортогональны и оба остаются.

> Риск, зафиксированный явно: таблица `ProcessedEvent` и append-only логи исполнения растут неограниченно под опросом и ретраями. Нужна политика удержания (TTL / партиционирование / архивация), иначе inbox становится горячей точкой. Это отдельная задача фазы P1, а не деталь.

## 4. Симметрия push и pull

Оба канала -- push и pull -- это две взаимозаменяемые реализации одного порта приема, эмитирующие ОДНИ И ТЕ ЖЕ типизированные нормализованные события. Именно общий тип события гарантирует, что каналы не могут разойтись в трактовке изменения.

```csharp
// Providers.Abstractions/Ingestion/ (предлагаемые формы)
public interface IWebhookTranslator          // push
{
    bool VerifySignature(WebhookRequest request, string secret);
    IReadOnlyList<IHasEventIdentity> Translate(WebhookRequest request, string connectionName);
}

public interface IPollingSource              // pull
{
    Task<PollResult> PollAsync(PollContext context, CancellationToken ct);
}

public sealed record PollResult(
    IReadOnlyList<IHasEventIdentity> Events,
    string NextCursor);
```

Обе реализации регистрируются тем же механизмом, что и остальные три оси расширения ([005](005-extension-model.md)): keyed service по `ProviderType`, маркер-регистрация, фабрика, `ProviderSettingSchema`. Диалект уходит из Ingress за порт: `GitLabMergeRequestState`, `BranchTaskParser`, `YandexTrackerStatusRules` переезжают из `Ingress` в соответствующие `Providers.*` за `IWebhookTranslator`/`IPollingSource`.

### 4.1. Push: Ingress становится провайдер-агностичным

`Ingress.Webhooks` остается send-only фасадом, но его эндпоинты перестают быть захардкоженными по провайдеру. Целевая форма -- один параметризованный маршрут:

```
POST /webhooks/{connectionName}
  1. по connectionName находим соединение -> его ProviderType
  2. резолвим keyed IWebhookTranslator по ProviderType
  3. VerifySignature (constant-time, fail-closed) -- сохраняется
  4. Translate(payload) -> нормализованные события
  5. bus.Send(...) для каждого
  6. брокер недоступен -> 503 + Retry-After -- сохраняется
```

Это убирает два захардкоженных эндпоинта, две модели payload и разные заголовки секрета из [002](002-provider-independence.md) s.2.4. Проверка подписи по-прежнему двухфазна (сначала понять, какое это соединение, потом достать его секрет), как `SecretFunc` в go-scm ([002](002-provider-independence.md) s.5.5).

Честная оговорка про "no-ALC" (см. [005](005-extension-model.md) и `decisionsReconciled`): исчезают файлы эндпоинтов и захардкоженные маршруты, но НЕ ссылка на сборки. Хост-сборка `Ingress.Webhooks` обязана по-прежнему compile-time `ProjectReference` на `Providers.*`, иначе трансляторы не окажутся в ее DI-контейнере. Утверждать "ноль ссылок на провайдеров в хосте" -- значит требовать динамической загрузки, которая отвергнута в [002](002-provider-independence.md) s.4. Провайдер-агностичны становятся эндпоинты, а не граф сборок.

### 4.2. Pull: обобщение арендного воркера

Существующий `TaskReconciliationService` уже несет нужный скелет: распределенная аренда (lease) плюс `PeriodicTimer`. Его сегодняшняя проблема -- он захардкожен под задачи. Целевая модель обобщает его в хост `Workers.Polling`, который держит по одному арендованному циклу на каждое соединение с `IngestionMode=Poll`:

```
для каждого соединения с IngestionMode=Poll (под арендой):
  cursor <- прочитать IngestionCursor соединения
  result <- IPollingSource.PollAsync(new PollContext(connection, cursor), ct)
  для каждого события result.Events -> bus.Send(...)   // те же типы, что и push
  записать result.NextCursor в IngestionCursor          // атомарно с обработкой
```

`IPollingSource` для VCS переиспользует существующие read-порты (`GetOpenMergeRequestsAsync` и т.п.) -- это те же провайдерские методы, что уже есть, только вызванные по расписанию, а не по вебхуку.

## 5. Детерминированные id у поллера

Push получает `EventId` бесплатно из заголовка провайдера. Pull не наблюдает "событие" -- он наблюдает СОСТОЯНИЕ. Чтобы дедуп работал и на pull, поллер обязан синтезировать детерминированный id из наблюдаемого состояния:

```
EventId = hash(Source + entityKey + (updatedAt || version))
```

Свойство, которое это дает: пере-опрос неизменившегося состояния порождает ТОТ ЖЕ `EventId`, а значит `ProcessedEvent` его отбрасывает (self-dedup). Меняется только `updatedAt`/`version` -- меняется и id, событие проходит. Поэтому дедуп работает симметрично для обоих каналов без специальной логики в хендлерах.

> Риск, зафиксированный явно: если поллер синтезирует id недетерминированно (например, подмешивает время опроса), дедуп молча ломается -- каждый цикл пере-обрабатывает все, что видит. Это тихий отказ, который не проявится в тесте на одном канале. Детерминизм id -- предмет отдельного теста в P1.

## 6. Осиротевший `VcsService.SyncMergeRequestAsync` наконец получает вызывающего

Сегодня `VcsService.SyncMergeRequestAsync` -- мертвый код: у задач есть бэкстоп сверки (`TaskReconciliationService`), а у MR его нет, поэтому метод сверки MR никто не зовет. VCS-реализация `IPollingSource` (`IngestionMode=Poll`) складывает этот метод в свой цикл: поллер по расписанию сверяет открытые MR соединения, синтезирует детерминированные id и эмитит нормализованные события. Это закрывает асимметрию из s.1: MR получают тот же бэкстоп на потерянные вебхуки, что уже есть у задач, а осиротевший метод перестает быть мертвым кодом и становится телом источника опроса VCS.

## 7. Per-connection `IngestionMode` и курсор

Режим приема -- свойство соединения, а не глобальная настройка. Конфигурация -- данные плюс строковые ключи, никаких колонок под провайдера (см. [009](009-admin-and-migration.md)).

```csharp
public enum IngestionMode { Push = 1, Poll = 2 }
```

| Поле | Где | Смысл |
|---|---|---|
| `IngestionMode` | `VcsConnection` / `TrackerConnection` | Push или Poll -- какой порт активен для этого соединения |
| `PollIntervalSeconds` | там же | Период `PeriodicTimer` для Poll |
| `IngestionCursor` | отдельная строка на соединение | Последняя позиция опроса (`NextCursor` из `PollResult`); только у Poll-соединений |

`IngestionCursor` продвигается атомарно вместе с обработкой пачки: курсор нельзя двинуть вперед, если события пачки не отправлены на шину. Свежесть курсора видна оператору в админке ([009](009-admin-and-migration.md), экран Ingestion). Все даты -- `Kind=Utc`. Новые сущности (`ProcessedEvent`, `IngestionCursor`) -- attribute-first маппинг, зеркальные миграции на MsSql и Postgres.

## 8. Новый словарь сообщений

Все сообщения остаются типизированными записями `IMessage`, роутинг -- `TypeBased`, единственная входная очередь -- прежняя константа `MessageRouting.InputQueue`. Меняется состав словаря, не транспорт.

### 8.1. Per-task расчет и готовность

Глобальное `ReleasePlanRecalculationRequested` заменяется на per-task записи. Единый глобальный план демотирован до внутренней read-model ([004](004-target-architecture.md)), поэтому и триггер расчета становится точечным.

Здесь проходит граница окружений (см. [004](004-target-architecture.md), [007](007-execution-engine.md)): окружение -- ортогональное измерение выкатки, но не плана. Дерево и порядок задачи одинаковы во всех окружениях, поэтому расчет плана env-free -- `RolloutPlanRecalculationRequested` несет только `TaskId`. Готовность же считается per-environment: (T, E) готова независимо от (T, E'), -- поэтому `TaskReadinessChanged` несет и `EnvironmentId`.

```csharp
public sealed record RolloutPlanRecalculationRequested(Guid TaskId) : IMessage;
public sealed record TaskReadinessChanged(Guid TaskId, Guid EnvironmentId) : IMessage;
```

### 8.2. Команды и события исполнения

Порождаются движком выкатки ([007](007-execution-engine.md)); здесь важно лишь, что они едут по тому же транспорту, что и события приема. Выкатка нацелена ровно на одно окружение ([007](007-execution-engine.md)): окружение задается при запуске и наследуется шагами, поэтому `RolloutLaunched` и команды шага деплоя несут `EnvironmentId` -- стратегия деплоя ([005](005-extension-model.md)) должна знать, в какое окружение катит, не восстанавливая его из `RolloutId`.

```csharp
public sealed record RolloutLaunched(Guid RolloutId, Guid EnvironmentId) : IMessage;
public sealed record DeployStepRequested(Guid RolloutId, Guid StepId, Guid EnvironmentId) : IMessage;
public sealed record DeployStepPollRequested(Guid RolloutId, Guid StepId, Guid EnvironmentId) : IMessage;
public sealed record StepSettled(Guid RolloutId, Guid StepId) : IMessage;
public sealed record RolloutCancellationRequested(Guid RolloutId) : IMessage;
```

### 8.3. Действия

`ActionRequested` разводит побочные эффекты (Telegram, запись в трекер) на отдельного консьюмера, чтобы упавшее действие логировалось и ретраилось независимо и НИКОГДА не роняло шаг деплоя ([007](007-execution-engine.md)).

```csharp
public sealed record ActionRequested(
    Guid BindingId, string ActionType, string PayloadJson) : IMessage;
```

### 8.4. Единый транспорт

Сегодня строитель строки подключения AMQP продублирован: одна копия в `Ingress`, другая в `Infrastructure`. Копии расходятся молча. Целевая модель сводит их в один сборщик в `Application/Contracts`, который используют оба хоста (плюс новые `Workers.Executor` и `Workers.Polling`). Одна правка вместо двух, и настройки транспорта не разъезжаются.

## 9. Что кладется в основу, а что явно не проверено

Симметрия push/pull и дедуп -- это механика; она корректна независимо от содержимого атласа. Но две посылки за пределами этого слоя остаются НЕ проверенными и должны быть подтверждены до того, как per-task деревья обретут смысл (см. [006](006-per-task-planning.md), фаза P0):

1. `TaskDependency` должен реально наполняться на боевых конфигурациях. Аудит это пометил; роадмап утверждает, что починено. Пока не подтверждено сквозным прогоном -- посылка.
2. НАПРАВЛЕНИЕ ребра зависимостей Яндекс.Трекера помечено UNVERIFIED прямо в коде. Неверное направление инвертирует каждое дерево. Как предупреждает Atlassian и s.3.6 [002](002-provider-independence.md), направление обязан вычислять адаптер -- API его не гарантирует. Подтвердить против живого API.

Прием событий этих двух вещей не чинит и не может подменить: он лишь гарантирует, что данные попадают в атлас ровно один раз и одинаково по обоим каналам.

## 10. Сводка решений

| Решение | Выбор | Почему |
|---|---|---|
| Форма идентичности | `IHasEventIdentity { Source, EventId }` | Дедупу нужны только два поля; конверт платит типобезопасностью |
| Роутинг | Типизированный Rebus `TypeBased` сохранен | Нет нетипизированного `JsonElement`, нет полумигрированной модели |
| Дедуп | `ProcessedEvent` inbox + входящий шаг Rebus | Обязателен, как только push и poll видят одно изменение |
| Push | Провайдер-агностичный `/webhooks/{connectionName}` | Диалект за `IWebhookTranslator`; хост все еще ссылается на провайдеров |
| Pull | Обобщенный арендный `Workers.Polling` + `IPollingSource` | Переиспользует lease-скелет и read-порты; дает MR бэкстоп сверки |
| Id поллера | Детерминированный `hash(source+key+updatedAt)` | Пере-опрос неизменного состояния само-дедуплицируется |
| Режим | Per-connection `IngestionMode` + `IngestionCursor` | Push/pull взаимозаменяемы для любого соединения |
| Транспорт | Один AMQP-сборщик в `Application/Contracts` | Убирает молчаливо расходящийся дубль |
