Разворот -- это **эволюция луковицы, а не переписывание.** Все, что аудит ([001](001-current-state.md)) и исследование независимости ([002](002-provider-independence.md)) признали хорошим, сохраняется дословно: ядро с нулем зависимостей, чистый `ReleasePlanGraph` без EF, анти-коррупционный шов `PlanMergeRequest`, нормализованное ребро `TaskDependency`, позднее связывание MR с задачей, keyed-services-шов провайдеров, Rebus, конвейер auth/permissions, resx-локализация, изоляция диалектов в `ProviderSpecificMapping`, дисциплина `Kind=Utc` + `RowVersion`. ## 1. Видение продукта и центральное расхождение

### 1.1. Что построено

Сегодня центральный объект продукта -- **один глобальный план**: `ReleasePlan` с фильтрованным уникальным индексом по `IsActive` (ровно один активный план на всю систему), в него сложены все готовые к выкатке MR, разложенные по стадиям Kahn-уровней. PWA открывается на этом плане (маршрут `/`), оператор перетаскивает MR между стадиями. Админка умеет заводить соединения, репозитории и стеки. Чего в ней нет: **списка задач, плана под конкретную задачу и вообще какого-либо исполнения выкатки.** Отсюда прямая цитата из отзыва: "я не понимаю, для чего приложение".

### 1.2. Что нужно

Оператор мыслит не "глобальным планом всех готовых MR", а **задачей, которую он хочет выкатить.** Целевая модель:

1. оператор выбирает задачу к выкатке;
2. видит дерево ее зависимостей -- задачи-предпосылки и их merge requests;
3. видит, ГОТОВА ли она (каждая предпосылка выкачена);
4. запускает выкатку;
5. наблюдает, как она исполняется в порядке зависимостей, каждый VCS -- по своему принципу деплоя.

### 1.3. Расхождение и его разрешение

Глобальная сортировка всех готовых MR по стадиям не выбрасывается -- она **понижается в статусе**: из центрального объекта продукта в внутреннюю read-модель. Мы называем ее **атлас** -- живое объединение всех рёбер зависимостей, из которого вырезается каждый план-под-задачу. Атлас остается тем самым чистым `ReleasePlanGraph`; меняется не он, а то, что план теперь -- это проекция атласа, укорененная в целевой задаче, а не сам атлас целиком.

Синтез называется **"Выкатка от задачи поверх внутрипроцессной оси расширения из четырех семейств".** Он закрывает все восемь требований поворота, не нарушая ни одного жесткого ограничения (см. чек-лист в разделе 8).

## 2. Атлас (источник истины) против RolloutPlan-под-задачу (проекция)

Два чисто разделенных понятия. Их смешение -- корень путаницы текущей модели.

### 2.1. Атлас -- источник истины

Атлас -- это живое объединение всех принятых данных, и оно сохраняется без изменений:

| Сущность | Роль в атласе |
|---|---|
| `TaskItem` | задача трекера; `ExternalId` уникален в пределах `TrackerConnectionId`, `Status` -- собственный ключ трекера |
| `TaskDependency` | нормализованная упорядоченная пара `DependentTask` waits-on `DependsOnTask`; уникальный индекс, `Restrict` на обе связи -- сохраняется дословно (вывод [002](002-provider-independence.md) s.3.6: это единственное ребро, которое есть во всех трекерах) |
| `MergeRequest` | позднее связывание через `TaskExternalId`; `Status` -- нормализованный enum текстом |
| `Repository`, `VcsConnection`, `TrackerConnection` | соединения и их конфигурация |
| `RepositoryDependency` | конфигурируемое упорядочивание репозиториев: `FromRepository` деплоится ПОСЛЕ `ToRepository`, тип `Hard`/`Soft`; уникальная пара, `Restrict` на обе связи, запрет петли; редактируется в админке и YAML -- это и есть правило построения плана, которым заменены стеки (DELTA, [006](006-per-task-planning.md)) |
| `Environment` | именованная цель деплоя `{ Id, Key (unique, "staging"/"prod"), Name, Order (int), IsEnabled }`; конфигурируемый упорядоченный список (глобальный для v1), `Order` задает последовательность промоушена (staging до prod); ортогональное измерение, не усложняющее чистый граф |

**Атлас сам по себе никогда не является планом.** Он -- материал, из которого план вырезается.

### 2.2. RolloutPlan -- укорененная проекция

План-под-задачу -- новый агрегат, живущий в **новой таблице рядом со старой** `ReleasePlan`, а не вместо нее (см. решение о coexistence в разделе 6). Предлагаемая форма:

```csharp
// Предлагаемая форма, не скопированный код.
public sealed class RolloutPlan
{
    public Guid Id { get; set; }
    public Guid TargetTaskId { get; set; }              // FK Restrict
    public int Version { get; set; }
    public PlanSource Source { get; set; }              // Generated | Imported | Edited
    public PlanStatus Status { get; set; }              // Draft | Ready | Stale
    public string YamlHash { get; set; }                // детект внешнего дрейфа
    public string ConflictsJson { get; set; }           // ViolatedBy, никогда не молча
    public DateTime SnapshotStartedAt { get; set; }     // Kind=Utc
    public byte[] RowVersion { get; set; }
}
```

Ключевое: у `RolloutPlan` **свой** фильтрованный уникальный индекс по `TargetTaskId WHERE active` -- ровно один активный план **на задачу** (а не один на систему). Дети агрегата:

- `PlanTaskNode { RolloutPlanId, TaskId }` -- задача, попавшая в замыкание цели;
- `PlanItem { PlanTaskNodeId, MergeRequestId, DeployStrategyKeyOverride?, IntraTaskOrder?, ManualInclusion }` -- MR, привязанный к узлу-задаче;
- `PlanOverride { RolloutPlanId, Kind, Payload }` -- правки оператора как дельты (`AddEdge | RemoveEdge | IncludeMr | ExcludeMr | SetIntraTaskOrder`), которые переживают `Recalculate`.

Подробно закрытие замыкания, аддитивное расширение чистого графа и семантика overrides -- в [006](006-per-task-planning.md).

## 3. Идентичность узла: граф из MR против дерева из задач

Это разрешение фатального изъяна, который проходил через несколько черновиков поля: они пытались хранить Kahn-уровень **на задаче** и "группировать уровни MR под задачей". Так делать нельзя.

`PlanMergeRequest.cs` формулирует правило -- в редакции DELTA оно ослаблено: **"merge requests одной задачи не упорядочиваются друг другом ПО ЗАВИСИМОСТИ задач; они не упорядочены, КРОМЕ случая, когда политика упорядочивания репозиториев упорядочивает их репозитории".** Ребра `TaskDependency` между ними по-прежнему нет (они делят одну задачу), но `RepositoryDependency` МОЖЕТ упорядочить их, если их репозитории связаны ([006](006-per-task-planning.md)). Значит, задача тем более НЕ занимает одну волну -- ее MR могут законно попасть в разные волны (и из-за repo-политики, и из-за замыкания). Следствие однозначно:

| Понятие | Уровень | Где живет |
|---|---|---|
| Волна исполнения (Kahn-уровень) | **свойство MR** | `RolloutStep.Wave`, из MR-level топосортировки |
| Дерево, которое видит оператор | **презентационная группировка** | целевая задача в корне, задачи-предпосылки как дети через `TaskDependency`, MR -- листья |

Граф-узел остается MR (`ReleasePlanGraph` MR-центричен). Дерево -- это способ показать замыкание оператору, а не структура исполнения. Мы **не персистим** per-task Kahn Level: он был бы ложью об порядке исполнения. Разделение "группировка для показа" против "волны исполнения" -- то, что сохраняет чистый движок переиспользуемым и корректным. Обоснование -- в таблице решений (раздел 6, вопрос об идентичности узла).

## 4. Две истины готовности

Лучшая идея поля -- **разделить две истины о состоянии MR**, которые сегодня свёрнуты в одну.

### 4.1. Истина приема против истины оркестратора

| Истина | Enum | Кто заполняет | Смысл |
|---|---|---|---|
| Приема (ingestion) | `MergeRequestStatus { Opened=1, Reviewed=2, ReadyForDeploy=3, Merged=4, Closed=5 }` | прием событий из VCS | в каком состоянии MR у провайдера |
| Оркестратора | `DeploymentState { NotStarted, Claimed, Deploying, Deployed, Failed, Skipped }` | движок исполнения | что оркестратор сделал с этим MR |

`MergeRequestStatus` сохраняется нетронутым. `DeploymentState` -- **новый Core-enum** (Core остается zero-dep, это чистое перечисление) как ЗНАЧЕНИЕ неизменен; меняется его КЛЮЧЕВАНИЕ (DELTA). Истина деплоя теперь ведется не одним столбцом на `MergeRequest`, а на пару (MR, окружение) -- в новой таблице `MrDeploymentState { MergeRequestId, EnvironmentId, State (DeploymentState), UpdatedAt (Utc), RowVersion }`, PK `(MergeRequestId, EnvironmentId)`, заменяющей прежний per-MR столбец на `MergeRequest`. MR -- по-прежнему единица, которую стратегия деплоит, но теперь в конкретное окружение: тот же MR может быть `Deployed` в staging и `NotStarted` в prod одновременно. (Каждая новая `RowVersion`-сущность требует своей записи в `ProviderSpecificMapping` -- стандартная ловушка.) Держать приемную и оркестраторскую истины раздельно -- значит быть защищенным от дрейфа: приемная истина и оркестраторская истина не могут затереть друг друга.

### 4.2. Вывод готовности и семантика замыкания

Готовность -- **производная, а не отдельный хранимый флаг, и считается ПЕР окружение** (DELTA):

- задача **Deployed в окружении E**, когда каждый ее деплоящийся MR имеет `Deployed`/`Skipped` в E; задача без деплоящихся MR авто-удовлетворена;
- готовность пары (цель, E) = каждая задача в замыкании зависимостей цели (кроме самой цели) -- Deployed в E; ПЛЮС опциональный конфигурируемый **гейт прогрессии окружений**: деплой (T, E) может требовать, чтобы T была уже Deployed в окружениях, стоящих в `Order` перед E (по умолчанию включен, поэтому prod требует staging). Гейт -- конфиг, редактируемый.

Для скорости списков поддерживается быстрая per-(задача, окружение) read-модель `TaskDeploymentStatus { TaskId, EnvironmentId, ... }`, транзакционно, но она **явно перестраиваема** из `MrDeploymentState` -- и потому никогда не может стать дрейфующим источником истины.

Семантика замыкания (единственно связная): выкатка перещелкивает `DeploymentState` для **каждого** MR, который деплоит через все замыкание, в целевом окружении прогона. Поэтому зависимость, выкаченная внутри прогона родителя, помечает эту задачу-зависимость Deployed в этом окружении и разблокирует ее **других** зависимых. Иначе задачи-зависимости никогда не достигли бы Deployed и межзадачная готовность была бы недостижима. Замыкание и `ReleasePlanGraph` при этом **окружение-агностичны**: выкатка исполняет то же per-task упорядочивание, но с привязкой к ОДНОМУ окружению -- окружение это слой скоупинга и гейтинга поверх чистого графа, а не его усложнение. Детали исполнения -- в [007](007-execution-engine.md).

| Где живет истина деплоя и как считается готовность без дрейфа? Запуск привязан к одному целевому окружению (см. решение о мульти-окружении ниже); задача без деплоящихся MR авто-удовлетворена | "Запусти эту задачу" становится полной самодостаточной операцией под ментальную модель оператора; окружение -- ортогональный скоуп поверх того же замыкания |

Проигравший гонку общего MR пропускает шаг, когда победитель отметил Deployed; redelivered-отправка видит claimed-by-me и возобновляет через `ExternalRef`/`ReconcileAsync`. Корректность на claim + state machine + reconciliation, НЕ на lease-expiry (lease -- только для liveness) | Один durable claim закрывает три гонки сразу; lease-expiry без fencing -- заведомо небезопасный паттерн |
| Полный CloudEvents-конверт со string-Type роутингом или типизированный Rebus? | Минимальная идентичность, не конверт по проводу: события реализуют `IHasEventIdentity { Source, EventId }` для dedup-inbox; типизированный Rebus TypeBased сохраняется; никакого единого `JsonElement`-конверта. Оба (push-translators и poll-sources) эмитят ОДНИ типизированные события | Дедупу нужно только `(Source, EventId)`; полный конверт заплатил бы type-safety и оставил наполовину мигрированную модель ради будущего, которое сейчас не строится |
| Новая Core-only Contracts-сборка для разрыва цикла между слоями? | Нет. SPI-интерфейсы плагинов + context/result + нормализованные ingestion-события живут в `Providers.Abstractions` (уже reference-ится Infrastructure и Providers.*); Rebus-оркестрация -- в `Application/Contracts`. Core не reference-ит ничего | Цикл возникает, только если поместить интерфейсы провайдеров в Application, чего мы не делаем; вторая сборка дублировала бы `ProviderKey`/schema без пользы для границы |
| Как поменять инвариант "один активный план" без поломки main во время coexistence? | НЕ трогать фильтрованный индекс. Ввести планы-под-задачу как НОВЫЕ таблицы (`RolloutPlan` со своим per-task индексом) рядом с нетронутым глобальным `ReleasePlan`; старый код читает старую таблицу, новый -- новую; удалить старую только в фазе retirement | Каждая фаза остается реально shippable -- ни один инвариант не переворачивается, пока оба пути живы |
| Может ли оператор запустить план, нарушающий обязательное (hard/task) ребро? | Правка/импорт МОГУТ ЗАПИСАТЬ нарушающий план (никогда молча -- `ConflictsJson`, по [001](001-current-state.md) s.2.6), `force` относится к сохранению черновика. Но контрол ЗАПУСКА отказывает любому плану, нарушающему обязательное ребро сейчас | Сохраняет правило "никогда молчаливого плана" и при этом не дает исполнителю выкатить заведомо неверный порядок, когда у планов появились зубы |
| Выживают ли `Stack`/`StackDependency` в модели-под-задачу? | Нет. Стеки удаляются целиком (`Stack`, `StackDependency`, `RepositoryStack`) и заменяются прямым конфигурируемым упорядочиванием репозиториев `RepositoryDependency` (`From` деплоится ПОСЛЕ `To`, `Hard`/`Soft`, уникальная пара, `Restrict` на обе связи, запрет петли; редактируется в админке и YAML). В `PlanEdgeKind` `StackHard`/`StackSoft` становятся `RepoHard`/`RepoSoft` с тем же приоритетом отбрасывания (RepoHard критичнее, затем TaskDependency, RepoSoft отбрасывается первым). Это и есть правило построения плана, которое просил владелец | Прод-данных нет ([001](001-current-state.md)), поэтому удаление чистое и раннее, а не в фазе retirement; прямое repo->repo проще стеков и напрямую выражает нужду в редактируемом порядке репозиториев |

## 7. Сквозной реестр рисков

Риски отсортированы по тому, насколько молча они бьют. Первые два опираются на **непроверенные внешние факты** и должны быть сняты до P2 (см. фазы в [009](009-admin-and-migration.md)).

1. **Дерево зависимостей держится целиком на двух непроверенных фактах.** (а) `TaskDependency` должна быть реально заполнена для боевых установок -- аудит это флагнул, roadmap говорит "исправлено", но это надо **подтвердить end-to-end**. (б) НАПРАВЛЕНИЕ ребра зависимости Яндекс.Трекера помечено UNVERIFIED в коде ([002](002-provider-independence.md) s.3.6: Atlassian прямо предупреждает, что направление интерпретируемо только на уровне UI, не API). Неверное направление **инвертирует каждое дерево**. Если любой из фактов неверен, всякое замыкание и всякая готовность пусты или перевернуты.
2. **Асинхронное завершение pipeline -- поверхность наибольшего риска.** Гонки poll-против-webhook, застрявшие InProgress-шаги и провайдеры (например, триггеры GitLab pipeline), не уважающие клиентский idempotency-токен, означают, что "exactly-once deploy" деградирует до best-effort. Смягчается claim-before-call + `ExternalRef` `ReconcileAsync` + watchdog-таймаутом, но не устраняется.
3. **Идемпотентность сторонней deploy-стратегии** -- контрактное обязательство, проверяемое SDK conformance-тестом, но не наказуемое типовой системой; неидемпотентная кастомная стратегия может задвоить деплой на redelivery вопреки per-MR claim, если игнорирует `ExternalRef`.
4. **Forward-only исполнение:** частично провалившаяся мульти-сервисная выкатка (часть MR смержена, поздний шаг упал) не имеет автоматического отката; оператору остается Paused-выкатка и ручной fix-forward, что для части целей может быть неприемлемо.
5. **Per-entity rowversion-против-xmin:** каждая новая `RowVersion`-сущность (`Rollout`, `RolloutStep`, `RolloutPlan`, `MrDeployClaim`, `MrDeploymentState`) нуждается в своей записи в `ProviderSpecificMapping`, иначе Npgsql молча маппит `[Timestamp]` в неписанный `bytea` и оптимистичная конкуренция на Postgres **не срабатывает вообще** -- невидимо, пока не запустят вторую БД, а на этом частично держится guard от двойного деплоя.
6. **`ProcessedEvent`-inbox и append-only логи попыток/событий** растут неограниченно под поллингом и retries; нужна TTL/партиционирование/архивация, иначе они станут hotspot.
7. **Два представления рёбер** (персистентные overrides плана против производных MR-level рёбер графа) могут разойтись; правило "единая деривация для import/edit/recalc" должно быть закреплено тестами, иначе YAML и UI молча разойдутся о том, что такое ограничение.
8. **Рантайм-ошибки ключей** (`DeployStrategyKey`/`ActionType`/`ProviderType` с опечаткой) всплывают как `UnknownProviderException` в рантайме; write-time + startup-валидаторы смягчают, но неверно засеянная prod-строка все же может застопорить выкатку.
9. **Новый фильтрованный индекс по `(TargetTaskId)`, семантика per-MR claim и токены конкуренции** -- ровно то поведение, которое SQLite НЕ воспроизводит; их надо проверять на живом SQL Server + Postgres, иначе повторится провал прошлого аудита.
10. **Корректность гейта прогрессии окружений.** Гейт "(T, prod) требует (T, staging)" -- новая поверхность корректности: неверный `Environment.Order`, ошибочно выключенный гейт или дыра в проверке позволят выкатить в prod, минуя staging. Правило чисто конфигурационное и наказывается только проверкой на запуске, не типами; закрепляется тестом на замыкание + гейт.
11. **Удвоение `RowVersion`-сущностей из-за ключевания per (MR, окружение).** `MrDeploymentState` и per-env `MrDeployClaim` добавляют изолируемые для Postgres сущности (см. риск 5); каждая забытая запись в `ProviderSpecificMapping` молча отключает оптимистичную конкуренцию на Postgres и ослабляет guard от двойного деплоя -- ровно то, что SQLite не покажет.
12. **Конкуренция пересекающихся выкаток** сделана per-MR claim БЕЗОПАСНОЙ, но не СПРАВЕДЛИВОЙ: поведение starvation/ожидания для горячего общего MR не специфицировано и может потребовать очереди или политики приоритета.
13. **Per-task/per-team авторизация запуска** не смоделирована (только глобальный `release.execute`); кто может запускать выкатку какой задачи -- отложено.

## 8. Чек-лист соблюдения жестких ограничений

Каждое ограничение проверяется на **сборке или на живой БД**, а не в рантайме -- в духе [001](001-current-state.md): "designed" не путать с "works".

| Ограничение | Как соблюдается | Как проверяется |
|---|---|---|
| **Core -- ноль зависимостей** | `DeploymentState` -- чистый enum; никаких провайдеров, EF или пакетов в Core | ProjectReference-граф Core пуст; ломается на `dotnet build` |
| **No-ALC** | вся расширяемость -- compile-time keyed services + фабрика по строковому ключу из БД; хосты ProjectReference-ят провайдеров (честная оговорка, см. [005](005-extension-model.md)) | нет `AssemblyLoadContext`, нет `Assembly.Load`; проверяется чтением композиционного корня |
| **CPM** | версии пакетов только в `Directory.Packages.props`; в `.csproj` -- `<PackageReference Include="X" />` без `Version` | `dotnet build` при `TreatWarningsAsErrors` |
| **Зеркальные миграции** | каждая миграция добавляется в `Migrations.MsSql` И `Migrations.Postgres`; каждый новый `RowVersion` -- своя запись в `ProviderSpecificMapping` (rowversion против xmin), фильтр индекса тоже там | `has-pending-model-changes` + live SQL Server и Postgres для инвариантов, которые SQLite не показывает |
| **Kind=Utc** | все новые даты (`StartedAt`/`FinishedAt`/`ProcessedAt`/`ExpiresAt` ...) -- только `Utc`; адаптеры разбирают через `DateTimeOffset` и отдают `.UtcDateTime` | тест на Postgres (Npgsql бросает на `Local`/`Unspecified` в `timestamptz`) |
| **0 предупреждений** | `TreatWarningsAsErrors=true` -- условие сборки, не пожелание; XML-doc на public-членах, где комментарий добавляет смысл | `dotnet build ReleaseOrchestrator.slnx` -- 0 ошибок, 0 предупреждений |
| **Никаких пустых файлов** | `bash scripts/clean-empty-files.sh` перед каждым коммитом | предкоммит-проверка |

Каждая из пяти фаз (P0-P5, [009](009-admin-and-migration.md)) держит эти проверки зелеными -- фаза, оставляющая их красными, не считается завершенной.
