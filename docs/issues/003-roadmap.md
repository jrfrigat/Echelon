# 003. Дальнейшие шаги

Приоритет — по принципу «сначала то, без чего продукт не выполняет свою функцию; потом то, без чего его нельзя эксплуатировать; потом развитие». Оценки — грубые, в человеко-днях, для одного разработчика, знакомого с кодовой базой.

## Этап 0. Проверить то, что не проверено (1–2 дня)

Пока это не сделано, все остальные оценки — гипотезы. Ветка `fix/audit-remediation` собирается и проходит 64 теста, но **приложение не запускалось ни разу**.

1. **Поднять окружение и применить миграции.** `Phase3_PlanIntegrityAndArchive` содержит data-fix SQL, который никогда не выполнялся: схлопывание дублей MR/задач, дедупликация активных планов, backfill `SnapshotStartedAt`. На пустой БД это no-op; на непустой — проверить на копии.
2. **Сверить `.env.example`.** Файл заблокирован настройками разрешений и не прочитан. Все сообщения об ошибках `docker compose` ссылаются на него — если он устарел, они врут. Эталон — README §11.1.
3. **Собрать образы.** Реестр из среды аудита фильтруется; пины версий образов (`mssql/server:2022-CU14-ubuntu-22.04`, `redis:7.4-alpine`, `datalust/seq:2024.3`…) **не проверены на существование**.
4. **Прогнать сквозной сценарий:** вебхук GitLab → MR в БД → лейбл → `ReadyForDeploy` → план. Это первая настоящая проверка того, что ветка работает.
5. **Просканировать пакеты на уязвимости.** Прокси отдавал 403 на `api.nuget.org`; про CVE ничего не известно.

## Этап 1. Продукт должен заработать (3–5 дней)

### 1.1. Загрузка зависимостей задач — **блокер** (2–3 дня)

`TaskDependency` не наполняется ничем ([001 §3.1](001-current-state.md#31-зависимости-задач-не-загружаются-никогда)). Задачные рёбра физически отсутствуют, план строится только по стекам. Это делает бессмысленной половину продукта.

`TrackerService.SyncTaskAsync` написан и не вызывается. Нужно решить, **когда** синхронизировать:

| Вариант | Плюсы | Минусы |
|---|---|---|
| По `TaskCreated`/`TaskStatusChanged` из вебхука | Просто, событийно | Зависимости меняются без смены статуса — вебхук не придёт |
| По `MrOpened` (подтянуть задачу ветки) | Синхронизируем только то, что нужно плану | Задача может измениться после создания MR |
| По расписанию для открытых задач | Ловит всё | Нагрузка на API трекера, лаг |
| **Комбинация: событие + периодический догон** | Покрывает оба класса | Больше кода |

Рекомендация — комбинация, но это **решение владельца продукта**, а не техническое.

Смежное: у Яндекс.Трекера нет вебхука «связи изменились» — **не проверено**, требует уточнения по документации. Если его нет, периодический догон обязателен.

### 1.2. Связь «репозиторий → трекер» (1 день)

Сейчас ключ задачи ищется глобально; при неоднозначности MR **не связывается** (fail-closed) — правильно, но задачные рёбра теряются. Продукт заявлен многотрекерным.

Минимально: `Repository.TrackerConnectionId` (nullable). По-хорошему — сущность `TrackerProject`, которую README и так упоминает как отложенную.

### 1.3. Согласовать `VcsService` (0.5 дня)

При оживлении (1.1) он будет противоречить консьюмерам: свой `StateMap`, не знает `ReadyForDeployLabel`, не уважает `IsStatusManual`, не пишет `ClosedAt`. Делать **до** того, как код перестанет быть мёртвым.

## Этап 2. Убрать течи провайдеров (2–3 дня)

Делать **сейчас**, независимо от того, появится ли второй провайдер: это чистая выгода. Подробности — [002 §5](002-provider-independence.md#5-рекомендация).

1. **Креды и `orgId` — из сигнатур портов** в фабрику и типизированные опции адаптера (0.5 дня).

Внимание: это **отмена моего собственного решения** — я свёл дублирующиеся правила в Core, что убрало расхождение, но поместило диалект GitLab в домен. Дедупликация верна, дом — нет.
3. **Version-детект при инициализации провайдера** (0.5 дня). Нужен уже сейчас, с одним GitLab: self-hosted версии разные, и Renovate — доказательство, что без этого не живут.
4. **`VcsType`/`TrackerType` → строка** (0.5 дня). Добавление провайдера перестаёт быть изменением домена и миграцией.

## Этап 3. Эксплуатируемость (3–5 дней)

Без этого систему нельзя вести в проде.

1. **CI/CD** (1–2 дня). Сейчас нет ничего: ни пайплайна, ни автосборки, ни прогона тестов. README обещает GitLab CI / GitHub Actions. Минимум: build + test + образы. Здесь же — скан уязвимостей (этап 0.5).
2. **Метрики и трейсинг** (1–2 дня). README обещает Prometheus + Grafana — нет ни пакета, ни `/metrics`. Для асинхронного пути Ingress → RabbitMQ → Core отсутствие трейсинга означает, что потерянное сообщение искать нечем, кроме текстовых логов. OpenTelemetry закрывает и то, и другое.
3. **TLS** (0.5 дня). Реверс-прокси в compose нет; приложение к нему готово (`UseForwardedHeaders`, HSTS), но пока прокси не поставлен, **Bearer-токены и секреты вебхуков идут по открытому HTTP**.
4. **Ключи DataProtection** (0.5 дня). Лежат в той же БД, что и зашифрованные ими токены GitLab/Трекера. В такой модели шифрование не даёт ничего: кто получил дамп БД, получил и шифротекст, и ключи. Нужен `ProtectKeysWithCertificate` или внешнее хранилище.
5. **Leader election для архивации** (0.5 дня). Сервис поднимается в каждой реплике. Корректность выживает (идемпотентная вставка + retry), но будут дедлоки и лишняя работа. Redis уже в стеке.
6. **Буферизация в Ingress** (0.5 дня). README §3.1 обещает 503 при недоступности RabbitMQ; сейчас исключение уходит как 500, а GitLab на 500 обычно не ретраит → **событие теряется**.

## Этап 5. Второй провайдер (оценка после этапа 2)

**Не начинать раньше, чем он реально понадобится.** [002 §6](002-provider-independence.md#6-границы-применимости): до второго провайдера любые догадки о «правильной» границе абстракции — спекуляция. Renovate и Atlantis пришли к своим интерфейсам итеративно.

Когда понадобится — порядок из [002 §5.3–5.5](002-provider-independence.md#53-выбор-провайдера-keyed-services--фабрика): keyed services + фабрика, capabilities, нормализованный конверт события в Ingress.

Ожидаемо дешёвый первый кандидат — **Jira**: её модель связей (`inward`/`outward`) изоморфна модели Яндекс.Трекера, адаптер будет почти зеркальным.

## Долги, которые стоит помнить

| Долг | Почему не сделано |
|---|---|
| Пустая миграция `Phase2_AddIndexes` | Удаление применённой миграции ломает существующие БД. Реальные индексы добавляет `Phase3` |
| `AppDbContext : IdentityDbContext` | Создаёт 7 таблиц ASP.NET Identity, при том что аутентификация через AD и `UserManager`/`SignInManager` не используются. Убирается миграцией, но это отдельная задача |
| Нет уникальных индексов на `(AdGroupSid, PermissionClaimId)` и `(UserId, PermissionClaimId)` | Проверка дублей прикладная, от гонки не защищает |
| `Authorization:BootstrapAdminObjectIds` | Временная мера. Убрать, когда права выданы нормальным способом |
| Тесты не покрывают контроллеры, консьюмеры, архивацию, PWA | Покрыто то, где цена ошибки максимальна. Архивация удаляет данные — её стоит покрыть следующей |
| `docker compose` не запускался | См. этап 0 |
