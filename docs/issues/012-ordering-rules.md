# 012 — Язык правил порядка выкатки (YAML)

Статус: реализовано, 2026-08-02 — язык, разбор YAML, валидация и применение в планировщике.

[006](006-per-task-planning.md), которая задала правило только «репозиторий после репозитория».

## Задача

Сейчас настраиваемое правило порядка ровно одно — `RepositoryDependency` (репозиторий A катится
после репозитория B, hard/soft). Всё остальное либо выведено из трекера (связи и иерархия задач),
либо правится вручную на конкретном плане. Нужен общий декларативный язык: порядок между задачами,
коннекторами, репозиториями и их группами, с гибкостью уровня GitHub Actions, в YAML, версионируемый
и без обязательного UI.

## Что из GitHub Actions переносится, а что нет

Переносится:

- **Явный DAG через `needs:`** вместо неявного порядка объявления. Читается локально: у каждой
  единицы написано, чего она ждёт;
- **Одна версионируемая декларация**, которую можно ревьюить и откатывать;
- **Условия** — «это правило действует только когда …».

**Не переносится главное: `jobs` в Actions пишутся руками.** Здесь единицы работы не пишутся, а
**обнаруживаются** — задачи приходят из трекера, MR и ветки из VCS, и их состав меняется на каждом
событии приёма. Перечислить их в файле нельзя: файл устареет к следующему вебхуку.

Отсюда центральное решение: **правило описывает не единицы, а селекторы над обнаруженной работой** —
и порядок задаётся между группами, которые эти селекторы задают.

## Форма

```yaml
version: 1

# Группы: именованные селекторы над тем, что нашли коннекторы.
# Пустая группа — не ошибка сама по себе (репозиторий может ещё не иметь работы),
# но правило, где ВСЕ группы пусты, репортится: см. «Молчание запрещено».
groups:
  db:
    repositories: ["group/svc-db", "group/*-migrations"]

  backend:
    repositories: ["group/svc-*"]
    exclude:
      repositories: ["group/svc-db"]     # иначе db попал бы в обе группы

  frontend:
    connectors: ["gitlab-main"]          # селектор по коннектору
    repositories: ["group/web"]

  hotfix:
    branches: ["hotfix/*"]               # селектор по имени ветки
    tasks: { labels: ["urgent"] }        # и по признакам задачи

# Порядок между группами. Разворачивается в рёбра между MR, которые группы отобрали.
order:
  - group: backend
    needs: [db]
    type: hard        # hard | soft — кто уступает при цикле

  - group: frontend
    needs: [backend]
    type: soft

# Политика ожидания задач — то, что сейчас лежит в PlanningSettings и на TaskItem.
tasks:
  wait_for_subtasks: true
  wait_for_linked: true
  group_order: together      # together | subtasks_first | linked_first

  # Точечные переопределения, тем же селекторным языком.
  overrides:
    - match: { tasks: { keys: ["INFRA-*"] } }
      wait_for_subtasks: false
```

### Селекторы

Одна ось — один ключ, все перечисленные оси соединяются по И, внутри оси значения по ИЛИ:

| Ось | Матчит | Форма |
|---|---|---|
| `connectors` | имя VCS-подключения | точное имя или glob |
| `repositories` | `ExternalId` репозитория (`group/project`) | glob |
| `branches` | имя ветки (у MR — исходной) | glob |
| `tasks.keys` | ключ задачи | glob |
| `tasks.labels` | лейблы MR | точное значение |
| `exclude` | вложенный селектор, вычитается | те же оси |

Glob, а не регулярка: `group/svc-*` читается всеми, а регулярку в конфиге порядка выкатки никто не
хочет отлаживать. Ключ задачи и так извлекается настраиваемой регуляркой — там она оправдана, здесь
нет.

## Как это входит в существующий граф

**Это не второй движок.** Правило компилируется в то, что уже умеет чистый `ReleasePlanGraph`:

```
YAML → селекторы → множества MR → рёбра (from, to, kind) → addEdges/removeEdges → ReleasePlanGraph.Build
```

Причина не стилистическая. [006](006-per-task-planning.md) §7 объявляет это центральным инвариантом:
**импорт, правка в UI и пересчёт обязаны проходить одной деривацией**, иначе YAML и UI молча
разойдутся в том, что считается ребром. Если у языка правил появится своя топосортировка, оператор
увидит в предпросмотре один порядок, а получит другой. Инвариант держится тестом, который гоняет один
сценарий через все три входа и требует идентичного `PlanGraphResult`.

Конкретно:

- `order[].needs` с `type: hard` → `PlanEdgeKind.RepoHard`, `soft` → `RepoSoft`. Никаких новых видов
  рёбер: приоритет сброса при цикле уже определён и протестирован;
- `tasks.*` → `TaskWaitPolicy` (уже есть, [011](011-release-audit.md) §1.6 контекст) — это вход
  планировщика, не ребро;
- `groups` сами по себе ничего не добавляют в замыкание. Замыкание по-прежнему определяется **только**
  связями задач: порядок репозиториев не должен затягивать в план задачу, которой там иначе не было бы
  (006 §4). Группа лишь отбирает среди того, что уже в замыкании.

Развёртка `needs` — декартово произведение: каждый MR группы-ожидающей получает ребро от каждого MR
группы-предшественника. На больших группах это квадратично; см. «Открытые вопросы».

## Молчание запрещено

Правило, которое ничего не отобрало, — это правило, которое не работает, и узнать об этом на выкатке
дороже, чем при сохранении. Поэтому:

- селектор, не совпавший **ни с чем существующим** (несуществующий коннектор, glob репозитория без
  единого совпадения в конфигурации) — **ошибка валидации** со списком допустимых значений, как
  `UnknownProviderException` в [005](005-extension-model.md);
- группа, пустая **в конкретном плане** (репозиторий есть, работы по нему в этой задаче нет) — не
  ошибка: это нормальное состояние. Но `needs` на пустую группу не создаёт рёбер, и это отражается в
  предпросмотре, а не проглатывается;
- цикл между группами разрывается существующим механизмом и попадает в `ConflictsJson` — план может
  нарушить ограничение, но никогда молча (001, «never a silent plan»).

## Где живёт

Отдельный документ, а не поле в плане: план под задачу — это **проекция**, он пересобирается на каждом
событии приёма. Правило — **вход** планировщика и обязано это пересоздание переживать. Та же причина,
по которой `TaskWaitPolicy` и `PlanOverride` лежат не на `RolloutPlan` (переключение `PlanOverride` с
плана на задачу описано в [011](011-release-audit.md)).

Хранение: одна строка с текстом YAML + распарсенная проекция в таблицы (в первую очередь существующий
`RepositoryDependency`, чтобы админка и YAML правили одно и то же). Импорт замещает набор целиком —
диффу здесь взяться неоткуда, а частичное применение оставит порядок в состоянии, которого никто не
писал.

Эндпоинты — по образцу 006 §6.2: `export` / `validate` / `import?force=`, где `validate` прогоняет
**ту же** деривацию и ничего не сохраняет.

## Разобранный пример

Расстановка, на которой видно, что делает YAML, а что происходит и без него.

```
task-1                        зонтик, своего кода нет
├── task-2  (подзадача)       group/svc-db      (gitlab-main)
│                             partner/web       (gitlab-partner)
│   └── ждёт task-4 (связь)   group/svc-auth    (gitlab-main)
└── task-3  (подзадача)       group/svc-api     (gitlab-main)
                              partner/reports   (gitlab-partner)

task-2 и task-3 между собой не связаны — только общий родитель.
```

**Дерево строится без единой строки YAML.** Иерархия (`task-1` ← `task-2`, `task-3`) и связь
(`task-2` ← `task-4`) приходят из трекера; замыкание и рёбра между MR выводятся из них. YAML нужен
ровно для одного: **порядка между репозиториями**, которого трекер не знает.

```yaml
version: 1

tasks:
  wait_for_subtasks: true      # родитель ждёт подзадачи — иначе task-1 выкатится первым
  wait_for_linked: true        # task-2 ждёт task-4
  group_order: together        # подзадачи и связанные не упорядочены между собой

groups:
  backend-main:
    connectors: ["gitlab-main"]
    repositories: ["group/svc-db", "group/svc-api"]
  frontend-partner:
    connectors: ["gitlab-partner"]
    repositories: ["partner/*"]

order:
  - group: frontend-partner
    needs: [backend-main]
    type: hard
    scope: within_task         # см. ниже — иначе task-2 и task-3 склеятся
```

Что получится для выкатки `task-1`:

| Волна | Что катится | Почему |
|---|---|---|
| 1 | `svc-auth` (task-4), `svc-api` (task-3) | ничего не ждут |
| 2 | `svc-db` (task-2), `partner/reports` (task-3) | `svc-db` ждёт task-4; `reports` ждёт `svc-api` по правилу |
| 3 | `partner/web` (task-2) | ждёт task-4 и `svc-db` по правилу |

`task-1` своих MR не имеет, поэтому в волнах не появляется — он узел дерева, а не шаг выкатки. Это
нормальный случай для зонтичной задачи, и его стоит видеть в UI как узел без элементов.

### Почему здесь понадобился `scope`

Правило порядка репозиториев в текущей модели **глобально**: оно применяется ко всему плану, в том
числе между задачами, которые ничем не связаны (006 §4 прямо это фиксирует). Без `scope` строка
«partner после gitlab-main» дала бы ребро `svc-db` (task-2) → `partner/reports` (task-3) — и две
заведомо независимые задачи выстроились бы в цепочку. План остался бы корректным, но потерял бы
параллельность, которой оператор вправе ожидать: он же сказал, что задачи не связаны.

Поэтому у `order[]` нужен `scope`:

| Значение | Рёбра строятся |
|---|---|
| `within_task` | только между MR одной задачи |
| `across_plan` | между любыми MR плана — сегодняшнее поведение `RepositoryDependency` |

Умолчание — `across_plan`, чтобы существующие правила не поменяли смысл молча. Но для расстановки
выше правильный ответ `within_task`, и без него ту же расстановку пришлось бы выписывать
перечислением конкретных пар репозиториев, что не масштабируется.

## Открытые вопросы

1. **Порядок под окружение.** 006 §4.1 фиксирует: план env-agnostic, окружение выбирается на запуске.
   Запрос «для теста один шаг пайплайна, для прода другой» это **не** нарушает — там речь о готовности,
   а она уже per-environment. Но если понадобится именно **порядок**, разный по окружениям, инвариант
   придётся снимать осознанно, и это отдельное решение, а не строчка в схеме.

2. **Стоимость декартова произведения.** Группа из 50 MR, ждущая группу из 50, — это 2500 рёбер на
   одну строку `needs`. Сейчас графы маленькие, но язык позволяет написать такое. Варианты: узел-
   синхронизатор на группу (меняет форму графа) либо кап с явной ошибкой. Ограничение честнее.

3. **Приоритет YAML против админки.** Оба правят `RepositoryDependency`. Нужно решить: YAML — источник
   истины (админка read-only при наличии файла), либо последняя запись побеждает. Второе воспроизводит
   ровно тот класс расхождения, который весь этот документ старается исключить.

4. **`if:` из Actions.** Условия вида «правило действует, только когда MR несёт лейбл» — это уже
   селектор `tasks.labels`. Полноценные выражения (`if: ${{ ... }}`) добавлять не стоит, пока не
   появится случай, который селекторами не выражается: язык выражений в конфиге порядка выкатки
   отлаживать нечем.

5. **Совместимость с планом под задачу.** У 006 §6 своя YAML-схема — это **экземпляр** плана
   (конкретный PROJ-42), здесь — **правило**, порождающее планы. Две схемы, разные файлы, разные
   эндпоинты. Стоит проверить, что имена ключей не наводят на мысль о взаимозаменяемости.
