# 001. Текущее состояние

## 1. Что это за продукт

Release Orchestrator превращает набор merge request'ов в упорядоченный по стадиям план выкатки. Порядок диктуется из двух независимых источников:

- **зависимости задач** из трекера (TASK-2 зависит от TASK-1 → MR по TASK-1 катится раньше);
- **зависимости стеков** — репозитории объединены в «стеки», между стеками заданы Hard/Soft-связи (БД → бэкенд → фронт).

Из рёбер строится граф, топологическая сортировка Кана раскладывает его на **стадии**: стадия — набор MR, которые можно катить параллельно. Плюс ручное редактирование плана, YAML-импорт/экспорт, права через AD и архивация закрытых задач через 90 дней.

Ядро продукта — это «вход + рёбра + топосортировка». Всё остальное обслуживает эти три вещи. Именно поэтому дефекты в них были фатальны, а дефекты в архивации — нет.

## 2. Что исправлено

Сборка: **0 ошибок, 0 предупреждений**. Тесты: **64 зелёных** (`tests/ReleaseOrchestrator.UnitTests`). Их не было вообще.

### 2.1. Ядро плана (`1b22f9f`)

| Дефект | Суть |
|---|---|
| Рёбра вырождались в петли | `TaskDependency` смаплен так, что `task.Dependencies` возвращал строки, где задача — **предшественник**, а не зависимый. В планировщике `dep.DependsOnTaskId` тождественно равнялся `mr.Task.Id` → ребро MR→сам-себе → `inDegree` не обнулялся → MR уходил в «остаток». **Порядок инвертировался ровно в целевом сценарии.** |
| Циклы рушили downstream | Цикл и **всё достижимое из него** сваливалось в одну финальную стадию молча. Теперь ребро цикла отбрасывается по приоритету (Soft → задачные → Hard), каждый отброс сохраняется в `ReleasePlan.ConflictsJson` и показывается оператору. |
| Soft-связи игнорировались | `.Where(d => d.Type == Hard)` — Soft не влияли ни на что. Теперь соблюдаются, когда не мешают, и отбрасываются первыми при конфликте (README §5.2). |
| Задача с несколькими MR | `FirstOrDefault(m => m.TaskId == ...)` брал один MR предшественника из нескольких. Остальные не упорядочивались. |
| Петли от стеков | Репозиторий в двух взаимозависимых стеках давал ребро сам-в-себя. |
| Недетерминированность | Запрос без `OrderBy` → два прогона на одних данных давали разные планы → diff «авто vs ручной» бессмыслен. |
| Ложная атомарность | Комментарий обещал «atomic swap», но `ExecuteUpdateAsync` и `SaveChangesAsync` шли двумя транзакциями. Падение между ними оставляло **ноль** активных планов. |
| Два активных плана | Импорт деактивировал все планы, пересчёт — только автоматические. Итог: два `IsActive=true`, `GetActiveAsync` возвращал произвольный. Теперь инвариант держит фильтрованный уникальный индекс. |

Алгоритм вынесен в `Application/ReleasePlanning/ReleasePlanGraph` — чистый класс без EF (README §3.2 всегда этого требовал). Раньше он был `private static` внутри класса, завязанного на `AppDbContext`, — **недостижим для теста, и это прямая причина, почему дефекты дожили до аудита**.

> Проверено: тест на маппинг EF краснеет на исходной (перепутанной) привязке навигаций. Тест, который не падает на баге, бесполезен.

### 2.2. Вход планировщика (`5d110d7`)

`ReadyForDeploy` был единственным фильтром входа — и **не выставлялся ничем**: встречался только в объявлении enum, в фильтре и в CSS-классе. Автоплан всегда был пуст.

Реализованы оба заявленных способа: лейбл VCS (`VcsConnection.ReadyForDeployLabel`) и `PATCH /api/merge-requests/{id}/status` под `release.plan.approve` с пометкой `IsStatusManual`, которую вебхук не перезатирает.

Там же:
- **Дебаунсер заменён** на коалесинг в консьюмере. Он подтверждал сообщение и оставлял работу в 15-секундном in-memory таймере: рестарт пода терял пересчёт, а каждая реплика вела свой таймер. Теперь работа выполняется **до** подтверждения, а `ReleasePlan.SnapshotStartedAt` делает лишние запросы дешёвыми.
- **Дублирующиеся правила сведены в один источник:** `BranchTaskParser` (одна копия не понимала `S3-42`, другая — `X-1`) и `TaskStatusRules` (только один список знал `resolved` → такие задачи считались закрытыми для пересчёта, но не получали `ClosedAt` и не архивировались никогда).
- `MergeRequest.ClosedAt` добавлен: архивация фильтровала по `MergedAt < cutoff`, а у закрытых MR это `NULL`, и `NULL < cutoff` = `UNKNOWN` → закрытые MR не архивировались **никогда**.

### 2.4. Архивация (`cb9864c`)

**Не завершалась ни разу.** Удаление задачи упиралось в FK `TaskDependencies` (`Restrict`), исключение ловил единственный `try/catch` вокруг всего цикла, и тот же пакет падал каждую ночь. MR были намертво прибиты `StageItems` исторических планов, которые никто не удалял.

Теперь: рёбра удаляются явно (Cascade на оба FK в одну таблицу SQL Server запрещает), старые планы архивируются и удаляются первыми, вставка в архив идемпотентна (архив и оперативная БД — разные базы, общей транзакции нет), ретраи на пакет, порядок фаз планы → MR → задачи.

`ArchivedReleasePlan` наконец пишется — README §8.2 обещал это с самого начала.

### 2.5. Найдено сверх исходного аудита

Три дефекта, которых не заметил ни один из четырёх аудиторов:

1. **`DataProtectionKeys` не создавала ни одна миграция.** `AppDbContext` объявляет `DbSet<DataProtectionKey>`, но таблицы нет ни в `InitialCreate`, ни в снапшоте. На свежей БД первое же `protector.Protect()` — сохранение любого VCS-подключения — упало бы на «Invalid object name». Всплыло при генерации миграции.
2. **Полная блокировка свежей установки.** `PermissionClaims` не наполнялась ничем, а `config.edit` невозможно выдать без `config.edit`. Раньше это блокировало только админку; после применения `release.plan.view` к чтениям — **всё приложение**. Это ухудшение внесено в ходе правок и исправлено сидингом + `Authorization:BootstrapAdminObjectIds` (README §7.4).
3. **Проверки конфигурации только выглядели как fail-fast.** Redis и RabbitMQ проверялись внутри ленивых лямбд → срабатывали при первом запросе и при старте шины, а не на старте приложения. Нашёл DI-тест.
4. **Защиту жёстких связей обходил drag-and-drop.** Импорт YAML отвергал план, нарушающий жёсткую связь стеков, а `MoveItem`/`AddItem`/`ReorderStages` принимали то же самое молча — и возвращали план с `Conflicts = 0`, то есть объявляли его чистым. Проверка, мимо которой не проходил импорт, была в одном перетаскивании. Нашлось при попытке покрыть ручное редактирование тестами.

### 2.6. Правило: план может нарушать связь, но не может это скрывать

Дыру из п. 4 можно было закрыть с двух сторон, и выбрана не та, что очевиднее. Запрещать правку симметрично импорту — значит закрыть законный аварийный сценарий: иногда выкатиться нужно вопреки объявленному порядку, и у этих эндпоинтов нет даже `force`.

Поэтому **оба** пути теперь принимают правку и пересчитывают конфликты, записывая нарушение на план. Импорт больше не отвергает — он записывает. `force` сузился до своего единственного честного смысла: пропускать неизвестные `mr_id`, а не отключать проверки.

Обоснование: `PlanConflict` уже означал «ограничение, которое план не соблюдает» — `RecalculateAsync` с самого начала записывал конфликты, а не падал. Отвергающий импорт был единственным местом, выпадавшим из этой модели. Теперь правило одно и общее: **выкатывать вопреки правилам можно, врать о том, что правила соблюдены, — нельзя.**

Все три пути (пересчёт, импорт, ручная правка) считают нарушения через `ReleasePlanGraph.ViolatedBy` — тот же вывод рёбер, что и у планировщика, чтобы они не разошлись в понимании того, что такое ограничение. Мягкие связи исключены: планировщик сам их роняет ради разрыва цикла, и отмечать оператора за то же решение — значит приучить его не читать список.

## 3. Что осталось сломано

### 3.1. ~~Зависимости задач не загружаются никогда~~ — ИСПРАВЛЕНО

Было **critical**: `TaskDependency` создавался ровно в одном месте — `TrackerService.SyncTaskAsync` — и этот метод не вызывался ниоткуда. `IVcsService`/`ITrackerService` были зарегистрированы в DI и не инжектились никуда. Таблица `TaskDependencies` всегда оставалась пустой → задачных рёбер не существовало → план строился только по стекам. Починка инвертированной навигации была необходима, но недостаточна: данные не приходили.

Что сделано:

- **`TaskSyncRequested` + `TaskSyncConsumer`** — синхронизация идёт через шину, поэтому переживает рестарт и ретраится при недоступности трекера. Раньше её не было вовсе.
- **Триггеры:** создание задачи, смена статуса, и появление MR со ссылкой на неизвестную задачу. Вебхук не несёт связей, а трекеры не шлют событие при их изменении — поэтому связи приходится вытягивать.
- **Периодическая сверка** (`TaskReconciliationService`, по умолчанию раз в 30 минут для открытых задач) — событий на изменение связей нет, без сверки граф отставал бы молча.
- **Неизвестная задача-предшественник больше не теряется.** Было `if (depTask is null) continue;` — ребро исчезало навсегда, потому что к зависимой задаче никто не возвращался. Теперь предшественник подтягивается из трекера (поверхностно, без рекурсии — одна доп. операция на ребро).
- **Порядок событий больше не важен.** `MergeRequest.TaskExternalId` хранит ключ из ветки независимо от того, существует ли задача; когда задача приезжает, ожидающие MR связываются с ней. Раньше MR, пришедший раньше своей задачи, оставался несвязанным навсегда.
- **Диффом вместо «удалить всё и вставить заново»** — иначе сбой между шагами оставлял задачу вообще без зависимостей.

> Против живого Трекера не запускалось. Но путь с БД **теперь покрыт**: переход на .NET 10 свёл версии EF и SQLite, и офлайновые тесты с базой стали возможны. `TrackerService` покрыт 11 тестами — он производит все рёбра задач, и за всю жизнь проекта его не вызывал никто. Проверено мутацией: если вернуть исходный пропуск неизвестного предшественника, падают пять из одиннадцати.

### 3.2. ~~Нет связи «репозиторий → трекер»~~ — ИСПРАВЛЕНО

Добавлено `Repository.TrackerConnectionId` (nullable): поиск ключа задачи ограничивается трекером репозитория. Null сохраняет прежний глобальный поиск — это нормально для одного трекера. При неоднозначности MR по-прежнему не связывается (fail-closed): промах стоит порядка, ошибка — портит его.

Полноценная сущность `TrackerProject` из README всё ещё не сделана — текущее решение проще и закрывает практическую потребность.

### 3.3. ~~`VcsService` не согласован~~ — ИСПРАВЛЕНО

Убран собственный `StateMap`, добавлены `MergeRequestStatusResolver`, `IsStatusManual`, `ClosedAt`, `TaskExternalId`.

Одна честная оговорка: API VCS не возвращает лейблы, поэтому label-driven promotion в этом пути не пересчитывается. Сервис намеренно **не понижает** статус `ReadyForDeploy` — promotion принадлежит вебхуку, и сверка не должна молча выкидывать MR из плана.

### 3.4. ~~Известная уязвимость в зависимости~~ — ЗАКРЫТА переходом на .NET 10

`System.Security.Cryptography.Xml` 9.0.5 нёс две уязвимости высокой серьёзности ([GHSA-37gx-xxp4-5rgx](https://github.com/advisories/GHSA-37gx-xxp4-5rgx), [GHSA-w3x6-4m5h-cxqf](https://github.com/advisories/GHSA-w3x6-4m5h-cxqf)) и приходил транзитивно через DataProtection — который шифрует токены GitLab и Трекера. На .NET 9 фикс был недостижим: он требовал пакета, отсутствующего в кэше при заблокированном nuget.org.

Переход на .NET 10 закрыл её: DataProtection 10.0.10 разрешает уже исправленную версию.

Всплыла и была закрыта следующая: `Microsoft.OpenApi` 2.0.0 ([GHSA-v5pm-xwqc-g5wc](https://github.com/advisories/GHSA-v5pm-xwqc-g5wc), high) — приходит транзитивно через `Microsoft.AspNetCore.OpenApi`, закреплена на 2.7.5.

Побочная находка, которая важнее обеих: **уязвимости не были видны**. SDK 9 по умолчанию аудирует только прямые зависимости, и транзитивные молчали. В `Directory.Build.props` включён `NuGetAuditMode=all`. NU1902/NU1903 оставлены предупреждениями, а не ошибками, потому что фикс из этой среды достижим не всегда (прокси); **в CI они обязаны валить сборку**.

### 3.5. Что осталось от .NET 10

Переход выполнен: все 8 проектов на `net10.0`, SDK 10.0.300, пакеты 10.0.10, образы `sdk:10.0.300` / `aspnet:10.0.8`. Сборка 0/0, 201 тест зелёный.

Побочный выигрыш оказался крупнее самого перехода: версии EF и SQLite сошлись, и **тесты с БД стали возможны офлайн**. Ограничение, из-за которого ядро и блокер не были покрыты ничем, снято не обходным путём, а исчезновением причины.

Попутно исправлены устаревшие в .NET 10 API: `ForwardedHeadersOptions.KnownNetworks` → `KnownIPNetworks` (ASPDEPR005) и `WithOpenApi()` (ASPDEPR002, удалён). Убран `Microsoft.Extensions.Logging.Configuration` — на .NET 10 он в shared framework, и NuGet справедливо ругался на лишнюю ссылку (NU1510).

> Теги образов **не проверены**: реестр из этой среды фильтруется. Версии выбраны не наугад — SDK 10.0.300 и рантайм 10.0.8 установлены локально, значит выпущены.
