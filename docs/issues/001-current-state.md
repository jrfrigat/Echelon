# 001. Текущее состояние

## 1. Что это за продукт

Release Orchestrator превращает набор merge request'ов в упорядоченный по стадиям план выкатки. Порядок диктуется из двух независимых источников:

- **зависимости задач** из трекера (TASK-2 зависит от TASK-1 → MR по TASK-1 катится раньше);
- **зависимости стеков** — репозитории объединены в «стеки», между стеками заданы Hard/Soft-связи (БД → бэкенд → фронт).

Из рёбер строится граф, топологическая сортировка Кана раскладывает его на **стадии**: стадия — набор MR, которые можно катить параллельно. Плюс ручное редактирование плана, YAML-импорт/экспорт, права через AD и архивация закрытых задач через 90 дней.

Ядро продукта — это «вход + рёбра + топосортировка». Всё остальное обслуживает эти три вещи. Именно поэтому дефекты в них были фатальны, а дефекты в архивации — нет.

## 2. Что исправлено

Сборка: **0 ошибок, 0 предупреждений**. Тесты: **64 зелёных** (`tests/ReleaseOrchestrator.UnitTests`). Их не было вообще.

### 2.1. Ядро плана (`1b22f9f`)

| Дефект | Суть |
|---|---|
| Рёбра вырождались в петли | `TaskDependency` смаплен так, что `task.Dependencies` возвращал строки, где задача — **предшественник**, а не зависимый. В планировщике `dep.DependsOnTaskId` тождественно равнялся `mr.Task.Id` → ребро MR→сам-себе → `inDegree` не обнулялся → MR уходил в «остаток». **Порядок инвертировался ровно в целевом сценарии.** |
| Циклы рушили downstream | Цикл и **всё достижимое из него** сваливалось в одну финальную стадию молча. Теперь ребро цикла отбрасывается по приоритету (Soft → задачные → Hard), каждый отброс сохраняется в `ReleasePlan.ConflictsJson` и показывается оператору. |
| Soft-связи игнорировались | `.Where(d => d.Type == Hard)` — Soft не влияли ни на что. Теперь соблюдаются, когда не мешают, и отбрасываются первыми при конфликте (README §5.2). |
| Задача с несколькими MR | `FirstOrDefault(m => m.TaskId == ...)` брал один MR предшественника из нескольких. Остальные не упорядочивались. |
| Петли от стеков | Репозиторий в двух взаимозависимых стеках давал ребро сам-в-себя. |
| Недетерминированность | Запрос без `OrderBy` → два прогона на одних данных давали разные планы → diff «авто vs ручной» бессмыслен. |
| Ложная атомарность | Комментарий обещал «atomic swap», но `ExecuteUpdateAsync` и `SaveChangesAsync` шли двумя транзакциями. Падение между ними оставляло **ноль** активных планов. |
| Два активных плана | Импорт деактивировал все планы, пересчёт — только автоматические. Итог: два `IsActive=true`, `GetActiveAsync` возвращал произвольный. Теперь инвариант держит фильтрованный уникальный индекс. |

Алгоритм вынесен в `Application/ReleasePlanning/ReleasePlanGraph` — чистый класс без EF (README §3.2 всегда этого требовал). Раньше он был `private static` внутри класса, завязанного на `AppDbContext`, — **недостижим для теста, и это прямая причина, почему дефекты дожили до аудита**.

> Проверено: тест на маппинг EF краснеет на исходной (перепутанной) привязке навигаций. Тест, который не падает на баге, бесполезен.

### 2.2. Вход планировщика (`5d110d7`)

`ReadyForDeploy` был единственным фильтром входа — и **не выставлялся ничем**: встречался только в объявлении enum, в фильтре и в CSS-классе. Автоплан всегда был пуст.

Реализованы оба заявленных способа: лейбл VCS (`VcsConnection.ReadyForDeployLabel`) и `PATCH /api/merge-requests/{id}/status` под `release.plan.approve` с пометкой `IsStatusManual`, которую вебхук не перезатирает.

Там же:
- **Дебаунсер заменён** на коалесинг в консьюмере. Он подтверждал сообщение и оставлял работу в 15-секундном in-memory таймере: рестарт пода терял пересчёт, а каждая реплика вела свой таймер. Теперь работа выполняется **до** подтверждения, а `ReleasePlan.SnapshotStartedAt` делает лишние запросы дешёвыми.
- **Дублирующиеся правила сведены в один источник:** `BranchTaskParser` (одна копия не понимала `S3-42`, другая — `X-1`) и `TaskStatusRules` (только один список знал `resolved` → такие задачи считались закрытыми для пересчёта, но не получали `ClosedAt` и не архивировались никогда).
- `MergeRequest.ClosedAt` добавлен: архивация фильтровала по `MergedAt < cutoff`, а у закрытых MR это `NULL`, и `NULL < cutoff` = `UNKNOWN` → закрытые MR не архивировались **никогда**.

### 2.3. Безопасность (`5d110d7`, `cb9864c`, `35f465a`)

| Дефект | Severity |

Добавлены: заголовки безопасности, rate limiting на обоих хостах, `UseForwardedHeaders` (без него HTTPS-редирект и HSTS за прокси не работают), `oid` как единый идентификатор пользователя, аудит изменений прав, отзыв персональных прав (его не было — только правка БД).

### 2.4. Архивация (`cb9864c`)

**Не завершалась ни разу.** Удаление задачи упиралось в FK `TaskDependencies` (`Restrict`), исключение ловил единственный `try/catch` вокруг всего цикла, и тот же пакет падал каждую ночь. MR были намертво прибиты `StageItems` исторических планов, которые никто не удалял.

Теперь: рёбра удаляются явно (Cascade на оба FK в одну таблицу SQL Server запрещает), старые планы архивируются и удаляются первыми, вставка в архив идемпотентна (архив и оперативная БД — разные базы, общей транзакции нет), ретраи на пакет, порядок фаз планы → MR → задачи.

`ArchivedReleasePlan` наконец пишется — README §8.2 обещал это с самого начала.

### 2.5. Найдено сверх исходного аудита

Три дефекта, которых не заметил ни один из четырёх аудиторов:

1. **`DataProtectionKeys` не создавала ни одна миграция.** `AppDbContext` объявляет `DbSet<DataProtectionKey>`, но таблицы нет ни в `InitialCreate`, ни в снапшоте. На свежей БД первое же `protector.Protect()` — сохранение любого VCS-подключения — упало бы на «Invalid object name». Всплыло при генерации миграции.
2. **Полная блокировка свежей установки.** `PermissionClaims` не наполнялась ничем, а `config.edit` невозможно выдать без `config.edit`. Раньше это блокировало только админку; после применения `release.plan.view` к чтениям — **всё приложение**. Это ухудшение внесено в ходе правок и исправлено сидингом + `Authorization:BootstrapAdminObjectIds` (README §7.4).
3. **Проверки конфигурации только выглядели как fail-fast.** Redis и RabbitMQ проверялись внутри ленивых лямбд → срабатывали при первом запросе и при старте шины, а не на старте приложения. Нашёл DI-тест.

## 3. Что осталось сломано

### 3.1. Зависимости задач не загружаются никогда

**Severity: critical. Продукт не выполняет свою функцию.**

`TaskDependency` создаётся ровно в одном месте — `TrackerService.SyncTaskAsync` ([TrackerService.cs:62](../../src/ReleaseOrchestrator.Infrastructure/Tracker/TrackerService.cs)). Этот метод **не вызывается ниоткуда**:

```
$ grep -rn "SyncTaskAsync|SyncMergeRequestAsync" src --include=*.cs
Application/Services/ITrackerService.cs:5:    Task SyncTaskAsync(...);          # объявление
Application/Services/IVcsService.cs:7:     Task SyncMergeRequestAsync(...);    # объявление
Infrastructure/Tracker/TrackerService.cs:13: public async Task SyncTaskAsync   # реализация
Infrastructure/Vcs/VcsService.cs:22:         public async Task SyncMergeRequestAsync
```

`IVcsService` и `ITrackerService` зарегистрированы в DI и **не инжектятся никуда**. Задачи создаёт только `TaskCreatedConsumer` из вебхука — а он зависимости не загружает.

**Следствие:** таблица `TaskDependencies` всегда пуста → задачных рёбер в графе нет → план упорядочен **только по стекам**. Починка инвертированной навигации (§2.1) необходима, но недостаточна: данные не приходят.

Требует решения (см. [003 §1](003-roadmap.md)): когда синхронизировать — по `TaskCreated`, по `MrOpened`, по расписанию, или всё вместе.

> Прочитано. Не воспроизведено запуском — нет живого Трекера.

### 3.2. Нет связи «репозиторий → трекер»

Репозитории принадлежат `VcsConnection`, задачи — `TrackerConnection`, связи между ними в модели нет. Ключ задачи из ветки можно искать только глобально. Сейчас при неоднозначности `MrOpenedConsumer` **не связывает** MR с задачей (fail-closed) и пишет warning — это лучше, чем связать с чужой, но продукт заявлен многотрекерным, и в такой конфигурации задачные рёбра просто теряются.

README упоминает отложенную сущность `TrackerProject` — вероятно, она и должна закрывать этот пробел.

### 3.3. `VcsService` не согласован с остальным кодом

`VcsService` держит собственный `StateMap` ([VcsService.cs:15](../../src/ReleaseOrchestrator.Infrastructure/Vcs/VcsService.cs)) вместо `MergeRequestStatusResolver`, не учитывает `ReadyForDeployLabel`, не уважает `IsStatusManual` и не выставляет `ClosedAt`. Сейчас безвредно — код мёртвый (§3.1), но при его оживлении он будет противоречить консьюмерам.
