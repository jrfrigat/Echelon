# 007. Движок выкатки

> Черновик от 2026-07-18. Проектный документ, не отчет о сделанном.

## 0. Что это и чего сегодня нет

Сегодня оркестратор умеет только читать. Все методы провайдеров -- read-only (`GetMergeRequestAsync`, `GetOpenMergeRequestsAsync`, `GetIssueAsync`), действия выкатки нет ни одного. План выкатки существует как порядок, но никто по нему ничего не выкатывает: оператор смотрит на волны и переключает MR руками во внешней системе. Движок выкатки -- ровно та подсистема, которой нет.

Требование к ней жесткое и простое: выкатка должна переживать перезапуск процесса, падение брокера и повторную доставку сообщения, ни разу не выкатив один MR дважды. Отсюда три несущих решения, вокруг которых построен весь документ:

1. **Все состояние -- в БД.** Координатор не держит в памяти ничего, что нельзя пересобрать из строк. Падение и рестарт -- это просто следующее пробуждение.
2. **Корректность держится на атомарной заявке на MR** (single-writer compare-and-set), а не на истечении аренды. Аренда -- про живость, а не про безопасность.
3. **Выкатка forward-only.** Автоматического отката нет; восстановление после частичного сбоя -- fix-forward через retry/skip. Это осознанное ограничение, а не недоделка (см. [004](004-target-architecture.md), реестр рисков).

Планирование (замыкание, дерево, per-task YAML) описано в [006](006-per-task-planning.md); контракт стратегии как одна из четырех осей расширения -- в [005](005-extension-model.md); события и дедуп-inbox, на который опирается идемпотентность, -- в [008](008-ingestion-and-messaging.md). Здесь -- про сам прогон.

## 1. Агрегаты

Выкатка -- отдельный набор сущностей рядом с планом, а не мутация плана. План может быть пересчитан, отредактирован, помечен `Stale` -- уже запущенная выкатка обязана продолжать работать по тому, что было на момент запуска. Поэтому у `Rollout` есть **замороженный снимок** плана, и шаги ссылаются на него, а не на живые `PlanItem`.

| Агрегат | Роль | Ключевые поля |
|---|---|---|
| `Rollout` | Один прогон выкатки одной целевой задачи в одно окружение | `TargetTaskId`, `EnvironmentId`, `RolloutPlanId`, `PlanSnapshotJson` (заморожен при запуске), `Status`, `LaunchedByOid`, `IdempotencyKey` (unique), `StartedAt`/`FinishedAt` (Utc), `RowVersion` |
| `RolloutStep` | Выкатка одного MR в окружение прогона -- пара (MR, окружение); окружение унаследовано от `Rollout` | `RolloutId`, `MergeRequestId`, `TaskId`, `Wave`, `DeployStrategyKey`, `State`, `AttemptCount`, `ExternalRef`, `MergeShaAtSnapshot`, `LastError`, метки Utc, `RowVersion`; unique (`RolloutId`, `MergeRequestId`) |
| `MrDeployClaim` | Атомарный single-writer-замок против двойной выкатки в одном окружении | `MergeRequestId`, `EnvironmentId`, `OwnerRolloutId`, `State`, `ExpiresAt`; PK (`MergeRequestId`, `EnvironmentId`) |
| `RolloutStepAttempt` | Append-only лог попыток шага | `RolloutStepId`, `AttemptNo`, `Outcome`, `Message`, `At` (Utc) |
| `RolloutEvent` | Append-only аудит-таймлайн прогона | `RolloutId`, `Kind`, `PayloadJson`, `At` (Utc) |

`Rollout.Status`: `Pending -> Running -> (Paused) -> Succeeded | Failed | Cancelled` (плюс промежуточный `Cancelling`). `RolloutStep.State` -- отдельная машина: `Pending -> Claimed -> Deploying -> (Awaiting) -> Succeeded | Failed | Skipped`.

**Ground truth выкатки живет на паре (MR, окружение), не на шаге и не на задаче.** В Core остается enum `DeploymentState { NotStarted, Claimed, Deploying, Deployed, Failed, Skipped }` как неизменный тип-значение -- отдельная от `MergeRequestStatus` истина. Меняется его *ключевание*: истина выкатки теперь per (MergeRequest, Environment) и живет в дочерней таблице `MrDeploymentState` с PK (`MergeRequestId`, `EnvironmentId`). Прежнее одностолбцовое состояние на самом `MergeRequest` заменено этим per-env ребенком. `MergeRequestStatus` (Opened..Merged/Closed) остается истиной *ингестии* и не трогается; `DeploymentState` -- истина *оркестратора*, потому что MR -- это единица, которую стратегия реально выкатывает, а окружение -- ортогональное измерение, в которое ее выкатывают. Две истины не смешиваются, и это единственный способ не получить дрейф между "GitLab говорит merged" и "мы это выкатили в prod" (обоснование -- [004](004-target-architecture.md), раздел про две истины). Готовность задачи -- производная и считается **per окружение**: задача Deployed в окружении E, когда все ее выкатываемые MR в `Deployed`/`Skipped` в E; задача без выкатываемых MR удовлетворена в любом окружении автоматически.

Все новые сущности: маппинг атрибутами на модели, `Kind=Utc`, `RowVersion`, зеркальные миграции на MsSql и Postgres. **Осторожно с токеном конкурентности:** каждая новая `RowVersion`-сущность (`Rollout`, `RolloutStep`, `RolloutPlan`, `MrDeployClaim`, `MrDeploymentState`) требует своей отдельной записи в `ProviderSpecificMapping` -- иначе Npgsql молча смапит `[Timestamp]` на `bytea`, который никогда не заполняется, и оптимистичная блокировка на Postgres не сработает вообще. Это не декоративный риск: заявка на MR частично опирается на `RowVersion`, и невидимый на SQLite баг тут ломает именно защиту от двойной выкатки. Переход на per-(MR, окружение) claim и state **удваивает** число таких сущностей, которые нужно изолировать для Postgres, -- тем внимательнее к каждой. Проверяется на живом SQL Server и Postgres, а не на SQLite.

```csharp
// Core/Enums/DeploymentState.cs -- предлагаемая форма
public enum DeploymentState
{
    NotStarted = 0,
    Claimed    = 1,
    Deploying  = 2,
    Deployed   = 3,
    Failed     = 4,
    Skipped    = 5
}
```

```csharp
// Infrastructure/Persistence/Models/MrDeploymentState.cs -- предлагаемая форма
// PK (MergeRequestId, EnvironmentId); своя RowVersion => своя запись в ProviderSpecificMapping.
public sealed class MrDeploymentState
{
    public long            MergeRequestId { get; set; }
    public long            EnvironmentId  { get; set; }
    public DeploymentState State          { get; set; }
    public DateTime        UpdatedAt      { get; set; } // Kind=Utc
    public byte[]          RowVersion     { get; set; } = default!;
}
```

## 2. Поток запуска

Запуск -- `POST /api/tasks/{key}/rollouts`, тело несет **целевое окружение** (ключ окружения, например `staging`/`prod`), новое право `release.execute` (отдельное от `release.plan.view`/`release.plan.approve`). Окружение выбирается на запуске, а не хранится в плане. Вся подготовка -- в одной транзакции, чтобы двойной сабмит не породил два прогона:

1. **Проверка готовности per окружение.** Готовность считается для выбранного окружения E. Если хоть одна задача замыкания цели (кроме самой цели) не `Deployed` **в E** -> `409` со списком блокирующих задач. Плюс опциональный настраиваемый **шлюз прогрессии окружений**: выкатка (T, E) может требовать, чтобы T уже была `Deployed` в окружениях, стоящих в порядке (`Environment.Order`) перед E -- по умолчанию включен, так что prod требует staging; нарушение -> `409`. Оба условия считаются запросом, а не по хранимому флагу; порядок окружений и включенность шлюза -- конфигурация.
2. **Запрет на нарушение обязательного ребра.** Редактирование плана может *записать* план, нарушающий обязательное (task/RepoHard) ребро -- но никогда молча (`ConflictsJson`, инвариант docs/001 s.2.6). Запуск же отказывает любому плану, который сейчас нарушает обязательное ребро. `force` при импорте влияет только на сохранение черновика и **никогда** не разрешает запуск заведомо неверного порядка (см. [006](006-per-task-planning.md)).
3. **Заморозка плана** в `PlanSnapshotJson`.
4. **Присвоение волн (env-agnostic).** `ReleasePlanGraph.TopoSort` прогоняется по множеству MR плана; сам топосорт не знает об окружении -- дерево и порядок одинаковы во всех окружениях, поэтому он прогоняется один раз на прогон, то есть на пару (задача, окружение). Волны -- свойство уровня MR (Kahn level), они кладутся в `RolloutStep.Wave`. Per-task-уровня волн не существует: MR одной задачи законно попадают в разные волны. Task-зависимость их не упорядочивает (у них общая задача); упорядочить их может только политика порядка репозиториев ([006](006-per-task-planning.md)), и тогда они и оказываются в разных волнах.
5. **Материализация строк.** Создаются `Rollout` (с выбранным `EnvironmentId`) + `RolloutStep` (окружение унаследовано от прогона). `DeployStrategyKey` каждого шага = `PlanItem.DeployStrategyKeyOverride ?? Repository.DeployStrategyKey` -- ключ env-независим, окружение есть параметр рантайма. Уникальный `IdempotencyKey` не дает запустить прогон дважды.
6. **Enqueue `RolloutLaunched`** (несет `environmentId`).

### Область прогона

Запуск задачи T в окружение E выкатывает **все ее невыкаченное в E замыкание зависимостей, deps-first, ПЛЮС собственные MR T**. MR, уже выкаченные в E, становятся шагами в состоянии `Skipped` (они попадают в снимок и таймлайн, но внешний вызов не делается). Это единственная связная семантика замыкания: при успехе каждого шага флипается `MrDeploymentState` соответствующей пары (MR, E), и когда все выкатываемые MR *любой* задачи замыкания достигают `Deployed` в E, эта задача становится `Deployed` в E и разблокирует своих прочих зависимых в E. Иначе задачи-зависимости никогда не дошли бы до `Deployed` и кросс-задачная готовность не удовлетворялась бы вообще (обоснование -- [004](004-target-architecture.md), раздел про семантику замыкания). Само дерево и порядок замыкания при этом одинаковы во всех окружениях: окружение -- слой скоупинга и гейтинга поверх чистого графа, а не его усложнение.

Мультиокружение (staging, затем prod) -- в объеме с самого начала и является первоклассным ортогональным измерением. Окружение выбирается на запуске (см. поток выше), а не хранится в плане; один прогон скоупится ровно одним окружением -- пара (целевая задача, окружение). Порядок окружений задается конфигурацией (`Environment.Order`, глобально для v1) и определяет прогрессию (staging перед prod); шлюз прогрессии по умолчанию требует prod после staging и редактируется. Конфигурация окружений и per-env готовность описаны в [004](004-target-architecture.md) и [009](009-admin-and-migration.md).

## 3. Координатор без состояния в памяти

`RolloutOrchestrator` -- это `BackgroundService` под распределенной арендой (тот же скелет, что у существующего `TaskReconciliationService`: lease + `PeriodicTimer`). Координатор **не хранит в памяти ничего**. На каждом пробуждении он заново выводит готовый фронт из строк:

> готовый шаг = `Pending`-шаг, у которого все шаги-предшественники (шаги MR из более ранних волн, от которых он зависит по ребрам плана) находятся в `Succeeded` или `Skipped`.

Раз фронт выводится из БД, падение и рестарт возобновляют выкатку бесплатно: новый экземпляр (или тот же после аренды) читает те же строки и приходит к тому же фронту. Никакого "продолжить с шага N в памяти" -- продолжать нечего, память пуста по построению.

Координатор диспетчит `DeployStepRequested` до **ограничения параллельности по волне** (per-wave concurrency cap): в пределах волны шаги независимы и могут идти параллельно, но их число ограничено, чтобы не залить провайдер и не превратить конкуренцию за общие MR в шторм. Аренда гарантирует, что диспетчер один; заявка на MR (раздел 4) гарантирует безопасность даже если аренда где-то протекла.

## 4. Атомарная заявка на MR

Это самое острое место безопасности, и оно решается одним durable-механизмом, а не набором таймеров. Перед любым `StartAsync` шаг атомарно compare-and-set переводит `MrDeployClaim(MergeRequestId, EnvironmentId)` из `NotStarted` в `Claiming` под single-writer PK/`RowVersion`, и **до внешнего вызова** персистит `MrDeploymentState = Deploying` для пары (MR, окружение). Ключ заявки -- пара (MR, окружение): один и тот же MR может законно выкатываться в два **разных** окружения одновременно, а заявка запрещает двойную выкатку только в пределах **одного** окружения.

Одна эта заявка закрывает **три гонки сразу**:

| Гонка | Что происходит без заявки | Что дает заявка |
|---|---|---|
| (a) Два параллельных прогона делят один MR в одном окружении | Оба зовут `StartAsync` -> двойная выкатка | Проигравший claim-падает; как только победитель пометит пару (MR, окружение) `Deployed`, проигравший короткозамыкает свой шаг в `Skipped` |
| (b) Повторная доставка первого dispatch (Rebus redelivery) | Повторный шаг снова триггерит выкатку | Повторный dispatch видит "claimed-by-me" и возобновляет через `ExternalRef`, а не триггерит заново |
| (c) Падение между claim и внешним вызовом | Рестарт слепо повторяет вызов | `DeploymentState=Deploying` уже персистнут -> при возобновлении зовется `ReconcileAsync` (спросить провайдер про пайплайн с детерминированным ключом), а не повторный триггер |

**Почему не lease-expiry.** Аренда с истечением без fencing -- известно небезопасный паттерн: истекшая-но-живая нода думает, что все еще владеет ресурсом, и делает второй вызов, пока владеет новый. Никакой таймаут этого не чинит, потому что "истекла" и "остановилась" -- разные события. Корректность у нас держится на **claim + машине состояний шага + сверке по `ExternalRef`**, а per-rollout аренда нужна только для живости (чтобы диспетчер был один и работа двигалась). Это разделение -- главное, что отличает движок от наивного "взял аренду -- выкатывай".

```csharp
// Предлагаемая форма атомарного захвата (иллюстрация, не копия кода)
// Единственный писатель побеждает; остальные получают 0 строк и уходят в Skipped/resume.
var claimed = await db.MrDeployClaims
    .Where(c => c.MergeRequestId == mrId && c.EnvironmentId == envId && c.State == ClaimState.NotStarted)
    .ExecuteUpdateAsync(s => s
        .SetProperty(c => c.State, ClaimState.Claiming)
        .SetProperty(c => c.OwnerRolloutId, rolloutId), ct);
// claimed == 0 -> проверить владельца: это я (resume по ExternalRef) или чужой (Skipped)
```

Опциональная проверка дрейфа: если после снятия снимка голова MR сдвинулась, `MergeShaAtSnapshot` не совпадет с текущим `MergeSha` -- шаг переводится в `Failed` для ручного разбора, а не выкатывается на устаревшем состоянии.

## 5. Контракт стратегии выкатки

Стратегия -- ось расширения (b) из [005](005-extension-model.md): ключ `Repository.DeployStrategyKey` (второе измерение рядом с `VcsConnection.ProviderType`, потому что принцип выкатки зависит от репозитория, а не от соединения), переопределяемый на уровне `PlanItem`. `DeployContext` несет **целевое окружение** (ключ), так что стратегия выкатывает MR именно в него; env-специфичные параметры (имя пайплайна, ветка, переменные) живут в schema-declared настройках стратегии, адресуемых per окружение. `DeployStrategyKey` при этом env-независим -- окружение есть параметр рантайма. Контракт двухфазный, чтобы асинхронные пайплайн-деплои были возобновляемыми:

```csharp
// Providers.Abstractions/Deploy/IDeployStrategy.cs -- предлагаемая форма
public interface IDeployStrategy
{
    DeployCapabilities Capabilities { get; }
    Task<DeployResult>  StartAsync(DeployContext ctx, CancellationToken ct);
    Task<DeployResult>  PollAsync(string externalRef, CancellationToken ct);
    Task                CancelAsync(string externalRef, CancellationToken ct);
    Task<DeployResult?> ReconcileAsync(DeployContext ctx, CancellationToken ct);
}

public sealed record DeployResult(
    DeployOutcome Outcome,          // Succeeded | Failed | Awaiting | AlreadyDone
    string?       ExternalRef = null,
    string?       Message     = null);
```

| Исход | Значение | Что делает движок |
|---|---|---|
| `Succeeded` | Синхронно выкачено | Шаг -> `Succeeded`, `DeploymentState` MR -> `Deployed` |
| `Failed` | Ошибка выкатки | Шаг -> retry/`Failed` по политике раздела 6 |
| `Awaiting` | Запущен асинхронный пайплайн | Шаг -> `Awaiting`, `ExternalRef` сохранен, включается `StepWatcher` |
| `AlreadyDone` | Уже было выкачено (идемпотентный no-op) | Шаг -> `Succeeded` без побочных эффектов |

**`AlreadyDone` -- это контракт, а не удобство.** `gitlab-merge` возвращает `AlreadyDone`, если MR уже смержен; `gitlab-pipeline` триггерит именованный пайплайн и возвращает `Awaiting` + `ExternalRef`. `ReconcileAsync` позволяет возобновленному шагу *переприцепиться* к уже летящему пайплайну (найдя его по детерминированному idempotency-ключу), а не триггерить второй.

**Асинхронные пайплайны.** `StartAsync -> Awaiting+ExternalRef`; отдельный `StepWatcher` поллит `PollAsync` с бэкоффом. Обязателен **watchdog-таймаут**, который принудительно переводит зависший шаг в `Failed` -- иначе шаг может висеть в `Awaiting` вечно. Опциональный вебхук о завершении пайплайна (через тот же путь ингестии, [008](008-ingestion-and-messaging.md)) может закрыть шаг раньше поллинга; гонка "поллинг против вебхука" разрешается той же машиной состояний шага (кто первый перевел -- тот и перевел, второй видит уже не `Awaiting`).

## 6. Повтор, пропуск, отмена

Политика по умолчанию -- **fail-stop**: у шага `AttemptCount` с ограниченным экспоненциальным бэкоффом для транзиентных ошибок; за пределом лимита шаг переходит в `Failed`, и прогон встает в `Paused`. Дальше -- оператор:

| Действие | Эндпоинт | Семантика |
|---|---|---|
| Повтор шага | `POST /api/rollouts/{id}/steps/{stepId}/retry` | Сбрасывает шаг в `Pending`, координатор подберет его на следующем пробуждении |
| Пропуск шага | `POST /api/rollouts/{id}/steps/{stepId}/skip` | Шаг -> `Skipped`; оператор берет на себя, что MR выкачен вне движка или не нужен |
| Отмена прогона | `POST /api/rollouts/{id}/cancel` | `Status -> Cancelling`, новый dispatch прекращается, летящие шаги доигрывают (best-effort `CancelAsync` для пайплайнов) |

**Forward-only, fix-forward.** Автоматического отката нет. Уже смерженный MR нельзя размержить -- поэтому частично сбойный мультисервисный прогон (часть MR смержена, поздний шаг упал) оставляет оператору `Paused`-прогон и ручное продвижение вперед через retry/skip. Для некоторых целей это может быть неприемлемо; ограничение названо прямо, а не спрятано (реестр рисков -- [004](004-target-architecture.md)).

Дрейф: `MergeShaAtSnapshot` сверяется перед выкаткой шага; расхождение -> `Failed` на ручной разбор (раздел 4).

## 7. Идемпотентность как тестируемый контракт

Идемпотентность стратегии -- обязательство контракта, а не гарантия системы типов. Компилятор не заставит `StartAsync` быть идемпотентным. Поэтому предлагается **conformance-тест SDK**: набор тестов, которые прогоняются против любой реализации `IDeployStrategy` и проверяют инварианты -- повторный `StartAsync` с тем же `DeployContext` дает `AlreadyDone` (или тот же `ExternalRef`), `ReconcileAsync` находит запущенное, `PollAsync` по неизвестному `ExternalRef` не бросает. Новая стратегия обязана пройти этот SDK, иначе ее нельзя считать готовой.

Честная граница: **остаточный best-effort остается**. Если сторонний провайдер пайплайнов не уважает клиентский idempotency-токен (а GitLab pipeline triggers это могут), то "exactly-once deploy" деградирует до best-effort даже при наличии заявки на MR: заявка не даст *нам* дернуть дважды, но не помешает провайдеру запустить дубликат, если наш `ExternalRef`-reconcile его не находит. Это смягчено (claim-before-call + `ExternalRef` reconcile + watchdog), но не устранено, и так и записано в рисках.

## 8. Действия трекера и уведомления -- отдельным путем

Смена статуса в трекере и отправка в Telegram -- это ось расширения (c) из [005](005-extension-model.md) (`IActionHandler`, опциональный `ITrackerMutator`, пробуемый через `is`). Ключевое правило движка: **действие никогда не валит шаг выкатки**.

И выкатка, и переходы ингестии публикуют тонкие события. `ActionDispatcher` матчит их против строк `ActionBinding` (event -> action type -> scope, данные, не код) и enqueue-ит `ActionRequested` в **отдельный** `ActionConsumer`. Поэтому упавшее действие (Telegram недоступен, трекер вернул 500) логируется и ретраится независимо и **никогда** не переводит `RolloutStep` в `Failed`. Деплой уже случился -- то, что уведомление о нем не ушло, не должно откатывать факт выкатки или блокировать волну.

```yaml
# ActionBinding -- конфигурация, не код. Новая привязка = строка в БД,
# новый ТИП действия = один класс + AddX() (см. 005).
event: StepSettled            # или TaskReadinessChanged, RolloutSucceeded, ...
action: tracker-status        # tracker-status | tracker-comment | telegram
scope: { kind: Task, taskId: PROJ-42 }
settings: { status: "Deployed" }
enabled: true
```

Двойной выстрел действия при падении сразу после побочного эффекта ограничен per-binding дедупом (тот же inbox-принцип, [008](008-ingestion-and-messaging.md)), но не устранен полностью -- см. риски фазы P4 в [009](009-admin-and-migration.md).

Существующие OpenTelemetry/Serilog/Seq и проброс span'ов Rebus несут телеметрию выкатки бесплатно; append-only `RolloutStepAttempt`/`RolloutEvent` дают аудируемый таймлайн (с политикой ретенции, чтобы логи не росли безгранично).

## 9. Порядок работ

Движок -- фаза **P3** дорожной карты ([009](009-admin-and-migration.md)), после того как per-task план (P2) уже ходит рядом с глобальным. Внутри P3:

1. `DeploymentState` (Core) per (MR, окружение) через `MrDeploymentState` + `Environment` + `Rollout` (с `EnvironmentId`)/`RolloutStep`/`MrDeployClaim` (per (MR, окружение)) + append-only логи; зеркальные миграции с per-entity rowversion/xmin в `ProviderSpecificMapping` (помнить про удвоенное число rowversion-сущностей).
2. Семейство `IDeployStrategy` + `gitlab-merge`/`gitlab-pipeline` + `Workers.Executor` (арендованный координатор + консьюмер шагов + асинхронный `StepWatcher`) с атомарной заявкой, замороженным `PlanSnapshot`, resume через `ReconcileAsync` и запретом запуска при нарушении обязательного ребра.
3. Эндпоинты launch/progress/cancel/retry/skip + сид права `release.execute`; PWA: запуск + живой прогресс + история.

Определение готовности каждой фазы неизменно: `TreatWarningsAsErrors` (0 предупреждений), зеркальные миграции на обоих провайдерах, `Kind=Utc`, и -- поскольку именно новый фильтрованный индекс, семантика заявки и токены конкурентности SQLite не воспроизводит -- проверка инвариантов на живом SQL Server и Postgres, а не только на SQLite. Иначе это повтор уже случавшегося провала аудита. Перед коммитом -- `bash scripts/clean-empty-files.sh`.
