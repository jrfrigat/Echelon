# Echelon

**Echelon** планирует и выполняет выкатки вокруг той единицы, в которой люди на самом
деле работают, - вокруг **задачи**. Он читает задачи из трекера и merge request'ы из одного или
нескольких VCS-подключений, выясняет всё, чего задача ждёт, раскладывает работу по волнам выкатки и
ведёт её в каждое окружение.

Задача редко умещается в один репозиторий. Echelon берёт подзадачи, связанные задачи и
правила порядка репозиториев и отвечает на вопрос, который релиз-инженер задаёт каждый день: что
должно уехать, в каком порядке и что ещё не готово.

> **Статус: в бою не проверен.** Код покрыт тестами, обе СУБД проверены на живых серверах, но ни одна
> выкатка ещё не выполнялась против настоящего GitLab. Прежде чем полагаться, прочитайте
> [Зрелость](#зрелость).

## Принципы

- **План - это проекция, а не сохранённое мнение.** Каждое событие приёма строит его заново из
  атласа, поэтому он не может разойтись с реальностью. Решения оператора живут дельтами и
  переигрываются на каждой сборке, а не лежат готовым результатом, который затрёт первый же вебхук.
- **Одна деривация.** Пересчёт, ручная правка, импорт YAML и сам запуск приходят к порядку выкатки
  одним и тем же кодом, а план записывает порядок, который решил. Три копии этой логики - это три
  шанса выкатить в порядке, которого никто не утверждал.
- **Никаких молчаливых планов.** Выкатка может пойти против объявленного ограничения - иногда должна,
  - но не может при этом выглядеть чистой. Каждое нарушенное ограничение записано в плане.
- **Ядро не знает ни одного провайдера.** Словари GitLab и Яндекс.Трекера, их статусы и форматы
  ключей живут в адаптерах. Домен видит только нормализованные значения.
- **Очерёдность выкатки - одно, способ выкатки - другое.** Очерёдность одна для всех окружений; от
  окружения зависит лишь то, как репозиторий уезжает и что там считается готовностью.

## Что он делает

| | |
| :-- | :-- |
| **Приём** | Вебхуки и опрос VCS- и трекер-подключений, с дедупликацией через inbox |
| **Планирование** | Замыкание зависимостей задачи, разложенное по волнам связями, иерархией и правилами репозиториев |
| **Правила порядка** | YAML-документ (группы и `needs`), обобщающий "репозиторий A после репозитория B", с визуальным редактором |
| **Выполнение** | Выкатки по окружениям, одна заявка на пару (merge request, окружение), подключаемые стратегии деплоя |
| **Готовность** | Правила на окружение, переопределяемые на репозитории, с пином на отдельный MR как аварийным выходом |
| **Ретенция** | История выкаток и планов стареет, чтобы архив мог наконец забрать закрытые задачи |

## Структура решения

Onion, зависимости только внутрь:

```
Core                    enum'ы, чистый разбор; ноль зависимостей
  <- Application        порты, контракты сообщений, алгоритм планирования (без EF)
      <- Infrastructure модели EF, DbContext, адаптеры (Rebus, Redis, DataProtection)
      <- Providers.Abstractions <- Providers.GitLab / Providers.YandexTracker
          <- Web (корень композиции, API, хостинг PWA) / Ingress.Webhooks
```

Алгоритм планирования чистый и тестируется без базы. Провайдеры регистрируются на этапе компиляции
через keyed services, а не подгружаются в рантайме.

## Установка

Нужны .NET 10 SDK и Docker.

```bash
git clone https://github.com/jrfrigat/echelon.git
cd echelon
cp .env.example .env      # задайте пароли, которые он перечисляет
docker compose up -d
# Откройте http://localhost:8081
```

PostgreSQL вместо SQL Server и один экземпляр без Redis:

```bash
docker compose -f docker-compose.yml -f docker-compose.postgres.yml -f docker-compose.single-instance.yml up -d
```

## Сборка и запуск

```bash
dotnet build Echelon.slnx    # 0 ошибок, 0 предупреждений; предупреждения - ошибки
dotnet test Echelon.slnx
dotnet run --project src/Echelon.Web
```

Миграции по умолчанию применяются на старте. Для нескольких реплик выключите это
(`Database__MigrateOnStartup=false`) и накатывайте из CI или init-контейнера, иначе реплики гонятся.

## Зрелость

Проверено:

- 667 тестов, 0 предупреждений, предупреждения как ошибки в CI
- миграции накатаны начисто на живых SQL Server 2022 и PostgreSQL 16, включая циклы отката
- приложение стартует, мигрирует и отвечает healthy на обеих СУБД
- HTTP API покрыт против настоящего хоста: маршруты, политики авторизации, коды и тела ответов

Не проверено:

- **ни одна выкатка не выполнялась против настоящего GitLab** - ни одна стратегия деплоя не работала
  по-настоящему
- образы в среде разработки не собираются (реестр фильтруется)
- поведение под нагрузкой и на нескольких репликах закрыто рассуждениями, а не замерами
