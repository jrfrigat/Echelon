# Echelon - планирование и выполнение выкаток

<p align="center"><a href="README.md">English</a> - <b>Русский</b></p>

[![CI](https://github.com/jrfrigat/echelon/actions/workflows/ci.yml/badge.svg)](https://github.com/jrfrigat/echelon/actions/workflows/ci.yml)
[![.NET](https://img.shields.io/badge/.NET-10-512BD4)](https://dotnet.microsoft.com/)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

Echelon планирует и выполняет выкатки вокруг той единицы, в которой люди на самом деле работают, - вокруг **задачи**. Он читает задачи из трекера и merge request'ы из одного или нескольких VCS-подключений, выясняет всё, чего задача ждёт - подзадачи, связанные задачи, правила порядка репозиториев, - раскладывает работу по **волнам выкатки** и ведёт её в каждое окружение. Задача редко умещается в один репозиторий, и Echelon отвечает на вопрос, который релиз-инженер задаёт каждый день: что должно уехать, в каком порядке и что ещё не готово.

**Планирование от задачи - YAML-правила порядка с визуальным редактором - выкатки и готовность по окружениям - адаптеры GitLab и Яндекс.Трекера - SQL Server или PostgreSQL - админка на Blazor**

> **В бою не проверен.** Код покрыт тестами, обе СУБД проверены на живых серверах, но ни одна выкатка ещё не выполнялась против настоящего GitLab. Прежде чем полагаться, прочитайте [Зрелость](#зрелость).

## Возможности

- **Планирование от задачи, а не от ветки** - замыкание зависимостей целевой задачи (подзадачи, связанные задачи, порядок репозиториев) превращается в упорядоченные волны выкатки, поэтому правка на пять репозиториев уезжает как одно целое
- **План - это проекция, а не сохранённое мнение** - каждое событие приёма строит его заново из атласа, а решения оператора живут дельтами и переигрываются на каждой сборке, вместо готового результата, который затрёт первый же вебхук
- **Одна деривация** - пересчёт, ручная правка, импорт YAML и сам запуск приходят к порядку выкатки одним и тем же кодом, а план записывает порядок, который решил
- **Никаких молчаливых планов** - выкатка может пойти против объявленного ограничения, но каждое нарушение записано в плане; выглядеть чистой при этом она не может
- **YAML-язык порядка** - группы и `needs` обобщают "репозиторий A после репозитория B" на задачи, коннекторы и репозитории, а визуальный редактор порождает тот же документ, который читает планировщик
- **Импорт и проверка плана** - выгрузите план, поправьте волны, отправьте обратно; `validate` делает ту же сверку, что и `import`, но ничего не сохраняет
- **Правки состава** - merge request можно принудительно убрать из выкатки или добавить в неё; решение хранится на задаче и переживает следующее событие приёма
- **Выполнение по окружениям** - одна заявка на пару (merge request, окружение), подключаемые стратегии деплоя (слияние, запуск пайплайна или своя) и шлюз прогрессии окружений
- **Правила готовности** - на окружение, с переопределением на репозитории и пином на отдельный MR как аварийным выходом, когда сигнал наблюдать нечем
- **Две СУБД, одна модель** - SQL Server и PostgreSQL, а расхождения провайдеров (токен конкурентности, диалект фильтрованного индекса, коллация) собраны в одном файле
- **Регистрация провайдеров на этапе компиляции** - keyed services, без сканирования сборок в рантайме; ломающая правка порта становится ошибкой компиляции в каждом адаптере
- **Ретенция, дающая архиву сливаться** - история выкаток и планов стареет, поэтому задача, которую хоть раз выкатывали, наконец покидает оперативную базу
- **Админка на Blazor** - отдаётся с того же origin, что и API, локализована на английском и русском

## Быстрый старт

Нужны .NET 10 SDK и Docker.

```bash
git clone https://github.com/jrfrigat/echelon.git
cd echelon
cp .env.example .env      # задайте пароли, которые он перечисляет
docker compose up -d
# -> http://localhost:8081
```

PostgreSQL вместо SQL Server и один экземпляр без Redis:

```bash
docker compose -f docker-compose.yml -f docker-compose.postgres.yml -f docker-compose.single-instance.yml up -d
```

Сборка и запуск из исходников:

```bash
dotnet build Echelon.slnx    # 0 ошибок, 0 предупреждений; предупреждения - ошибки
dotnet test Echelon.slnx
dotnet run --project src/Echelon.Web
```

> Миграции по умолчанию применяются на старте. Для нескольких реплик выключите это
> (`Database__MigrateOnStartup=false`) и накатывайте из CI или init-контейнера, иначе реплики гонятся.

## Как строится выкатка

```
трекер + VCS  ->  атлас   ->  замыкание  ->  волны   ->  выкатка в окружение
   приём         задачи,      чего ждёт    порядок     одна заявка на пару
  (вебхук         MR,         цель         стадий      (merge request,
   или опрос)    ветки                                  окружение)
```

Порядок складывается из трёх источников в один граф: связи и иерархия задач, правила порядка
репозиториев и собственные рёбра оператора. Циклы разрываются снятием наименее критичного ребра, и
каждое снятие записывается в план как конфликт.

## Архитектура

Onion, зависимости только внутрь:

```
Core                    enum'ы, чистый разбор; ноль зависимостей
  <- Application        порты, контракты сообщений, алгоритм планирования (без EF)
      <- Infrastructure модели EF, DbContext, адаптеры (Rebus, Redis, DataProtection)
      <- Providers.Abstractions <- Providers.GitLab / Providers.YandexTracker
          <- Web (корень композиции, API, хостинг PWA) / Ingress.Webhooks
```

Алгоритм планирования чистый и тестируется без базы. Два хоста поставляются отдельными образами:
приложение (API и админка) и приём вебхуков, который можно выставить наружу отдельно, чтобы API
выставлять не пришлось.

> Для авторов провайдеров публикуются три библиотеки - `Echelon.Core`,
> `Echelon.Providers.Abstractions` и `Echelon.Application`. Хосты, PWA и сборки миграций
> поставляются образами, а не зависимостью, которую стоит на себя брать.

## Зрелость

Проверено:

- 669 тестов, 0 предупреждений, предупреждения как ошибки в CI
- миграции накатаны начисто на живых SQL Server 2022 и PostgreSQL 16, включая циклы отката
- приложение стартует, мигрирует и отвечает healthy на обеих СУБД
- HTTP API покрыт против настоящего хоста: маршруты, политики авторизации, коды и тела ответов

Не проверено:

- **ни одна выкатка не выполнялась против настоящего GitLab** - ни одна стратегия деплоя не работала по-настоящему
- образы в среде разработки не собираются (реестр фильтруется)
- поведение под нагрузкой и на нескольких репликах закрыто рассуждениями, а не замерами
